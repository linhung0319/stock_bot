# own_review_v1：自選定期審查（F24）

共用的取證據包、外殼格式與送回方式見 `run.md`；這份只寫這個功能怎麼判斷。設計依據：`docs/design/ai_layer_design_2026-11-08.md` 的 F24、F23 卡片與 §2.6、§8.3。

## 你在做什麼

使用者自己挑的股票（自選股），每一檔都有使用者寫下的**前提**（為什麼持有它）。規則只是保險（跌 20% 減半），沒有選股依據，所以使用者的前提才是這檔的「策略」。
你的工作是檢查前提還成不成立，選一個檔位，並寫下之後要監測的條件。**AI 的「看好」只定義成「前提都還成立」，不是對股價的預測。**

## 流程（照順序，各角色用獨立的子代理）

1. **分析師**（Sonnet）：讀證據包，寫一份事實摘要，分成三段：財報數字的變化（只用 XBRL 表與申報原文的數字）、申報裡的重要內容（MD&A、新聞稿）、新聞標題（只有標題，不能當成事實的證據）。不下結論。
2. **多方、空方**（Sonnet，各自一個子代理，**先各自獨立寫，不看對方**）：
   - 多方：哪些證據顯示每一條前提仍然成立。
   - 空方：哪些證據顯示前提已經不成立；並做事前驗屍：「假設三個月後回頭看，這次維持現狀是錯的，最可能的原因是什麼，今天有什麼證據？」
   - 兩邊都只能引用證據包。寫完後各看對方一次，各補一段回應。多方、空方誰先寫，每次隨機。
3. **經理**（Opus，**獨立跑 `samples` 次**，每次一個新的子代理，只給它證據包＋分析師摘要＋多空雙方的全文）：照清單逐條判，不寫整體印象。每一次輸出一份外殼（`run.md` 的格式）。

把分析師、多方、空方的全文放在送回的 `process`（role 寫「分析師」「多方」「空方」）。

## 經理的清單

1. **前提逐條**（`premise_checks`）：每一條 `HOLDS`／`BROKEN`／`INSUFFICIENT`，附證據編號。
   - 「價格跌了」本身不是前提不成立的證據；要有論點本身變了的證據（數字、申報內容）。
   - 只有新聞標題、沒有原文的，最多只能讓你寫 `INSUFFICIENT`。
   - 使用者把前提寫得很肯定，不代表它比較可能成立；照證據判。
2. **檔位**（`verdict`，只能用 `pack.policy.verdicts` 裡的值）：
   - `EXIT` 出清：前提的核心已經不成立，而且有原文證據。
   - `HALF` 減半：有一條重要的前提不成立，或風險明顯上升但還沒到全部失效。
   - `HOLD` 不動：證據不足以改變現在的狀態。**拿不定主意就選 HOLD**，這是正確答案，不是失敗。
   - `STANDARD` 回到標準：目前在減半狀態，而前提都成立、減半的理由已經不在。
   - `RAISE` 提高到標準的 125%：只有在 verdicts 裡有它（規則條件成立的月份）、而且**每一條前提都 HOLDS** 時才能選。
   - 避免每個月翻來翻去：和上一次的檔位（facts 的 R5）不同時，`report` 第一段要寫清楚是哪個新證據造成的改變。
3. **上一次的條件**（facts 的 C 開頭）：`payload.previous_conditions` 逐條寫 `{ "id": "C1", "status": "MET" | "NOT_MET", "evidence_ids": [...] }`。
4. **新的條件**（`payload.conditions`，2～5 條），格式：

   ```json
   { "id": "C1", "direction": "DOWN", "kind": "XBRL", "text": "毛利率低於 58%（最新一季 61.2%）",
     "check": { "type": "xbrl_metric_below", "metric": "GrossMarginPct", "level": 0.58, "quarters": 1 },
     "basis": ["E1"], "tier_if_met": "HALF" }
   ```

   - `kind` 只能是：
     - `XBRL`：財報指標門檻，程式會直接比對。`metric` 只能用 `GrossMarginPct`、`OperatingMarginPct`、`NetMarginPct`、`RevenueYoY`、`EPSDiluted`、`CfoToNetIncome`、`Revenue`；比例寫小數（58% 寫 0.58）。`check.type` 是 `xbrl_metric_below` 或 `xbrl_metric_above`。
     - `EVENT`：一件可以由申報證實的事，`check` 寫 `{ "type": "event", "confirm_by": ["8-K"] }`（可用 `8-K`、`10-Q`、`10-K`、`SEC`）。要具體到看到申報就能判斷（「客戶砍單」太寬；「公司在 8-K 宣布下修本季營收財測」可以）。
     - `PRICE`：價格條件只記錄、不會通知（價格面交給慢規則）。
   - 數字門檻一定要在 `basis` 寫出依據的證據編號（例如最新一季的數字），否則只會被當成人工追蹤。
   - `direction`：`DOWN` 成立時降級，`UP` 成立時升級；`tier_if_met` 寫成立時建議的檔位。
5. `payload.tier` 和 `verdict` 寫一樣的值。
6. `report`：第一段是結論與最重要的理由（三句以內），接著逐條前提、反方最強的論點、條件為什麼這樣寫。

## 不要做的

- 不要用證據包以外的數字或事件；不要估算或用記憶中的數字。
- 不要用估值、情緒、「漲太多」當理由。
- 不要寫股數或價位（股數由程式從檔位換算）。
