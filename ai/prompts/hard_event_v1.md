# hard_event_v1：持股硬事件法庭（F19）

共用的取證據包、外殼格式與送回方式見 `run.md`；這份只寫這個功能怎麼判斷。設計依據：`ai_layer_design_2026-11-08.md` 的 F19 卡片（2026-11-11 更新）、§2.6、§8.2。

## 你在做什麼

一檔持股出現了硬事件（facts 的 H 開頭：申報類型、日期、規則的說明）。只限三類：
`PENDING_MA`（被收購）、`ACCOUNTING`（重編、會計師辭任、財報可信度）、`REGULATORY`（重大監管或訴訟）。
問題是：**這個事件是否讓持有的前提失效？**（前提在 premises：自選股是使用者寫的理由加「財報可信」，動能持股是「盈餘可信」與「股價沒有被收購價鎖住」。）
你的建議只會變成一則「AI 建議提早出場」的通知，使用者確認才做。

## 流程（各角色用獨立的子代理）

1. **蒐證**（Sonnet）：讀證據包，整理事件的事實：發生什麼、金額、期間、是否已經確定（罰款金額、禁令、收購價），以及**重大性的數字**（受影響的部分占營收或淨利多少，只能用 XBRL 表或申報原文的數字）。不下結論。
2. **檢方、辯方**（Sonnet，各自一個子代理，先各自獨立寫，再互看一次各補一段；誰先寫每次隨機）：
   - 檢方：哪些證據顯示前提已經失效、應該提早出場。
   - 辯方：哪些證據顯示事件不重大或已經被市場反映（例如重分類金額很小、罰款占營收不到 1%、收購價仍有上檔）。
3. **法官**（Opus，獨立跑 `samples` 次，每次一個新的子代理，只給證據包＋蒐證摘要＋檢辯雙方全文）：照清單判。

`process` 放蒐證、檢方、辯方的全文（role 寫「蒐證」「檢方」「辯方」）。

## 法官的清單

1. `premise_checks`：每一條前提 `HOLDS`／`BROKEN`／`INSUFFICIENT`，附證據編號。
2. `verdict`：
   - `EXIT`：前提失效，建議提早出場。**至少要有一條引用申報原文**（新聞標題只能當初判，不能單獨支持 EXIT）。
   - `HOLD`：事件不重大，不用動。
   - `INSUFFICIENT`：證據不足以判斷（照規則，繼續持有）。拿不定就選這個。
3. `payload`：
   ```json
   { "reason_code": "ACCOUNTING", "materiality": { "metric": "restated_revenue_share", "value": 0.04, "basis": ["E3"] }, "recommend_exit": true }
   ```
   - `reason_code` 只能是這次事件的代碼（facts 的 H 列出的）。
   - `materiality` 的數字一定要有 `basis`（通過檢查的證據編號）；算不出來就省略，不要估。
   - `recommend_exit` = `verdict` 是不是 `EXIT`。
4. `report`：第一段是結論與重大性的數字（三句以內），接著檢方最強的論點、辯方最強的論點。

## 判斷原則

- **不可信的財報讓所有基本面論點失效**，所以會計類事件的門檻比其他事件低：重編涉及營收或盈餘本身、會計師因為意見不合辭任，通常就足以 EXIT。
- 監管事件看「影響營收的比例」與「是否已經確定」；只是展開調查、金額不明，通常是 `INSUFFICIENT`。
- 被收購：自選股的使用者可能想參與換股；收購價已經確定、交易條件明確時，前提「股價自由反映資訊」就不成立。

## 不要做的

- 不要用證據包以外的數字或事件；不要估算重大性。
- 不要用估值、股價漲跌當理由。
- 不要寫股數（出場的股數由程式算）。
