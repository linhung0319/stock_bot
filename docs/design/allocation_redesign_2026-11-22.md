## 1. 核心

### 1.1 定義

- **核心的市值** `C` = 總資產 − 自選市值 − 動能市值（照舊，核心是清算中心）。也就是 VOO 市值＋SGOV 市值＋帳上現金。
- **SGOV 那一邊** = SGOV 市值＋帳上現金。**比例** `s` = SGOV 那一邊 ÷ `C`。
- 目標 `s` = 20%，界線 15%～25%（常數 `CORE = { bond: 0.20, band: 0.05 }`，放 `engine/types.ts` 的設定，取代 `crashCut`）。
- 全系統只有這個比例決定帳戶放多少現金。動能、自選都不自己留現金（T77）。

> 例：總資產 $100,000，自選 $20,000、動能 $30,000 → 核心 $50,000 = VOO $40,000＋SGOV $10,000。SGOV 約占總資產 10%。

### 1.2 錢進出核心

任何一桶賣出的錢、入金補完各格後剩下的錢 → **進核心**；任何一桶要買、出金 → **從核心拿**。兩個方向都照 80：20。

`composeWithCore`（`engine/orders.ts`）改寫，`halfUpTo` 拿掉。做法（`inv` = 這份清單其他單做完之後，帳上多出或不足的金額）：

| 情況 | 做法 |
|---|---|
| `inv > 0`（進核心） | VOO 買 `floor(inv × 0.8 ÷ VOO 價)` 股；SGOV 買 `floor(inv × 0.2 ÷ SGOV 價)` 股。配不到整股的零頭留在帳上（算 SGOV 那一邊） |
| `inv < 0`（從核心拿） | **先用帳上現金**（它本來就算在 SGOV 那一邊）。還不夠的部分 `need`：SGOV 那一邊該出 `need_total × 0.2`，其中現金已經出的先抵掉，剩下的賣 SGOV；其餘賣 VOO。賣單一律無條件進位到夠用（現有的 `round`／進位邏輯照舊），多出來的零頭留現金 |
| 單一邊不夠賣（例：SGOV 已經是 0） | 不夠的那一份由另一邊補；不因此多開一張單 |

- 買單總額仍以「現有現金＋賣單金額」的 98% 為上限（`capBuys`，照舊）。
- 行的原因文字：`錢交給核心（VOO 八成、SGOV 兩成）`／`從核心拿錢（VOO 八成、SGOV 兩成）`。
- **不追求每次都剛好 80：20。** 小額進出時整股會偏（VOO 一股約是 SGOV 的五、六倍，$500 進核心會變成 SGOV 1 股＋現金 $400）。偏掉的由 §1.3 的界線處理；B-11 的界線 ±5 pp 本來就包含這個誤差。
- **帳上的現金什麼時候換成 SGOV**：現金算 SGOV 那一邊，所以不影響比例，只是沒有利息。月報有其他單、而且現金超過總資產 0.25%（`orderMin`）時，清單順便加一行 `帳上的現金買 SGOV`（搭便車，取代現在的「帳上的現金交給核心」）；沒有其他單的月份不為它發通知。

**實作時定的細節（T80，`engine/orders.ts` 的 `coreSplit`、`composeWithCore`）**

- **哪些錢照 80：20 分**：只有「這份清單新進核心的錢」＝其他單的賣出 − 買進 − 要留著轉出的錢，加上這份清單帶進來的入金（`CoreContext.fresh`，入金的錢已經在帳上現金裡）。帳上原本的現金本來就算 SGOV 那一邊，不再分一次；不然每出一份清單，閒置現金就有八成被換成 VOO，比例會一直往 VOO 偏。98% 的緩衝先從帳上原本的現金扣。
- **進核心的整股**：VOO、SGOV 各自無條件捨去。**每一行的金額不到總資產 0.25%（`orderMin`）就不列**，錢留在帳上（§1.7 第二列的意思；原本只檢查合計）。所以小額時常常只有 VOO 一行，SGOV 那兩成留現金，比例不變。
- **從核心拿的整股**：要拿的總額 `X` 先扣帳上現金；SGOV 該出 `X × 20% −` 現金已經出的，**四捨五入**到整股（不到半股就不賣，免得多一行很小的單）；其餘賣 VOO，**無條件進位**到夠用。VOO 不夠賣時不夠的由 SGOV 補（進位）；SGOV 是 0 股時整筆由 VOO 出。多賣的零頭不到一股 VOO，留現金。還缺的部分照舊多賣到 ÷ 0.98。
- **搭便車的那一行只在月報**（`CoreContext.sweepCash`，通知種類是 `MONTHLY`、而且照目前的選項有其他單）：入金、出金、改比例、當天通知的清單不動帳上原本的現金。理由：照這一段的字（「月報有其他單」）；當天通知多半是賣單，出金只賣不買，入金清單只處理入金那筆錢比較好懂。SGOV 那一行拆成兩行（`錢交給核心（…）` 與 `帳上的現金買 SGOV`），按代號合併成一張單；金額門檻看兩行合計。
- **「帳上的現金交給核心」那一項（`f: 'CORE'`）不再產生**：沒有其他單、核心也在界線內的月份是「本月不用動」（`MONTHLY_EMPTY`），和上面「不為它發通知」一致。當天通知整則沒有要下的單時（例如慢規則選「照 AI：不動」）回覆當下就完成，不再因為閒置現金等填快照。
- 原因文字用設定的代號與比例組出來：`錢交給核心（VOO 八成、SGOV 兩成）`、`從核心拿錢（VOO 八成、SGOV 兩成）`、`帳上的現金買 SGOV`、F26 的行是 `核心比例`。

### 1.3 界線檢查

- **什麼時候**：只在月報訊號日（B-11：每天檢查沒有好處）。
- **用什麼算**：這份月報其他單（動能換股、依波動度減碼、自選、上限）照 §1.2 合成之後的預期持股，用訊號日收盤價算 `s`。
- `s < 15%` 或 `s > 25%` → 加一項（新的功能代號 **F26 核心比例調回**，`ItemKind: CORE_BAND`）：把 SGOV 那一邊調回 `C × 20%`。買 SGOV 時先用帳上現金。
- **不用搭便車**：月報可以只有這張單（比照單檔上限）。預估頻率：整個帳戶七到十二年一次（B-12），小帳戶因為整股可能多一點。
- 項目文字：
  - 標題：`核心比例調回：SGOV 那一邊占核心 26.3%，超過 25% → 調回 20%`
  - 理由：`核心固定放 VOO 八成、SGOV 與現金兩成。平常不調，超出 15%～25% 才調回。這次是股票跌多了（或漲多了），調回等於跌深買 VOO（漲多買 SGOV）。`
  - 選項：照做（預設）／這次不做。**不用寫理由。**
- **沒做怎麼辦**：這是策略類（`design_v2` §2.3.1）。不用另外記欠單：下個月月報重算 `s`，還在界線外就再列一次，回到界線內就不列。`coreOwe` 這個欄位整個不需要了（§1.6）。
- 月報暫停後重算、入金合併重算：`s` 跟著重算那天的持股與訊號日的價格重算（沒有「訊號日判斷要凍結」的問題，`MonthlyContext.crash` 不再寫）。

> 例：示範帳戶的股票跌 30%、SGOV 不變 → VOO $28,000、SGOV $10,000，`s` = 26.3% → 月報列：賣 SGOV $2,400、買 VOO $2,400（實際是整股）。

**實作時定的細節（T80，`engine/orders.ts` 的 `coreBandCheck`、`coreBandLines`；`engine/report.ts` 的 `coreBandItem`）**

- **兩個地方各算一次，用同一個 `coreBandCheck`**：正式流程的清單用整股算（月報其他項目照預設選項合成之後的預期股數與現金）；`planDay` 的金額模式也有同一個檢查（事件 `CORE_BAND`），只給重放用（§1.6），和 `backtest/b10_account.py` 的 `core_policy='ratio'` 同一套算式。判斷是嚴格大於界線（`|s − 20%| > 5 pp`），和回測相同。
- **F26 的行**：SGOV 那一邊太少 → 賣 VOO `round(差額 ÷ VOO 價)` 股，買 SGOV `floor(0.98 ×（賣得的錢＋帳上現金）÷ SGOV 價)` 股（帳上現金一起買）。太多 → 買 VOO `floor(差額 ÷ VOO 價)` 股，要付的錢 ÷ 0.98 先用帳上現金、不夠再賣 SGOV（進位）；SGOV 不夠賣就買得起多少買多少。換算出來一股都不用動就不列。
- **項目的形狀**：`kind: 'CORE_BAND'`、`f: 'F26'`，沒有 `ticker`（兩檔一起），排在月報的最後（它是其他單合成之後才算的）。理由的最後一句照方向只寫一種（`這次是股票跌多了，調回等於跌深買 VOO。` 或 `這次是股票漲多了，調回等於漲多買 SGOV。`）。
- **這次不做**：不用理由、不寫 `mom.owe`、沒有 `coreOwe`；影子紀錄照「實際和規則不同就記」記 VOO、SGOV 兩筆。上一份月報一直沒回覆時，舊的 F26 和策略項目一樣以新月報為準取消，新月報照現在的持股重算。
- **晚回覆**（提醒過才回，`design_v2` §2.3.1「忘了」）：其他項目重算完之後，F26 的行照回覆當天的持股與價格再算一次（`refreshCoreBand`）；已經回到界線內就清空，備註 `重算後已經回到界線內，這一項不用做`。
- **和動能比例回調的搭便車**：F26 是其他單合成之後才算的，`planDay` 決定要不要撤回回調（「當天沒有其他單」）時還不知道有沒有 F26。月報算出有 F26、而且有回調被撤回時，把搭便車關掉重算一次；重算後還有 F26 才採用（§1.5「F26 本身就是單」）。金額模式（重放）不這樣做，和回測一致。
- `MonthlyContext.coreBand` 記的是「其他單做完之後、調回之前」的 `s`、目標、核心市值，每次產生或重算月報都重算；沒有 F26 的月份也記（T81 的狀態文字要用）。

### 1.4 入金、出金、改比例

**入金**（只買不賣，照舊）：先補「低於目標最多」的格子，缺口小於 0.25% 的不補，剩下的進核心 → 照 §1.2 分。動能每檔的目標改成 `總資產 × 30% × 波動度比例 ÷ 5`（少了崩盤的 ×0.5）。

**出金**（只賣不買）。順序改成：

| 順序 | 現在 | 改成 |
|---|---|---|
| 先做 | 單檔上限檢查 | 照舊 |
| ① | 核心的現金（崩盤中才有） | 動能高於目標的部分 |
| ② | 動能高於目標的部分 | **核心，照 §1.2 的 80：20**（帳上現金先用） |
| ③ | VOO | 動能按比例 |
| ④ | 動能按比例 | 自選按比例 |
| ⑤ | 自選按比例 | — |

- 【D8，照建議】核心那一步照比例（B-11 沒有模擬「先拿 SGOV」）。理由：只有一條規則；先拿 SGOV 的話大額出金後 `s` 掉到界線外，下個月月報還是要賣 VOO 買回 SGOV，多一個下單日。
- 出金清單的「做完之後」那一列（`core_ai` §3.11）多寫一項：`核心裡 SGOV 與現金 19.2%（目標 20%）`。入金、改比例的清單也加。

**改比例**（`changeRatio`）：自選、動能的增減照舊，差額進出核心照 §1.2。`effPrev` 只剩波動度比例。

### 1.5 現有帳戶怎麼轉過去

**不寫專用的轉換程式**：新規則只看持股算出來的 `s`，所以轉換就是第一次界線檢查。

| 部署時的狀態 | 第一份月報會列什麼 |
|---|---|
| 崩盤規則未啟動（核心全是 VOO，`s` ≈ 0%） | F26：賣 VOO、買 SGOV 到 20%。約動到總資產的 10% |
| 崩盤規則啟動中（核心一半 SGOV，動能減半） | F26：賣 SGOV、買 VOO 到 20%；動能每檔的目標回到沒有減半的數字，照現有的比例回調列出（這一次不受「搭便車」限制，因為 F26 本身就是單） |

- 第一次的 F26 項目多一句備註：`這是從崩盤規則換到固定比例的一次性調整。`
- 【D1，使用者 2026-11-22】真實帳戶的持股怎麼調成 stock bot 的建議，是**正式上線時起步清單的事**，不在這裡另外設計轉換（起步的設計照 2026-11-08 的決定，等上線前才做；`design_v2` §2.3「起步」）。這份只留一個要求給那時候：起步清單算核心時用 §1.1 的比例（VOO 八成、SGOV 與現金兩成）。上線前系統裡的帳戶照上表走：部署後第一份月報的界線檢查自然列出 F26，不用特別處理。
- **資料的處理**（部署時的 migration 腳本或第一次流程）：`rule.crash` 改成可選、不讀不寫；`coreOwe` 清掉；`mom.owe` 裡原因是崩盤規則的清掉（其他原因的留著）；`rule.effPrev` 重算成波動度比例。
- **部署前確認沒有還沒回覆、帶 F5／F6 的月報**。有的話先讓使用者回覆或作廢，再部署。
- 影子紀錄裡舊的 F5／F6 留著，網站照樣看得到，標籤加「（已停用）」。

**實作時定的細節（T80，`engine/account.ts` 的 `migrateAccount`、`normRule`）**

- **不寫 migration 腳本，載入時轉**：`loadAccount`（正式）與示範模式讀狀態時呼叫 `migrateAccount`，和那一次操作一起存；只讀的請求不存，下次載入再轉一次，結果相同（重複呼叫不變）。持股不動。
- 做的事：設定補 `coreBond`、`coreBand`；規則狀態有 `crash` 這個欄位（0.17.0 以前）→ 拿掉、`effPrev` 改成 `volW ?? 1`（還沒跑過月報的維持 `null`）、記 `Account.fromCrashRule = true`；`coreOwe` 清掉；`mom.owe` 裡「那則通知上只有崩盤項目（F5／F6）有這一檔動能的單」的清掉，同一則通知上別的策略項目也欠這一檔的留著。
- 月報存的「月報前的狀態」（`SavedState.rule`）可能是舊的：還原時（入金合併、排除重算）同樣經過 `normRule`，`coreOwe` 不還原。
- **第一次的備註**：`fromCrashRule` 的帳戶在「還沒有照做過 F26」之前，每一份 F26 都帶 `這是從崩盤規則換到固定比例的一次性調整。`，理由不寫「漲多了／跌多了」那一句；選「這次不做」不算做過。
- **還沒回覆、帶 F5／F6 的舊通知**（部署前應該先清掉，這裡只保證不壞）：照做時照它列的單合成，核心吸收的差額照新規則分；選「這次不做」不寫 `coreOwe`、動能那幾檔也不記欠單；下一份月報出來時這幾項照舊以新月報為準取消。
- **上表第二列（崩盤規則啟動中）實際會怎樣**（用 0.17.0 的帳戶樣本測過，`test/fixtures/account-0.17.0.json`）：F26 照表列出（賣 SGOV、買 VOO）。動能的目標回到沒有減半的數字，但留任股只有偏離目標超過 ±50% 才列比例回調；減半的部位大約就在目標的一半上下，**不一定超過**（樣本裡四檔都沒超過，那份月報沒有列）。沒列的要等換股、之後偏離夠大、或波動度比例換格時才回到目標。要第一份月報就全部拉回，得另外加轉換的規則（例如啟動中的帳戶 `effPrev` 不重算，讓第一份月報把每檔拉回目標）；照 D1「不另外設計轉換」這裡沒有加，留給主持者決定。

## 3. 自選：賣

### 3.1 分兩種股票

用現有的 `fileKind()`（`app/thesis.ts`）：

| 種類 | 定義 | -20% 時 |
|---|---|---|
| **只有預設前提**（`DEFAULT_ONLY`） | 還沒採用過草稿、沒寫過論點 | **完全照舊**：規則減半（預設照規則），減半檢視只能選減半或出清 |

### 3.2 有論點的股票：跌幅審查

**觸發不變**：收盤比 52 週高點低 20% 以上（`SLOW.drawdown`）。**審查就是現有的減半檢視**（`OWN_DROP`，3 票、分析師可上網、每次都跑新眼光、程式先算跌幅拆解），不另開新任務。名稱從「減半檢視」改成「**跌幅審查**」，prompt 升版（`own_drop_v6`）：題目從「規則要減半，你同不同意」改成「這檔比高點低 20% 以上，逐條檢查前提，並判斷跌幅的來源」。可選的結論仍是出清／減半／不動。

**結論的效力**（改 `dropDecision` 與 `reduceAi`）。【D2，使用者 2026-11-22】只有「前提不成立」會讓它賣：

| 審查結果 | 條件 | 現在 | 改成 |
|---|---|---|---|
| **前提不成立** | 3 票都判同一條前提不成立，每一票都有合格引用（`own_thesis` §1.6 第 1 點的定義，照舊） | 預設減半；3 票都選出清時多一個「照 AI：出清」 | **預設減半**；3 票都選出清時多一個「照 AI：出清」；這次不做要寫理由。AI 那一行：`論點檢查（3 票）：前提「…」不成立` |
| **前提都沒有被判不成立** | 3 票一致、沒有任何前提被 3 票判不成立。**不論跌幅歸因是大盤、產業還是這檔自己** | 歸因大盤或產業且過程式核對 → 多一個「照 AI：不動」；否則減半 | **預設不動，不下單。** 選項：不動（預設）／減半（使用者自己想賣時用，不用理由）。跌幅拆解與歸因照樣顯示，只是資訊：`論點檢查（3 票）：你的 4 條前提都沒有被判不成立。這次下跌：大盤 -8%、產業比大盤 -9%、個股自身 -5%` |
| **票數不一致** | 審查跑完了，但 3 票對「哪一條前提不成立」沒有共識（含只有 1、2 票判不成立） | 減半 | **預設不動**。AI 那一行寫出分歧：`論點檢查：3 票裡有 1 票認為前提「…」不成立，沒有一致結論`。選項同上。照現有的規矩連續 3 次不一致列「要看的事」並自動重新起草論點 |
| **沒跑完** | 逾時、資料缺漏、被退回、沒開成 | 減半 | **不動，並重派**：09:30 重派一次（照舊），還是沒有就隔天再派，最多 3 個交易日。期間通知寫 `AI 論點檢查還沒有結論，先不動；會再檢查`。3 天都沒跑完 → 推告警（現有的 `REVIEW_FAILED`），列「要看的事」，仍然不動 |

- 程式原本拿跌幅拆解核對「個股自身不超過整段一半」才准不動，**這個核對拿掉**（它擋的正是使用者決定接受的情況）。拆解照算、照顯示，並照舊放進證據包。
- prompt `own_drop_v6` 跟著改：檔位「減半」「出清」必須對應一條判不成立的前提；沒有前提不成立就選「不動」，不能因為跌得多、歸因是公司自身而選減半。新眼光找到的新風險照舊只列出來、可以觸發重新起草論點，不直接讓它賣。
- **推播時間不變**：07:30 產生、等到 09:30 推（`pushHold` 的減半那一支照舊）。
- **金額分級**：只有「前提不成立」那一列會下單；金額 ≥ 總資產 5% → 當天通知，否則併入月報（照舊）。
- **不動的那一則怎麼給使用者**：照樣產生一則通知（當天，不分金額大小），LINE 一行：`【當天】MU 比高點低 21.4%：論點檢查（3 票）前提都沒有被判不成立，不減半。不用下單；細節在網站。`
  - **不用回覆**：2 個交易日沒有回覆就自動以「不動」結案（新的結案方式 `AUTO_DEFAULT`，只用在預設不下單的通知；不發提醒）。結案前可以改選減半，系統當場給清單。
  - 影子紀錄照舊三條線：照舊的慢規則（減半的股數）、照 AI、實際。之後看得出不減半是加分還是扣分。
- 靜默期、乙類通知併入、觸發之後另外有審查回來時的處理（`own_thesis` §3.4）照舊。

**實作時補的細節（T82，2026-11-22）**——上面的表沒寫到、但程式必須決定的：

1. **四種結果怎麼判**（`dropDecision`，看的是三票的 `premise_checks`，不是三票選的檔位）：
   - 沒跑完：票沒到齊、有不合格的票、資料缺漏、逾時、被退回。就算送回來的票判了前提不成立也算沒跑完。
   - 前提不成立：三票都判同一條、每一票都有合格引用。**不看三票選的檔位**（三票各選出清、減半、不動也算）；三票都選出清時才多「照 AI：出清」。
   - 前提都沒有被判不成立：三票都選不動，而且沒有任何一票把任何前提判成不成立（引用沒過檢查被降級的也算判過）。
   - 票數不一致：其餘跑完的情況——只有 1、2 票判；各判不同的前提；三票都判了同一條但不是每一票都有合格引用（通知寫「3 票都認為…不成立，但不是每一票都有合格的引用，不算數」）；沒有人判不成立但有人選了減半或出清（prompt 不准這樣選，程式另外在那一票記一筆、不會因此減半）。
   - 只有預設前提的股票（證據包沒有不動這個檔位）`dropDecision` 照舊是建議出清／同意減半／沒有可用的結論三種。「建議不動」這個結果從此沒有股票會產生；舊通知上的照樣顯示。
2. **項目的形狀**：仍是 F7、`OWN_RULE`，多一個記號 `thesisDrop`（種類以觸發當天為準，記在項目上）。選項是「不動」「減半」，前提不成立時是「減半」「（照 AI：出清）」「這次不做」。規則的那條線（`ruleChoice`）一律是減半，影子紀錄才有「照舊的慢規則會怎樣」。**規則的狀態在使用者照做減半、填了快照之後才變成 `HALF`**（寫成選項的效果），不是通知產生時；所以「這次不做」、沒回覆、自動結案都自然留在 `WATCH`。
3. **07:30 那一刻還不知道結果**，所以有論點的股票一律先產生一則當天通知（預設不動、那一行寫「AI 論點檢查進行中…結果出來之前先不動」），照舊等到 09:30 推。結果回來之後：
   - 沒有前提不成立 → 就地更新那一行，仍是不動。
   - 前提不成立、≥ 5% → 就地改成預設減半、要寫理由。
   - 前提不成立、< 5% → 那一項取消並寫明「併入下一份月報」、整則標成被取代（09:30 之前回來的話不會推 LINE），記成等月報的減半；月報把它列成同一種項目（預設減半）。**例外**：今天的月報已經出了（月報日當天觸發、或重派到月報日才回來）→ 留在當天那一則，免得多等一個月；吸收了乙類通知的那一則也留在當天。
   - 結果回來時通知已經不在等回覆：已經自動結案或你先選了不動 → 前提不成立時另發一則當天通知（≥ 5%，標題「跌幅審查：前提不成立」）或等月報（< 5%），其餘只放網站；你先選了減半（等下單）→ 不另外發減半，3 票建議出清的照 `own_thesis` §1.9 當成一次審查的建議，沒有前提被判不成立時推一則提醒「可以回去改決定」。
   - 等月報的那幾週又跌一級：不另外審查（上一次已經判前提不成立，減半已經排著）。
4. **`AUTO_DEFAULT`**：通知的狀態多這一種。只用在「整則都是預設不動的跌幅審查」；滿 2 個交易日的那次每日檢查結案，不產生提醒。**審查還沒有結果（還在跑、沒跑完但還會重派）時先不結案**，等有了結果或確定不再重派才結案——不然通知會在重派的第 3 天前就關掉。結案時寫影子紀錄（備註「2 個交易日沒有回覆，自動照預設（不動）結案」）。
5. **重派的節奏**：上面寫「09:30 重派一次（照舊）」，但原本的程式在 09:30 並沒有重派減半檢視，這次才加。做成：每個交易日 07:30、09:30 各最多派一次，最多 3 個交易日（共 6 次）；第 4 個交易日的 07:30 記成失敗、推 `REVIEW_FAILED`（文字：`MU 的跌幅審查（11-23 觸發）連續 3 個交易日沒有跑完，不再重派。這檔不動；之後財報後的審查與再跌一級時仍會檢查。`），列一件「要看的事」（`DROP_REVIEW_FAILED`，到這檔離開 `WATCH` 或再跌一級為止）。AI 層沒有設定時不會有審查，直接記成不再重派（通知寫「AI 論點檢查沒有跑完，不動」）。
6. **計數**：票數不一致算進定期審查的「連續幾次沒有一致結論」（同一個計數，連續 3 次列要看的事並重新起草）；有共識的（前提不成立、都沒有被判不成立）歸零。沒跑完的不算進定期審查的連續失敗（它有自己的重派與告警）。
7. **前提不成立時記 `aiTier`**（減半；3 票都選出清記出清；觸發原因 `DROP`），之後加回時看得到。沒有前提不成立時不動 `aiTier`。
8. **併進來的乙類、觸發之後另外回來的審查**（`own_thesis` §3.4）：它們本來就是「3 票判同一條前提不成立」，所以在跌幅審查的項目上等同前提不成立——預設減半、要寫理由；那次審查建議出清時多「照 AI：出清」。
9. **靜默期**：前提不成立的項目選「這次不做」→ 那條前提進靜默期；3 票建議出清而你選了減半也進（和以前「沒有照 AI 出清」相同）；照預設減半不進。
10. **審查的結果留到離開 `WATCH`**（`dropReview` 不在通知結案時清掉）：持股頁要寫「11-20 的論點檢查沒有前提被判不成立」。
11. **通知推出去之後才回來的結果**補推一行（03:30 或之後的流程）：`MU 的 AI 論點檢查回來了：前提都沒有被判不成立，不減半。不用下單；細節在通知 #12。`／`…3 票沒有一致結論，不減半。…`／`…前提不成立，預設改成減半。通知 #12 已更新，到網站決定。`。沒跑完的不補推。
12. **回應的紀錄**（`own_thesis_log` 的 `RESPONSE`，type R）多兩種結果：`KEPT`（預設不動、你也選不動）、`HALVED`（選了減半）；前提不成立時選這次不做照舊是 `SKIPPED`。
13. **prompt 與證據包**：有論點的股票「拿不定主意」的預設檔位從減半改成不動（`policy.abstain`），規則的動作寫「不動」；跌幅拆解照樣放在 `rule.detail.attr`（只顯示）；`idioWithinHalf` 留著給 §4.4。

### 3.3 不減半之後的狀態

現在「這次不做」之後，規則把這檔記成「已減半、目標用實際股數」。不減半不能這樣記（它沒有減半，之後也沒有東西要加回）。慢規則的狀態多一個值：

| 狀態 | 意思 | 目標 | 怎麼離開 |
|---|---|---|---|
| `STD` 標準 | — | 標準比重 | 比高點低 20% → 觸發 |
| `HALF` 減半 | 照舊 | 標準比重的一半 | 加回條件成立 → `STD`，買回 |
| **`WATCH` 審查後持有**（新） | -20% 時審查的結果是不動（前提都沒有被判不成立、票數不一致、沒跑完），或使用者選了這次不做 | 標準比重（不變） | ① 加回條件成立（站上 200 日線連續 10 天、距上次切換 ≥ 15 個交易日、跌幅已不到 20%）→ `STD`，**不下單、不通知**；② 再跌一級 → 重新審查（見下）；③ 審查的結果是減半或使用者選減半 → `HALF` |

**繼續跌怎麼辦**【D3，照建議】：每多跌 10 個百分點再審一次——比高點低 30%、40%、50% 各觸發一次跌幅審查（`WATCH.level` 記已經審過哪一級；常數 `DROP_LADDER = [-0.2, -0.3, -0.4, -0.5]`）。每一次的結論與效力都照 §3.2。理由：`WATCH` 是整個部位都還在的狀態，而且價格不再是賣出的理由，更需要隔一段跌幅再檢查一次論點；30%、40% 這幾級不需要新的判斷邏輯。

- `stepSlowRule` 是純函式、重放驗收在用，**不改它的行為**：`WATCH` 的進出寫在外層（`dailyCheck`），只有預設前提的股票永遠走不到 `WATCH`，重放的數字不變。
- 已經在 `HALF` 的股票繼續跌：照舊沒有價格上的動作（`own_thesis` K7），靠出場條件與審查。
- 持股頁：`WATCH` 顯示 `比高點低 23%：11-20 的論點檢查沒有前提被判不成立，沒有減半。再跌到 -30% 會重新審查；站回 200 日線連續 10 天後回到一般狀態。`

**實作時補的細節（T82）**：

- `WATCH` 只記在慢規則的狀態機（`OwnMeta.slow.state`）；「已反映到帳上的目標」（`rule.own[*].applied`）只有標準、減半兩種，`WATCH` 記標準。所以配置、入金、上限的算法都不用改。
- `stepSlowRule` 遇到 `WATCH` 不會切換、不產生訊號，只照舊更新「連續站上均線天數」與「距上次切換的天數」；外層的 `stepWatch` 用這兩個數判回到標準。進 `WATCH` 那天算一次切換（天數歸零），所以最快 15 個交易日後才會回到標準。
- 一天跌過兩級（例如 -25% 到 -45%）只審一次，記最深的那一級；-50% 那一級審過之後不再因為跌幅審查。
- 回到標準時，還沒回覆的跌幅審查項目當場取消（寫「已經站回 200 日均線…這一項取消」），等月報的減半也取消。
- 又跌一級時上一則還沒回覆：那一項取消、整則標成被取代，以新的通知為準；項目上註明上一次審的是哪一級。
- 還沒下單的加回（減半 → 標準、在等月報）遇到新的 -20%：照舊互相抵銷、留在減半，不開審查（它的部位還是一半）。
- 持股頁最後一塊的標題與說明分兩種：有論點的是「跌幅審查與價格」，只有預設前提的照舊是「慢規則（底線）」並加一句「寫了論點之後，跌 20% 會改成只觸發論點檢查」。帳戶頁的門檻條在 `WATCH` 時把門檻改成下一級。

### 3.4 加回

| 從哪裡來 | 加回時 |
|---|---|
| `HALF`（不論是規則、審查、你定的條件、乙類通知造成的） | 條件不變。買回到標準比重，錢從核心照 80：20 拿。通知上 AI 那一行的規矩不變（`own_thesis` §3.4 的 F8） |

### 3.5 沒有改的

你定的出場條件（甲類，預設照做）、AI 判前提不成立（乙類，預設不動）、硬事件、單檔上限 15% → 10%、部位偏大的提醒、定期審查的時機與五個檔位，全部照舊。

### 3.6 照使用者的角度走一遍

| 情況 | 會發生什麼 | 對應 |
|---|---|---|

| 這次不減半，三週後財報後審查判前提不成立 | 乙類通知（建議減半或出清，預設不動）；照做 → `HALF` 或結案 | 照舊 |
| 生命週期 | `STD` → 觸發 → 不減半 `WATCH` →（-30% 再審 → 前提不成立、減半 `HALF` → 站回均線加回 `STD`）或（站回均線 `STD`） | §3.3 |

**實作時補的細節（T82）**：

- 「自己賣了一半」怎麼認：分桶快照裡，這檔在 `WATCH`、清單外賣出的股數 ≥ 原本股數的四分之一、而且沒有賣光（比起「沒賣」更接近「賣一半」）→ 狀態改成 `HALF`，還沒回覆的跌幅審查項目取消，結果頁顯示那一句。賣得更少的照舊只提醒「低於標準比重」，仍在 `WATCH`；賣光照舊是移出自選。

- 審查還在跑的時候（07:30～09:30 之間）就在網站上先回覆：選不動 → 結案，之後才判前提不成立的話另外給（§3.2 第 3 點）；選減半 → 當場給清單。

## 4. 自選：買

### 4.0 原則

1. **買不買仍是使用者決定。** 系統不替使用者選股（`design_v2` §2.2）。新增的是：把使用者「打算怎麼買」先記下來，條件到了提醒並給股數。
2. **所有買進的建議都只進月報**，不發當天通知（買不急；`own_thesis` §1.9「往上的檔位只進月報」照舊）。
3. **預設選項跟著「是誰的決定」**：你事先定的（先買一半的補滿、你定的加碼條件、候補的進場條件）→ 預設照做；AI 發起的（125%、下跌加碼）→ 預設不做。【D10，照建議】
4. **部位只有三個大小**：標準比重的一半、標準、125%。不新增其他比例；股數照舊由程式換算。
5. **錢都從核心照 80：20 拿**；還沒買的那部分就留在核心，不另外保留（T77）。
6. **每一種買進都先過同一組程式檢查**（`buyAllowed(meta, file)`，新的純函式）。任何一項不過就不提：
   - 這檔不在減半狀態、沒有還沒結案的跌幅審查或乙類通知；
   - 沒有未解除的硬事件標記；
   - 最近 30 個日曆天內沒有前提被 3 票判不成立；
   - 做完之後這檔（自選＋動能合計）不超過總資產 10%（現有的 `crossCapBuy`）；超過的部分砍掉，砍到 0 就不提；
   - 沒過時不發通知，持股頁寫一行原因（例：`加碼條件成立，但 11-06 有前提被判不成立，這次不提加碼`）。

**實作時補的細節（T83，2026-11-23）**：`buyAllowed` 在 `engine/buy.ts`，是只看事實的純函式（`buyFacts` 從帳戶整理事實，T84 的加碼條件、下跌加碼與 T85 的候補進場共用）：

- 「減半狀態」= 慢規則狀態或已反映的目標是減半；先買一半、審查後持有不擋。
- 「還沒結案的跌幅審查」= 審查還在跑或還會重派（`dropReviewOpen`）、等月報的減半（`pending` 是減半）、還沒回覆的通知上有這檔的跌幅審查或減半項目。「還沒結案的乙類」= 還沒回覆的通知上有這檔的乙類項目，或記著等月報的乙類建議（`aiTier.suggest`、往下的檔位、有前提）。
- 「30 天內有前提被 3 票判不成立」看新欄位 `OwnMeta.brokenAt`（`recordAiTier` 帶前提時寫，定期審查與跌幅審查都會；之後的審查蓋掉 `aiTier` 也留著），再加上 `aiTier`、`dropReview` 裡的日期（舊資料沒有 `brokenAt`）。
- 上限用現在的持股算（自選＋動能的市值），不先套「已回覆、還沒填快照的清單」；超過的部分砍掉時項目的 note 寫明只買幾股。
- 不給股數時只看狀態（不算上限）：`raiseAllowed` 決定這次能不能讓 AI 選 125% 時用這種；股數到月報時再算。

### 4.1 先買一半，確認後補滿

**什麼時候算「先買一半」**：新的自選開檔時（快照新增、候補進場、轉入、認養），持股頁的標準比重那一欄多一個選項（只在開檔後第一次設定標準比重時出現）：

```
這檔打算放到總資產的 [ 6 ] %
( ) 已經買到這個比例
(•) 先買一半，確認後再補滿        ← 從候補名單進場的預設
```

- 選「先買一半」→ 狀態 `BUILD`（建立中）：目標是標準比重的一半；`OwnMeta.build = { since: 開檔日, confirmBy: 'EARNINGS' }`。
- 沒有選、或留空（現有行為：標準比重 = 現在占總資產的比重）→ `STD`，沒有補滿這件事。**系統不會因為使用者一次買足而提醒。**
- 這是使用者的意圖，不是專業判斷，所以由他選（`confirm_audit` 的四種之一）。
- **有論點、加入時已經比高點低 20% 以上**：現在是「一開始就是減半、等站回 200 日線」。改成一律走 `BUILD`、看下面的確認條件，不看 200 日線（理由：論點是這檔的依據；等均線會和 §4.4 的「論點還在時下跌可以加碼」矛盾）。只有預設前提的照舊（`HALF`、等均線）。

**確認條件**【D4，照建議】：「**開檔之後的第一份財報**」過關：

| 種類 | 過關的定義 |
|---|---|
| 有論點 | 那份財報觸發的審查（財報後審查）3 票一致，沒有任何前提被判不成立，檔位不是減半或出清 |
| 只有預設前提 | 程式比對系統預設前提 D1～D3（沒有硬事件、營收年增沒有連兩季為負、EPS 沒有連兩季低於去年同季）都沒有不成立 |

- 過關 → 下一份月報列一項（F27 補滿，`ItemKind: OWN_FILL`）：`MU：先買的一半已確認（11-20 的財報後審查，3 票，前提都沒有被判不成立）→ 補滿到標準比重，買 12 股`。預設照做。照做或不做之後都離開 `BUILD`：照做 → `STD`；不做 → `STD`，標準比重改成實際的比重（之後不再提）。
- 沒過關（審查沒有一致結論、資料缺漏）→ 等下一份財報。有前提被判不成立 → 走乙類通知，`BUILD` 留著。
- **兩份財報都沒過關，或開檔滿 200 個日曆天** → 「要看的事」列一行：`MU 先買的一半已經 7 個月沒有補滿（兩次財報後的審查都沒有一致結論）。要補滿、維持一半，或重新寫論點，到持股頁決定。`持股頁給兩個按鈕：「維持現在的大小」（標準比重改成實際比重，離開 `BUILD`）、「請 stock bot 草擬」。不自動買。
- 也可以自己加一條加碼條件（§4.2）當確認條件；它成立時一樣補滿。兩者先到的算。
- `BUILD` 期間的賣出規則不變：-20% 照 §3（審查的結果是不動時，另外可能出現 §4.4 的選項）；減半的話賣掉一半的一半，並離開 `BUILD`（進 `HALF`，加回時回到標準比重）。

其他的確認方式沒有採用：只看價格（站上 200 日線）對有論點的股票不是論點的證據；固定等 N 天沒有資訊量。

**實作時補的細節（T83，2026-11-23）**：

1. **怎麼表示，才不影響重放**：慢規則狀態（`OwnMeta.slow.state`）多 `BUILD`；已反映到帳上的目標（`rule.own[*].applied`，`OwnApplied`）也多 `BUILD`。它和 `HALF` 一樣目標是一半（`targetFrac`：標準 1、減半與先買一半 0.5；入金、自選合計的縮放、改比例都照這個算），差在 `BUILD` 和標準一樣**可以被減半**（規則引擎的減半條件從「目標是標準」改成「目標不是減半」）。重放只有 `STD`／`HALF`，`stepSlowRule` 沒改：`dailyCheck` 對 `BUILD` 的股票照標準狀態前進一步，沒有切換就留在 `BUILD`。B-8、B-12 的數字逐位不變。
2. **`BUILD` 期間跌 20%**：
   - 有論點：照 §3.2 開跌幅審查、進審查後持有（`WATCH`），`build` 留著，目標仍是一半（`applied` 還是 `BUILD`）。站回均線（§3.3 的「回到標準」）→ 回到 `BUILD`；審查判前提不成立、你選了減半 → `HALF`、`build` 拿掉；你自己賣了一半（§3.6）→ 一樣 `HALF`、`build` 拿掉。減半的股數照現有的「當時持有的一半」（一半的一半）。
   - 只有預設前提（使用者自己選了先買一半）：規則減半照舊（預設減半，≥ 5% 當天、否則月報）；目標變成 `HALF` 的那一刻（清單產生時）`build` 拿掉。還沒下單的減半被之後的加回抵銷 → 回到 `BUILD`。
   - **從先買一半被減半之後的目標是標準比重的四分之一**（主持者 2026-11-23 定；理由：「減半的話賣掉一半的一半」——減半的意思是目標砍半，BUILD 的目標是一半，所以減半期間是一半的一半；目標若照 §3.3 的表算成標準的一半，入金會把減半退掉一部分）。不改 D4（D4 管的是什麼時候補滿）。加回條件成立時照 §3.4 回到標準比重（不是回到 `BUILD`）。
   - 表示方式：`rule.own[*]` 仍是 `HALF`，多一個記號 `fromBuild`；目標的比例用 `pickFrac`（標準 1、先買一半與一般的減半 0.5、`fromBuild` 的減半 0.25），入金、自選合計的縮放、改比例都用它。所有改 `applied` 的地方都經過 `setApplied`：先買一半 → 減半時記號寫上，減半 → 減半保留，回到標準或標準 → 減半時拿掉。四條路都一樣：只有預設前提的規則減半（規則引擎）、有論點的審查後持有時審查判前提不成立而照做減半、乙類照做減半、你定的出場條件減半（`applyTier`），以及審查後持有時自己賣了一半（§3.6）。重放只有 `STD`／`HALF`、沒有這個記號，數字不變。
   - 通知（減半、跌幅審查的理由）與持股頁、帳戶頁寫「減半之後的目標是標準比重 6.0% 的四分之一（1.50%）」；入金清單寫「補到標準比重 6.0% 的四分之一 1.5%（先買一半時被減半）」。
3. **第一次設定標準比重**：新的自選開檔時（新增、轉入、認養、自己買進；上線那天就有的不算）`OwnMeta.buildAsk = true`，持股頁的標準比重那一欄多兩個選項（預設「已經買到這個比例」），第一次存了就拿掉。一開始就是減半或先買一半的不問；減半中、審查後持有的不問。快照表單新增自選那一列不問（設計只寫持股頁）。`build.since` 是開檔日（論點檔編號的日期），所以 200 天從開檔算，不從選的那天算。
4. **確認怎麼認**：財報後的審查（觸發原因 `EARNINGS`，新財報出現時開的那一次）套用時判。有論點：3 票一致、沒有任何前提被判不成立、檔位不是減半或出清。只有預設前提：看證據包 `rule.detail.defaultCheck`（程式用 XBRL 與硬事件算的 D1～D3，和 D1～D3 的 facts 同一套算法），**不看 AI 的票**；D2、D3 資料不足算沒過關。沒有結論的審查（逾時、被退回）也算一份沒過關。財報那天剛好跌 20%、只跑跌幅審查（§3.6 的分工）的那一份不算過關也不算沒過關，靠 200 天的期限兜底。
5. **補滿的項目**（F27，`OWN_FILL`）：月報產生時看。已經列在還沒回覆（或決定了還沒填快照）的月報上就不重列（`build.listed`）。現在已經到標準比重、沒有要買的 → 直接離開先買一半，不列（目標本來就該是標準比重，不用下單）。買進前的程式檢查（§4.0）沒過 → 不列，`OwnMeta.buyBlocked` 記原因（哪一天、哪一種買進、原因；之後的加碼也用同一個欄位，35 天後不再顯示），持股頁寫 `補滿的條件過關了，但…，這次不提補滿；下個月月報再看一次。`，下一份月報再試。選項：照做（補到標準比重）、這次不做（標準比重改成那時的實際比重，不超過單檔上限 15%）；兩個選項都帶 `BUILD_END` 效果，整則選這次不做時在回覆當下套用。影子紀錄走一般的項目（規則 = 補滿的股數）。
6. **拖太久**：還沒過關，而且兩份財報都沒過、或開檔滿 200 個日曆天 → 「要看的事」`BUILD_STALE` 列一次，持股頁列到你決定為止。兩個按鈕照設計；「要補滿」的路是自己買進、填快照，持股頁就會出現下一點的一鍵改。
7. **選了先買一半但其實買足了**：自選這一檔占總資產 ≥ 標準比重的九成（整股配不到剛好）→ 持股頁那一句與「改成已經買到這個比例」（目標回到標準比重，標準比重不變）。還沒回覆的補滿項目跟著取消。
8. **新增自選（F14）**：有論點、已跌 20% 的，項目標題寫「先買標準比重的一半，開檔後第一份財報的審查過關再補滿」。

### 4.2 你定的加碼條件

和出場條件同一張表、同一種格式、同一套監測（`own_conditions`；現有的 `direction: 'UP' | 'DOWN'` 欄位）。

| 項目 | 設計 |
|---|---|
| 成立時的動作（`action` 多兩個值） | `FILL`：補到標準比重（給 `BUILD` 或減半中的股票…見下）；`RAISE`：提高到標準的 125% |
| 格式 | 和出場條件相同：財報門檻（7 個指標、門檻、連續幾季）、申報事件、網頁／法說會事件。**不收價格條件**（跌到多少就加碼是 §4.4 的範圍，有它自己的限制） |
| 誰寫 | 你在編輯論點頁寫（AI 改寫成可監測的格式，你確認，照舊）；草稿（`own_draft` 升版）可以附 0～2 條加碼條件，一鍵採用時一起生效 |
| 監測 | 照舊三種：程式比 XBRL／新申報時 3 票確認／只在審查時判 |
| 上限 | 你定的條件合計仍是 8 條（出場＋加碼） |
| 成立時 | 先過 §4.0 的程式檢查 → 進下一份月報（F28 `OWN_ADD`）：`MU：你在 2026-11-20 定的加碼條件「營業利益率連兩季高於 35%」成立 → 提高到標準的 125%，買 6 股`。預設照做；不做不用寫理由（不買沒有風險要記） |
| `FILL` 對減半中的股票 | 不適用：減半是價格底線或論點出問題造成的，加回只看 §3.4。條件照樣標成立，持股頁寫 `條件成立；這檔在減半中，加回看 200 日線` |
| `RAISE` 的限制 | 和 §4.3 共用：距上次提高滿 12 個月；提高後標準比重 × 1.25，`raisedAt` 記日期 |
| 一次性 | 和出場條件一樣，成立一次就結束；要再用就重新定 |
| AI 監測中的條件（最多 3 條） | 不變：只有「重新審查」一種動作，AI 不能自己提加碼條件 |

`condMetItem`（現在賣出才產生項目）、`COND_ACTIONS`、`notifyTier` 要擴充；甲類通知只管賣出，加碼不走甲類（不發當天通知）。

**實作時補的細節（T84，2026-11-23）**：

1. **怎麼存**：同一張 `own_conditions`，`action` 多 `FILL`／`RAISE`，`direction` 寫 `UP`（改寫、草稿、勾選時程式都改成 `UP`，不靠 AI 寫對）。不用 migration：`action` 是 0012 用 `ALTER TABLE … ADD COLUMN action TEXT` 加的、0006 建表也沒有 `CHECK`，資料庫層不擋新值（`grep -n CHECK worker/migrations` 只有三處：兩張單列表的 `id = 1`、`web_source_ratings.tier`，都和 `own_conditions` 無關）。`COND_ACTIONS` 收五個值；另有 `EXIT_ACTIONS`（出場）、`ADD_ACTIONS`（加碼）兩組。`notifyTier` 對加碼條件回 `null`（不走甲類）。
2. **編輯論點頁**：加碼條件自己一塊（「加碼條件（可以不寫）」，動作只有「提高到標準的 125%」「補到標準比重」），存檔時接在出場條件後面一起送（同一個 `exitConditions`、同一套整組取代與改寫）。上限：出場條件照舊最多 6 條，出場加加碼合計最多 8 條（網站與 API 都擋）。貼回討論的區塊只換出場條件那一塊、不動加碼條件；討論包把加碼條件另外列一段（寫明「在編輯論點頁自己改，不要寫進收尾區塊的出場條件」），免得 claude.ai 把它抄進出場條件、被當成重新審查。
3. **改寫（`own_check_v7`）**：`U` 的 label 寫「使用者要的加碼條件（…；成立時：買進（提高到標準的 125%））」；題目多一句加碼條件 `direction` 寫 `UP`、不收價格條件。改寫結果：動作照使用者寫的那一條；**加碼條件寫成價格條件的擋下**（`blocked`：持股頁那一列沒有勾選框，寫「不會監測：加碼條件不收價格條件（跌到多少就加碼是『下跌加碼』的範圍，有它自己的限制）」；確認時也不收）。持股頁的改寫對照，加碼條件那一列多一行 `成立時：買進（提高到標準的 125%）（加碼條件，進月報、預設照做）`（§4.6 的「方向填錯」）。
4. **出場與加碼不能只改動作互換**：字一樣但一個成立時賣、一個成立時買，不算同一條（`planExits` 不認成沿用，會送改寫）；確認改寫時的動作選單、持股頁「改成立時的動作」都只給同一組的動作，伺服器也擋（要互換就回編輯論點頁重寫，對照才寫得出「成立時：買進」）。AI 建議的、AI 監測中的條件不能改成加碼（§4.2 表最後一列）。
5. **草稿（`own_draft_v4`）**：輸出多 `payload.adds`（0～2 條，`action` 是 `FILL`／`RAISE`，`kind` 只有 `XBRL`、`EVENT`，格式和出場條件同一套檢查）；**寫了價格條件、或其他格式不合格，整份退回**（和草稿的其他程式檢查一樣，不給半份）。採用時接在出場條件後面一起整組取代（8 條合計），寫進條件時方向 `UP`。整組取代的意思是：採用一份沒有加碼條件的草稿，你原本的加碼條件會撤下——採用前的對照會把它列在「撤下」裡（草稿有加碼條件時那一段的標題寫「出場條件與加碼條件」）。
6. **成立時**（`notifyOwnCondition` → `queueAddCondition`，四條成立的路——程式比 XBRL、財報新聞稿、新申報三票、審查三票——都一樣）：
   - 減半中 → 條件照樣標 `MET`，不提加碼，持股頁寫 `你定的加碼條件「…」成立；這檔在減半中，加回看 200 日線`（`buyBlocked` 的 `line`）。
   - 先買一半還沒過關、動作是補到標準比重 → **當成先買一半的確認**（§4.1「兩者先到的算」）：`build.ok`（`cond: true`），下一份月報列的是補滿（F27），不另列 F28。已經過關、補滿在等月報 → 不另外列。
   - 其他 → 記進 `OwnMeta.addMonthly`，下一份月報列 F28；不發當天通知。
7. **F28（`addItem`，月報產生時）**：照當天的持股換算。不列的情況都寫持股頁（`buyBlocked`，`what` = 加碼）、**不留到下個月**（條件是一次性的；持股頁那一句寫「加碼條件只成立一次，要再用就到編輯論點頁重新定一條」）：減半中；`RAISE` 距上次提高未滿 12 個月（和 AI 的 125%、下跌加碼共用 `raisedAt`）；已經到那個比例、沒有要買的；§4.0 的程式檢查沒過（超過上限的部分砍掉，項目的 note 寫只買幾股）。同一檔同一份月報只列一項（`RAISE` 優先；其他的寫持股頁）；有 F28 `RAISE` 時同一份月報不列 AI 的 F23；F28 會讓先買一半結束的（先買一半的股票直接 `RAISE`：照做時先 `BUILD_END` 再提高——你定的條件就是確認），同一份月報不列 F27。選項：照做（`RAISE` 帶 `APPLY_TIER RAISE`，標準比重 × 1.25、記 `raisedAt`）／這次不做（不用理由）。預設照做（D10），影子紀錄的規則那條線就是照做的股數。
8. **影子紀錄**：補滿（F27）與 F28 每一次回覆都記一筆（照做了也記；原本只有和規則不同時才記），之後看得到加碼的效果。

### 4.3 提高到 125%：門檻改看基本面

現在的門檻（`raiseAllowed`）：標準狀態、沒有硬事件、**連續站上 200 日線 126 個交易日**、距上次提高滿 365 天、每條前提都成立且有申報引用。

【D6，照建議】把價格那一項換掉：

| | 現在 | 改成 |
|---|---|---|
| 價格 | 連續站上 200 日線 126 天 | **拿掉** |
| 基本面 | 這一次審查每條前提都成立、有申報引用 | **連續兩次財報後的審查**都 3 票一致、每一條可驗證的前提都判成立（正面引用來自申報或財報，照舊不能只靠網頁）。也就是連兩季被證實 |
| 程式自己核對 | 無 | 最近兩季營收年增都是正的（XBRL）；資料不夠就不算過 |
| 狀態 | 標準 | 標準（`BUILD`、`WATCH`、`HALF` 都不行） |
| 間隔 | 365 天 | 不變 |
| 其他 | — | 過 §4.0 的程式檢查 |

- 提出的方式不變：月報一項（F23），預設不做，使用者選了才買。
- 另一條路是 §4.2 你自己定的 `RAISE` 條件。兩條路共用 12 個月的間隔。
- 提高之後不會自動降回來：新的比重就是標準（現況如此，不改）。上面有 10% 的買進上限與 15% 的單檔上限擋著。

理由：連續站上均線半年等於「漲了才加碼」，和長線、看論點的方向不一致；只有預設前提的股票沒有可驗證的前提，照舊不會被提 125%。

**實作時補的細節（T83，2026-11-23）**：

1. **「連兩季被證實」怎麼記**：每一次財報後的審查套用時記一筆 `OwnMeta.earnChecks`（只留最近兩筆）：證實 = 3 票一致（`AGREED`）、每一票都判了證據包裡的每一條前提（信念不在證據包裡，所以就是「每一條可驗證的前提」）、都是成立、判成立的引用有申報或財報（`holdsHard`）。沒有結論的也記一筆「沒有證實」，所以兩筆一定是相連的兩次財報。
2. **這次財報後的審查本身算不算**：AI 要在 `verdicts` 裡看到 `RAISE` 才能選。觸發原因是財報時，證據包只要求「上一次財報後的審查證實過」，這一次有沒有證實由 `reviewDecision` 看三票（原本就要求每一條前提都成立、引用有申報或財報）；其他觸發原因（月審、論點變動…）要最近兩筆都證實。
3. **營收**：程式用證據包組好時的 XBRL 季度表算最近兩季（要相連）的營收年增，兩季都是正的才過，資料不夠不算過；結果記在 `rule.detail.revenue`，`reviewDecision` 用同一份判，不重抓。
4. **狀態**：慢規則狀態與已反映的目標都要是標準（`BUILD`、`WATCH`、`HALF` 各有原因的字）；再過 §4.0 的程式檢查（只看狀態）。月報列 F23 時再用股數過一次（上限砍掉；沒過不列、記 `buyBlocked`，持股頁寫原因）。持股頁、月報的說明不再畫「連續站上 200 日均線」的條。
5. prompt 升 `own_review_v6`（v5 留著、檔頭加「不再使用」）：125% 的說明改寫；「先買一半」等於檔位 `STANDARD`，不要為了補滿選 `STANDARD`。`run.md` 照 `prompt_version` 找檔，不用改。

### 4.4 論點還在時，下跌可以加碼

這是五項裡風險最高的一項（攤平）。限制寫死在程式裡，AI 不能放寬。【D5，照建議】

- **只在一個時點出現**：有論點的股票，跌幅審查（-20% 或 §3.3 的更深一級）的結果是「前提都沒有被判不成立」，而且更嚴：**3 票對每一條可驗證的前提都判「成立」並有正面引用**（不減半只要求「沒有被判不成立」），**而且程式核對跌幅拆解：個股自身的跌幅不超過整段的一半**（§3.2 拿掉的那個核對搬到這裡：這檔自己跌、原因不明時可以不賣，但不提加碼）。這時通知上多一個選項：
  - 在 `STD`／`WATCH`：`加碼：提高到標準的 125%，買 6 股`
  - 在 `BUILD`：`補滿到標準比重，買 12 股`
- **預設仍是不動。** 選項說明固定寫：`AI 檢查的是論點有沒有壞，不是會不會繼續跌。下跌時加碼，跌更深時虧得更多；這一次下跌只會提這一次。`
- 限制：
  1. **一次下跌只加一次**：`OwnMeta.dipAdd = { episode: 觸發日, at }`。同一次下跌（回到 `STD` 之前）更深的幾級審查不再出現這個選項，不論上次有沒有選。
  2. 過 §4.0 的程式檢查（單檔 10%、無硬事件、30 天內沒有前提被判不成立）。
  3. 和 125% 共用 12 個月的間隔（選了就記 `raisedAt`；`BUILD` 的補滿不算）。
  4. 只有預設前提的股票、`HALF` 的股票沒有這個選項。
  5. 審查的 3 票必須引用申報或財報判成立；只靠網頁證據的不出現這個選項（和「往上的檔位不能只靠網頁」一致）。
- 這一項例外地出現在**當天的通知**上（因為它附在跌幅審查的那一則）；仍然不是另外發的通知。
- 加碼之後又跌到下一級：照 §3.2 審查，結果可能是減半（賣的是加碼後的一半）。影子紀錄記得到這兩筆。

**實作時補的細節（T84，2026-11-23）**：

1. **審查面**（`drops.ts` 的 `dipCheck`，`dropDecision` 判成 `CLEAR` 時一起算，記在 `dropReview.dip`）：三票對證據包裡的每一條前提（信念不在證據包裡，所以就是「每一條可驗證的前提」）都判成立、判成立的引用有申報或財報（和財報後審查的「證實」同一個函式 `premisesConfirmed`），再加跌幅拆解的核對 `idioWithinHalf`（個股自身的跌幅不超過整段的一半；拆解算不出來算沒過）。沒過時 `why` 寫哪一項。
2. **通知那一層的限制**（`report.ts` 的 `dipOffer`，純函式；`setThesisDrop` 每次重算那一項時呼叫，結果記在 `dropReview.dipOffer`，持股頁寫原因用）：結果是 `CLEAR` 而且審查面過了；有論點；不在減半；**一次下跌一次**；`STD`／`WATCH` → 提高到 125%（`raisedAt` 未滿 12 個月不給）、`BUILD`（審查後持有期間 `build` 還在、目標還是一半）→ 補滿到標準比重（不看間隔）；已經到那個比例不給；§4.0 的程式檢查（`buyCheck` 帶 `skipKey`：這一則跌幅審查項目本身不算「還沒結案的跌幅審查」），超過上限的砍掉、砍到 0 不給。T84 之前的審查沒有 `dip` → 不給、也不寫原因。
3. **「一次下跌」怎麼認**：新欄位 `OwnMeta.watchSince`——進審查後持有（第一次比高點低 20% 觸發）那天寫，回到標準（`leaveWatch`）時拿掉。`OwnMeta.dipAdd = { episode: watchSince, level, offered, at }`：選項第一次出現在哪一級的通知上就記下（`offered`），同一級那一項重算（股數、晚回覆）照樣給，**別的級不再給**（不論上次有沒有選）；照做了 `at` 記那天（效果 `DIP_ADD`）。下一次下跌 `watchSince` 不同，可以再提（仍受 12 個月間隔限制）。
4. **選項**：`id` 是 `AI`（AI 發起的，D10 預設不做），標題 `加碼：提高到標準的 125%，買 6 股`／`補滿到標準比重，買 12 股`；效果 `DIP_ADD` 加上 `APPLY_TIER RAISE`（記 `raisedAt`）或 `BUILD_END`（離開先買一半，補滿不算提高）。預設仍是不動（`choice` = `SKIP`；你已經選了加碼、重算時選項還在就保留）；規則那條線（`ruleChoice`）照舊是減半。整則仍是「預設不下單」的通知：2 個交易日沒回覆就 `AUTO_DEFAULT` 以不動結案。選項說明固定的那一句放在 `Item.dipAdd.note`（被上限砍掉一部分時後面加括號說明）。
5. **結果回來之前你已經回覆了**（07:30～09:30 先選了不動）：沒有還沒回覆的項目可以掛選項，這一次不提（自動結案會等審查結果，所以只有你先回覆的情況）。
6. **文字**：LINE 那一行 `MU 比高點低 21.4%：論點檢查（3 票）前提都沒有被判不成立，不減半。不用下單；這次多一個下跌加碼的選項（提高到標準的 125%，買 6 股，預設不動），要的話到網站選。`；推出去之後才回來的結果補推那一行也一樣多半句。網站：選項下面的說明（含固定那一句）、事實欄「下跌加碼」；持股頁審查後持有那一句多 `；通知上有下跌加碼的選項（…，預設不動）`、`；這次下跌選了加碼（11-24）` 或 `；沒有提下跌加碼：<原因>`。
7. **影子紀錄**：照舊三條線（`thesisDropShadow`）：規則 = 減半的股數、AI = 0（審查的結論是不動）、實際 = 買進的股數，備註「下跌加碼：提高到標準的 125%」。論點檔的回應記 `DIP_ADD`。
8. 順帶改正兩處 T82 的判斷：`decidedThesisDrop`（你已經選了要賣、在等下單）原本把「不是不動」都當成要賣，選了下跌加碼的不算；跌幅審查項目的「沒選就是這個」原本標在規則那條線（減半）上，改成標在實際的預設（沒有前提不成立時是不動）。

### 4.5 候補名單

還沒持有、但想在條件到的時候買的股票。

**資料**：`acct.watch: Record<代號, WatchMeta>`（帳戶狀態；最多 5 檔【D7，照建議】），`WatchMeta = { fileId, addedAt, note, stdWeight, entryConds 的參照, lastListed }`。候補也有論點檔（同一套 `own_thesis_log`、`own_conditions`、`own_drafts`，`file_id` 進場後沿用）。

**怎麼加**：帳戶頁自選那一區下面多一塊「候補」。輸入代號、選填一句「為什麼想買」（存成 `note`，等同現有的「買進時的一句話」，不是前提）、打算放的比重（留空用推薦值：自選預算內依波動度反比，現有的算法）。

**加了之後**：

1. 系統自動開一次論點草稿（`OWN_DRAFT` 放寬成可以替候補起草；現在限持有中）。草稿多一節「進場條件」1～3 條。一鍵採用。
2. **進場條件的格式**和 §4.2 相同（財報門檻、申報事件、網頁事件），另外多收一種**你自己寫的價格條件**：`收盤低於 $X` 或 `比 52 週高點低 Y% 以上`（程式每天比）。AI 的草稿不提價格條件（AI 不談估值與目標價的規矩不變）；價格條件只能是你自己填的數字。
3. 監測：財報門檻由程式比；申報事件由新申報時的 3 票確認；網頁事件與「只在審查時判」的條件——候補**沒有定期審查**（成本），這類條件在每月月底、有新證據時用一次條件確認任務判。只有預設前提（沒採用草稿）的候補只能有價格條件。
4. 候補股票的資料：價格、EDGAR 申報清單、XBRL 照持股的方式抓；不進每日事件掃描、不開硬事件法庭、不跑新眼光。

**進場條件成立**：

- 先過程式檢查：沒有規則偵測到的硬傷（用動能進場前的那一套規則偵測：被收購方、延遲申報、財報重編、會計師辭任——命中就不提，持股頁寫原因）；價格條件要在月報訊號日**仍然成立**。
- 下一份月報列一項（F29 `WATCH_ENTRY`）：`候補 AMD：你在 2026-11-20 定的進場條件「比 52 週高點低 25% 以上」成立（現在 -27%）→ 先買一半：買 9 股（標準比重 4%，錢從核心拿）`。預設照做。旁邊顯示草稿的「今天沒持股的話會不會買」那一題的答案與日期（只是資訊）。
- 自選桶合計已經超過預算（20%）時，項目多一句 `自選目前占 24%（預算 20%）`，不擋。
- 照做 → 使用者買進、在快照的自選桶填股數 → 候補轉成持股：論點檔沿用、狀態 `BUILD`、進場條件標成立。不做 → 條件已經成立過（一次性）；候補留著，要再等就重新定條件。
- 同一檔的進場項目每 90 天最多列一次。

**其他**：

- 使用者沒等條件、自己先買了（快照出現候補的代號）→ 直接轉成持股，論點檔沿用，進場條件標「撤下」。持股頁照 §4.1 問是買足了還是先買一半。
- 候補滿 12 個月沒有進場 → 「要看的事」一行，每年一次：`AMD 在候補名單一年了，進場條件還沒成立。要留著、改條件，還是移除？`
- 移除候補：論點檔結案（照現有的結案）。
- **出清的股票**不會自動進候補。使用者可以自己加回候補；因為前提不成立而出清的，30 天內加進候補不自動草擬（現有的防線：前提剛被判不成立時不自動草擬，防找理由買回）。新的論點檔照舊帶「上一次持有時的論點」。
- 候補的股票同時被動能買進：互不影響；進場時受跨桶上限限制。

*資料與論點檔（甲）*

1. **候補不是「0 股的自選」**：`acct.own` 的鍵會被價格必要清單（`requiredTickers`）、每日掃描與硬事件法庭（`scanTargets`）、慢規則（`dailyCheck`）、推薦比重的分母當成自選。所以照上面另立 `Account.watch?: Record<代號, WatchMeta>`（讀的時候 `?? {}`），「不進每日掃描、不開硬事件法庭、不跑新眼光」因此不用另外擋，但要有測試鎖住 `scanTargets`、`requiredTickers` 不含候補。
2. **`WatchMeta` 要放得下論點檔**（一鍵採用會寫論點、前提）：論點檔的欄位用和 `OwnMeta` 一樣的名字——`fileId, premises, thesis, premiseSeq, webSources, buyNote, attnShown`；候補自己的——`addedAt, stdWeight: number | null（留空 = 列 F29 時用推薦值）, lastListed: string | null, entry?（成立、等月報的進場條件，見 16）, blocked?: { date, text }`。上面寫的 `note` 就存成 `buyNote: { text, at }`（討論包、草稿的 B1 不用改）。新建時 `premises = SYSTEM_DEFAULT_PREMISES`（種類是「只有預設」）。
3. **共用入口 `fileMeta(acct, ticker)`**（`engine/account.ts`）：回 `{ meta, held } | null`，先找 `own` 再找 `watch`。論點檔的讀寫（`app/thesis.ts`、`ownDraft.ts`、`ownCheckAi.ts`、`ownConds.ts`、`ownAi.ts` 的條件部分、`ai/pack.ts` 的前提、討論包、`webEvidence`、`ledgerStore` 的開檔結案比對）改走它；只對持股有意義的（慢規則、審查、配置）不改。
4. **編號**：照舊 `newFileId(代號, 加入候補的訊號日, 上一份結案的編號)`，進場後沿用。程式裡把編號的日期當「開始持有」的地方（`openedOn`、`openedOf`、`fileDate`）改看新欄位 `OwnMeta.heldSince`（進場那份快照的訊號日；沒有就用編號的日期，舊資料不變）；`build.since` 也用它，所以候補放 8 個月才進場不會一進場就「200 天沒補滿」。`OwnMeta.origin` 加 `'WATCH'`。畫面寫 `11/20 加入候補 → 2/3 進場`。論點檔紀錄加一種 `ENTERED`（`{ via: 'F29' | 'SELF', shares, state }`）。
5. **開檔與結案紀錄**：`ownFilesOf`／`fileChanges` 把 `watch` 的編號一起算；同一個編號從 `watch` 搬到 `own` 不寫 OPEN／CLOSE。加候補寫 OPEN（`origin: 'WATCH'`）。
6. **移除候補**：新函式 `removeWatch`，結案原因加 `'WATCH_REMOVED'`（`CLOSE_TEXT`、`CLOSE_VERB` 跟著加）。`ownClosed[代號]` 每檔只有一筆、同時是「上一次持有時的論點」的來源，候補移除照寫但多帶 `held?`：原本那一筆若是持有的結案就搬進去，`prevFileOf` 遇到 `WATCH_REMOVED` 改用 `held`，免得候補的論點被顯示成「上一次持有」。還沒回覆的 F29 取消；條件不用動。
7. **30 天的防線要跨論點檔**：現有的「前提剛被判不成立不自動草擬」看的是同一份論點檔，新開的候補看不到舊的。`removeOwnPick` 把 `OwnMeta.brokenAt` 抄進 `ownClosed[代號].brokenAt`；候補的自動草擬與 F29 的程式檢查都看它（30 個日曆天）。手動按鈕照舊可以按。
8. **5 檔上限**：只算 `acct.watch` 的鍵；引擎的 `addWatch` 與 API 各擋一次（422）。已在自選的代號不能加候補，候補中的代號不能用「新增自選」（都 422，訊息指到對的地方）。
9. **價格放「追蹤」不放「必要」**：照「持股的方式」抓，但不能讓候補一檔打錯或下市就整個帳戶當天沒訊號——候補加進每日抓取的 `track` 與各處 `loadSeries`，不進 `requiredTickers`。沒有價格的候補不列 F29，頁面寫「價格抓不到」。加候補當下照「新增自選」的做法當場抓、檢查（不是核心標的、有收盤、歷史 ≥ 200 天）。
10. **網站**：`AccountView.watch: WatchRow[]`（代號、加入日、那一句話、比重或推薦值、進場條件與現在的狀態、草稿狀態、沒提的原因、`lastListed`），跟著 `state` 回。寫入端點：`ops/watch-add`（`{ ticker, note?, stdWeight?, dry? }`）、`ops/watch-update`、`ops/watch-remove`、`ops/watch-price`（見 12）。詳細頁沿用 `#/holding/<代號>`（`holdingDetail` 多回 `watch`），編輯論點頁、草稿那一塊照用；`draftStates` 含候補。

*進場條件、F29、候補 → 持股（乙）*

11. **`ENTRY` 怎麼存**：`CondAction` 加 `'ENTRY'`（另立 `ENTRY_ACTIONS`；`sameActionKind` 分出場／加碼／進場三組；`notifyTier` 對它回 null，不發甲類）。**進場條件另算、不占你定的 8 條**；上限是草稿或你寫的非價格條件 3 條、價格條件 2 條。
12. **價格條件**（你自己填的數字）：現在 `kind: 'PRICE'` 的意思是「只記錄、不監測」，這裡另開例外——只有「`action: 'ENTRY'`＋`check.type` 是 `price_close_below`（`level`）或 `price_drawdown_below`（`pct`）」才監測（`ConfirmMode` 加 `'PRICE'`，寫入就是 `ACTIVE`）；其他 `PRICE` 照舊只記錄。不經 AI 改寫：候補那一塊用結構化欄位（種類＋數字），程式組文字，`ops/watch-price` 整組取代價格那一組。`check` 帶 `asOf`，比對時用 `splits` 表在 `asOf` 之後的拆股換算 `level`（價格序列是拆股後的，不然 1 拆 2 會誤觸發）。
13. **價格條件什麼時候算成立**：「程式每天比」只用來顯示（`現在 -27%，條件成立中`），不改狀態；真正決定列不列的是**月報訊號日的收盤**（`monthEndInputs` 裡新的 `prepareWatchEntries`）。列進 F29 那一刻才標成立（一次性）；月中成立過、訊號日不成立的不算用掉。結果放 `MonthlyContext.watchEntries`，月報暫停後重算沿用同一份。
14. **F29 的硬傷檢查**：動能那一套規則偵測裡，被收購方、延遲申報是規則直接否決，但重編（8-K 4.02）、會計師辭任在動能是「開法庭」，候補沒有法庭。所以新純函式 `watchHardHits`：這四種只要是來自申報（新聞標題不算）、在 `HIT_WINDOW` 內就不提，持股頁寫原因；單日跳漲、EPS 背離、增資不擋。要連網，在 `prepareWatchEntries` 做。申報清單抓不到 → 這個月不提、下個月再看（買不急）。
15. **F29 的程式檢查與股數**：新 `watchBuyFacts` 給 `buyAllowed`——候補沒有慢規則狀態、審查、硬事件標記，有意義的只有「30 天內前提被判不成立」（看 7 的 `ownClosed.brokenAt`）、跨桶 10%（砍到 0 不提）、沒有要買的股數。另外加一項（比照 §4.0，往保守的方向）：**這檔你定的財報類出場條件現在已經成立 → 不提**，寫原因。股數 `floor(stdWeight × 0.5 × 總資產 ÷ 價格)`，`stdWeight` 留空時列的當下用推薦值並寫在項目上；錢從核心照 80：20（`composeNotif` 已經會做）。自選比例設成 0% 時不列。90 天：`lastListed` 記列的那份月報的訊號日，選不做、照做沒買都算列過。項目 `f: 'F29'`、`kind: 'WATCH_ENTRY'`，選項 `DO`（預設）／`SKIP`，影子紀錄每次都記。要特別測：F29 的行是 `bucket: 'own'` 但 `rule.own` 還沒有這檔，是現在沒有的組合。
16. **非價格的進場條件成立之後**：`notifyOwnCondition` 開頭對 `ENTRY` 分流成記進 `watch[t].entry`，等月報。被 90 天、硬傷、程式檢查擋下時**留到下個月再看**（進場條件是唯一的入口，丟掉就卡住），頁面寫原因；成立超過 100 天還沒列 → 丟掉，寫「要再用就重新定」。同一份月報同一檔只列一項，其他成立的在說明裡帶過、一起算用掉。
17. **候補 → 持股**：新函式 `promoteWatch(acct, view, ticker, via)`：用 `newOwnMeta` 建骨架、蓋上候補的論點檔欄位（`fileId` 沿用）、`origin: 'WATCH'`、`heldSince`、`rule.own[t] = { applied, stdWeight: watch.stdWeight ?? 推薦值 }`，刪掉 `acct.watch[t]`，寫 `ENTERED`。
    - **F29 照做**：`DO` 帶新效果 `WATCH_ENTER`，**只有快照的自選桶股數 > 0 才轉**；沒買的還是候補，照現有的「補做差額或就這樣」。轉過來的是 `BUILD`（`build = { since: heldSince, confirmBy: 'EARNINGS', misses: 0 }`），不問。
    - **自己先買**（清單外買進、舊式分類、轉入自選、認養都算）：在 `ensureOwnMeta` 開頭攔，有候補就 `promoteWatch(…, 'SELF')`，不重複開檔；狀態 `STD` 加 `buildAsk`，持股頁對 `origin === 'WATCH'` **預選「先買一半」**（§4.1 表單上寫的「從候補名單進場的預設」）；還沒回覆的 F29 取消。F29 還沒回覆、你自己買了：對帳會當成照清單做了，走 F29 那條路，可以接受。
    - **進場時已經比高點低 20% 以上**（價格條件「比高點低 25%」就是這種）：只有預設前提的照 §4.1 既有規則開在 `HALF`（目標一樣是標準的一半，補回看 200 日線），F29 標題寫明。**有論點的照 §3 字面：進場後的每日流程照常觸發 -20% 那一級（或已經到的更深一級）的跌幅審查**——那是「這檔低於高點 20%、該檢查論點」的訊號，D2、D3 不因為是剛買的而例外；結果是「前提都沒有被判不成立」而且過 §4.4 時，通知上照 §4.4 給 `BUILD` 的「補滿」選項（預設不動）。主持者考慮過「進場當下那一級不審」，那會改到 D2、D3 的字面，沒有採用。
    - **進場條件的狀態**：條件在資料庫、不跟帳戶版本走，快照當下不改；監測對「代號已在 `acct.own`」的 `ENTRY` 一律略過，下一次每日流程（`syncWatchConds`）補寫：列在 F29 上的那一條標成立，其他撤下（原因「已進場」或「你自己先買了」）。這樣復原快照時帳戶和條件不會不一致。

*草稿與非價格的進場條件（丙）*

18. **草稿放寬**：`startOwnDraft`、`requestOwnDraft` 改走 `fileMeta`；`startAutoDrafts` 加一段跑 `acct.watch`（加入 7 天內、沒論點、沒草稿、試不到 2 次、7 的 30 天防線），受 `DRAFT_AUTO_DAILY` 限制（一次加 5 檔會分幾天開）；T72 的七種觸發對候補全部不開（多半要審查或持有；「只有預設前提」由加入時那一次負責，「論點滿一年」由 20 涵蓋）。時機是每日第一次流程，頁面寫清楚。
19. **草稿的證據包與輸出**：候補版的數字——R1「還沒持有（候補，M/D 加入）」、R2「打算放的比重」、R4「自選合計與預算」，沒有 R3；B1 用 `buyNote`；上一份論點檔照放。題目加候補的說法，輸出多 `payload.entries` 1～3 條（`action: 'ENTRY'`、`kind` 只有 `XBRL`、`EVENT`，格式檢查用 `conditionFormatIssue`，寫了價格條件整份退回）。持有中的草稿不收 `entries`；候補的草稿照樣可以有出場與加碼條件（進場後才生效，見 21）。`own_draft_v4` 還沒部署，直接改、不升版。F29 旁邊顯示的「今天沒持股的話會不會買」就是草稿的 `would_buy_today`，寫明是反方的答案與草稿日期。
20. **一鍵採用**：`draftAdoptPlan` 把 `entries` 接上（`direction: 'UP'`、`origin: 'AI_DRAFT_ACCEPTED'`），整組取代非價格的進場條件；**你填的價格條件不在整組取代的範圍**（AI 草稿永遠沒有價格條件）。你自己寫的非價格進場條件：編輯論點頁對候補多一塊「進場條件」，走改寫（`own_check_v7` 還沒部署，直接改）；「只有預設前提的候補只能有價格條件」在 API 擋。
21. **候補期間的出場與加碼條件休眠**：成立的判斷對候補只看 `ENTRY`（`ownXbrlConditions`、F25），不然一次性的條件會在沒有持股時被用掉；進場後的下一次每日流程補比一次財報類條件。
22. **資料抓取**：EDGAR 申報清單的代號 = 掃描目標 ∪ 候補（去重，`edgar:<代號>` 的已看標記共用）；`classifyFresh`、`applyRuleEvents`、`startEventRuns` 照舊只吃掃描目標。XBRL（`ownFacts`）加上有財報類進場條件的候補；採用草稿當下用草稿那份季度表比一次，已成立就直接標成立。明確不加：財報新聞稿當天確認、個股大跌、提前審查、定期審查、部位大小與集中度、漲太多的提示、產業 ETF。
23. **非價格進場條件的確認**：確認來源有申報的，照持有中的做法在新申報出現時開 F25（新函式 `startWatchRuns`，`aiStep` 在 `startOwnRuns` 後呼叫）。只有法說會、新聞、網頁來源的（設計上面第 3 點「月底、有新證據時用一次條件確認任務判」）：現有的 `OWN_CONDITION`（`own_condition_v1`）題目寫死只讀申報原文、沒有取文件，判不了——**升 `own_condition_v2`**：文件 = 上次確認之後的 8-K、10-Q、10-K，加 `buildDocMenu` 的目錄與取文件，引用規則沿用 `condCite`，成立依據記 `WEB_VOTE`。月底檢查點那天開，「有新證據」= 這份論點檔上一次條件確認之後有新的 8-K／10-Q／10-K，或條件指名網頁來源而且距上次滿 25 天（`WEB_DUE_DAYS`）；都沒有就不開。`conditionPack` 對 `ENTRY` 寫「進場條件（成立時：候補進場，先買一半）」。
24. **一年沒進場**：`Attention` 加 `src: 'watch'` 與鍵 `WATCH_STALE`（`every: 12`，`since = addedAt + 365 天`，記在 `watch[t].attnShown`，連到帳戶頁）。條件都用掉的寫 `…一年了，目前沒有進場條件。要重新定，還是移除？`。候補的其他「要看的事」只留「草稿好了」。
25. **討論包與 `/thesis`**：`/admin/own/list` 帶候補並標記，討論包開場加一種「還沒持有，放在候補」；貼回的區塊對候補不收進場條件（進場條件在網站改）。
26. 不用 migration：`own_conditions.action` 沒有 CHECK、`kind` 本來就有 `PRICE`、`own_drafts.file_id` 可空；`watch` 在帳戶狀態的 JSON 裡。

*分段*：甲＝1～10（候補這個物件、論點檔共用入口、網站那一塊，不碰 AI、不碰月報）；乙＝11～17（價格條件、F29、候補轉持股，碰帳本，只靠價格條件就能把整條路走完）；丙＝18～25（草稿、非價格的進場條件、月底確認、一年的提醒、討論包）。依序做，每段驗收過才做下一段。

## 10. 不做的與理由

| 不做 | 理由 |
|---|---|
| 自選、動能自己留 SGOV | T77：券商畫面分不出是誰的，多一個要管期限的現金部位 |
| 月中補動能的空格 | 現有流程沒有這條路；空格最長一個月，錢在核心八成是 VOO |
| 每天檢查核心比例 | B-11：報酬一樣、下單日多 |
| 動能的文獻開關、200 日線、12-1 排名 | T74、T76 |
| 候補股票的定期審查、每日事件掃描 | 成本；候補沒有部位，進場前有規則偵測擋硬傷 |
| AI 提價格型的進場或加碼條件 | AI 不談估值與目標價的規矩不變 |
| 補滿、加碼、進場用當天通知 | 買不急；月報一次處理 |
| 加碼超過 125%、連續加碼 | 部位只有三個大小；12 個月間隔與單檔 10% 擋著 |
| 審查沒找到問題之後自動加碼 | 加碼永遠要使用者選 |
| 為這次改動做新的回測 | 自選的改動回測不出來，使用者已接受（計畫第 4 點）；核心與動能的數字在 B-11～B-14 |
