### 1.2 論點檔：一個組出來的檢視

每一檔自選股一份論點檔。它不是一張新表，是一個函式從五個地方組出來的（「已經決定的方向」第 3 點）：

```
thesisFile(db, acct, ticker) →
  帳戶狀態  acct.own[代號]            現行的論點、前提、靜默期、上限用的日期
  own_conditions                     條件
  sec_events                         事件
  ai_runs                            歷次 L2 的執行與結論
  own_thesis_log（新表）              論點的每一版、失效通知、使用者的回應、開檔與結案
```

- 放在 `worker/src/app/thesis.ts`（讀 D1，所以不在引擎裡；引擎仍是純函式）。L2 各功能的證據包（F24、F7、F25、自選股的 F19）、討論包、持股頁都從這個函式取資料（計畫 T25）。
- **現行的論點與前提留在帳戶狀態**：引擎與證據包本來就從 `acct.own[代號].premises` 讀；而且復原快照、把股數改成 0 又復原時，論點要跟著帳戶一起回來（設計 §10 第 39 點）。
- **歷史放 `own_thesis_log`**（只增加）。

**論點檔的編號**（`fileId`）＝`<代號>@<開檔的訊號日>`，例如 `MU@2026-11-15`，存在 `acct.own[代號].fileId`（`newOwnMeta` 建立）。條件與 log 都帶 `file_id`。

- **結案**：這檔從 `acct.own` 消失（移出自選、照建議出清、股數改 0）就是結案，不用另外改條件的狀態：所有讀條件的地方都只讀「`file_id` 等於這檔現在的 `fileId`」的列，所以舊條件自然不再被監測（修 N8）。再加回是新的 `fileId`，舊的那一份仍可在網站看。復原快照時 `acct.own[代號]` 連同原本的 `fileId` 一起回來，條件也就接回來。
- 結案時 log 寫一筆 `CLOSE`（在存帳戶的地方比較存檔前後的自選名單；`ledgerStore.ts` `saveAccount`）。
- **舊資料**：部署後第一次每日流程，沒有 `fileId` 的自選補上 `<代號>@<那天的訊號日>`，並把 `own_conditions` 裡同代號、`file_id` 是空的、狀態不是 `REPLACED` 的列補上同一個編號。

**論點檔的種類**（程式判斷，不存）：前提裡至少一條 `origin` 不是 `SYSTEM_DEFAULT` → 「有論點」；否則「只有預設」。

### 1.5 條件

#### 欄位（`own_conditions`，migration 加欄位）

| 欄位 | 說明 |
|---|---|
| 原有：`ticker`、`run_id`、`cond_id`、`direction`、`kind`（`XBRL`／`EVENT`／`PRICE`）、`text`、`check_json`、`tier_if_met`、`status`、`created_at`、`met_at`、`note`、`origin` | `origin`：條件的文字是誰寫的。`USER` = 你寫的（經 AI 改寫格式）；`AI` = 審查建議的。`tier_if_met` 對 AI 建議的條件是「AI 建議成立時做什麼」，只當勾選時的預設值 |
| 新：`file_id` | 屬於哪一份論點檔 |
| 新：`accepted_at` | 你勾選的時間。**有值就是「你定的條件」**，不論文字是誰寫的 |
| 新：`action` | 成立時做什麼：`EXIT`（出清）／`HALF`（減半）／`REVIEW`（重新審查）。勾選時定，之後可改 |
| 新：`premise_id` | 對應哪一條前提（可以是空的） |
| 新：`supersedes` | AI 建議「用這條取代那一條」時，被取代的列編號 |
| 新：`met_basis` | 成立是怎麼確認的：`XBRL`（程式比對 10-Q／10-K）／`PRESS`（財報新聞稿擷取，§1.11）／`FILING_VOTE`（申報原文三票）／`REVIEW_VOTE`（審查三票） |
| 新：`verified_at` | `PRESS` 成立的條件，10-Q／10-K 出來後核對的時間 |

「誰定的、哪一天」＝`origin` ＋ `accepted_at`；顯示成「你寫的，11/20 定」或「AI 建議，你在 11/20 勾選」。

#### 怎麼確認（由條件本身推出來，不另存；函式 `confirmMode`）

| 條件 | 確認方式 | 顯示 |
|---|---|---|
| `kind = XBRL` | 程式比對財報數字（新 10-Q／10-K；財報新聞稿當天見 §1.11） | 新財報出來時比對 |
| `kind = EVENT`，`confirm_by` 裡有申報類型（`8-K`、`10-Q`、`10-K`、`SEC`） | 新申報出現 → 條件確認（F25）三票讀原文 | 新申報出來時由 AI 確認 |
| `kind = EVENT`，`confirm_by` 只有 `earnings_call`、`major_news` | 只在審查時由三票判斷（P4） | 只在定期審查時檢查 |
| `kind = PRICE` 或沒通過格式檢查 | 不確認 | 只記錄 |

#### 狀態

| `status` | 意思 | 會不會自己發通知 |
|---|---|---|
| `PROPOSED` | 建議中：審查建議、你還沒勾選。也就是**觀察項** | 不會（見下） |
| `ACTIVE` | 監測中（你定的；確認方式是前兩種） | 成立時發甲類通知 |
| `REVIEW_ONLY` | 只在審查時檢查（你定的；確認方式是第三種） | 審查三票確認成立時發甲類通知 |
| `MANUAL` | 只記錄（價格條件、沒通過檢查的） | 不會 |
| `MET` | 已成立。一次性，不會再觸發；要再監測就重新定一條 | — |
| `RETIRED` | 你撤下，或被你勾選的新條件取代 | — |
| `EXPIRED` | 建議中的過期了 | — |
| `REPLACED` | 舊資料：改版前被整組替換的 | — |

#### 從「建議」到「監測中」

1. **審查不再整組替換條件。** 每次審查最多提 3 條「建議新增」（`payload.proposed_conditions`，§1.6），可以註明想取代哪一條（`supersedes`）。只有三票一致的審查（含一致選「不動」）才寫入，取自和結論同檔位的第一張合格票；票數不一致、資料缺漏、不合格、逾時的審查不動條件（修 N4、P5）。
2. 寫入時狀態是 `PROPOSED`。這次審查有寫入至少一條時，這檔原本還在 `PROPOSED` 的標成 `EXPIRED`（prompt 請 AI 把還適用的觀察項原樣再提，算在 3 條內）。這次一條都沒提時，舊的留著。
3. **你勾選**（持股頁）：選成立時做什麼（出清／減半／重新審查；預設帶 AI 建議的檔位）→ 寫 `accepted_at`、`action`，狀態依確認方式變成 `ACTIVE`／`REVIEW_ONLY`／`MANUAL`。有 `supersedes` 的，被取代的那條標 `RETIRED`。從此是你定的條件，之後的審查換不掉。log 寫 `CONDITION`。
4. **沒勾的是觀察項，自己不會發通知**（使用者 2026-11-15 決定；比「已經決定的方向」第 5 點的字面多一步，理由：沒表決的條件不能直接叫人賣，但整個丟掉會讓沒寫論點的股票失去條件監測）：
   - 財報類的觀察項：下一次審查組證據包時，程式用當時的財報數字算好「成立／不成立／資料還沒更新」，放進證據包（`facts` 的 W 開頭）。
   - 事件類的觀察項：交給每日掃描當觀察清單；標到之後怎麼提前開審查、頻率上限多少，在第 2 章定。
   - 觀察項成立與否只是給審查的輸入；要不要通知仍看 §1.9 的門檻（前提不成立）。
5. **上限**：一檔的 `ACTIVE`＋`REVIEW_ONLY` 最多 8 條；滿了要先撤下一條才能再勾。`PROPOSED` 最多 3 條（一次審查的量）。
6. 審查寫入新建議的那個月，月報的狀態文字加一行「MU 有 2 條 AI 建議的條件等你看（持股頁）」，不另發通知。

你自己寫的出場條件走 §1.8（寫 → AI 改寫格式 → 勾選），勾選時直接寫入一列 `origin = USER`、有 `accepted_at`。

| 上次有結論的審查之後的 8-K 原文 | 最多 5 份；順序：① 最新的 Item 2.02 ② 規則或每日掃描有標記的（新到舊）③ 其餘（新到舊）。沒有上一次審查時取最近 120 天。每份照 `fetchFilingDoc` 的長度上限，`source_id` = `edgar:<申報編號>` |
| 系統預設前提的程式結果（只有預設的股票） | `facts`：`D1`～`D3`（§1.12） |

**輸出**（`payload`）：

- `condition_checks`：對每一條 `C`、`W` 寫 `{ "id": "C1", "status": "MET" | "NOT_MET", "evidence_ids": [...] }`（取代 `previous_conditions`）。
- `proposed_conditions`：最多 3 條，格式同現在的 `conditions`，多兩個可選欄位 `premise_id`、`supersedes`（寫 `C2` 或 `W1`）。現有的條件已經涵蓋的事不要再提。
- 其餘（`premise_checks`、`verdict`／`tier`、`report`）照舊。

**程式怎麼用結論**（`reviewDecision` 改寫）：

1. **不成立的前提**＝三票的 `premise_checks` 裡，都判 `BROKEN`、而且每一票都至少有一條通過檢查、來源是申報原文或財報表（`documents` 的 `kind` 是 `filing` 或 `xbrl`）的引用——這樣的前提取交集；有多條時取編號最小的那條當「主要的」。交集是空的 → 沒有不成立的前提（修 N5；只有新聞標題或價格當證據的不算）。
2. **你定的條件由審查確認成立**：`REVIEW_ONLY` 與確認方式是申報三票的 `ACTIVE` 條件，三票的 `condition_checks` 都寫 `MET`、各有通過檢查的申報或財報引用 → 標 `MET`（`met_basis = REVIEW_VOTE`），發甲類通知（§1.10）。財報類的條件以程式比對為準，審查的看法只記錄。
3. **審查的建議**（乙類）要不要給使用者、什麼時候給：§1.9。
4. `RAISE`（提高到 125%）的條件不變，仍只進月報。

### 1.8 貼回與編輯

持股頁的「編輯論點」頁（取代現在的「加前提」文字框）。同一頁可以貼上討論的結果，也可以直接手寫。

**解析**（純函式 `parseThesisBlock(text, ticker)`，`worker/src/ai/discussion.ts`）：

- 先去掉 markdown 的程式碼圍欄。找 `===STOCKBOT 論點 v1 <代號>===` 到 `===END===`；代號要和這一頁相同，不同就擋下並說明。
- 區塊內照行首的標籤切：`論點：`、`前提：`、`出場條件：`、`這次的結論：`、`理由：`（全形或半形冒號都收）。
- 前提、出場條件：行首是 `數字` 加 `.`、`、` 或 `)` 的算一條。出場條件用最後一個 `→`（或 `->`）切成條件與動作；動作只收「出清」「減半」「重新審查」，其他字或沒寫 → 當成「重新審查」並在預覽標出來。
- 上限：論點 600 字、前提 5 條各 200 字、出場條件 6 條各 300 字；超過的截掉並在預覽標出來。
- 找不到標記：整段放進論點欄，提示「沒找到固定格式，請自己分到三欄」。

**預覽**：左邊現行的、右邊新的，三欄（論點、前提、出場條件）都可以手改。

- 前提的對應：新的和現行的文字相同（去掉空白與標點後比）→ 沿用原本的 `id`；其他是新的（發新的 `id`）；現行有、新的沒有 → 撤下。預覽列出「會撤下：P2 …」。新前提的 `origin` 是 `USER`。原本只有系統預設前提時，存了第一條你的前提就拿掉預設（照舊）。
- 從乙類通知的「拿去討論」回來時（網址帶通知編號，或這檔有還沒回覆的乙類通知），預覽有一個勾選「這是對通知 #N 的回應：修正論點，部位不動」，預設勾著（§1.10）。
- 「這次的結論」只顯示，不會自動做任何事。結論是減半或出清、而且有還沒回覆的乙類通知時，提示「回到通知 #N 按『照 AI』」。

**確認**（`POST /api/ops/own-thesis`：`{ ticker, thesis, premises: [{ id?, text }], exitConditions: [{ text, action }], source, replyTo? }`）：

1. 論點與前提立刻存進帳戶狀態（`version` 加 1），log 寫 `THESIS`（含出場條件的原文 `exitLines`，免得改寫失敗時不見）。
2. 出場條件送 AI 改寫格式（沿用 `OWN_CHECK` 的改寫模式，一票）。prompt 升成 `own_check_v2`：題目改成對已持有的股票也成立；證據包帶現行的論點、前提與既有的條件（P7）；每條帶使用者選的動作。
3. 送出失敗或 AI 層沒設定：頁面明白顯示「出場條件還沒送去改寫」與「重送」按鈕，不能沒有提示（N9）。
4. 改寫回來後在持股頁勾選才監測。**持股頁列出這檔最近 30 天所有改寫結果裡還沒勾的條件**，不是只看最近一次健檢（N9）。勾選時寫入 `origin = USER`、`accepted_at`、`action`。
5. 出場條件不再同時存成前提。

**其他寫入前提的入口**（照舊，不送改寫）：快照新增自選時寫的「為什麼買」、轉入自選或認養時寫的一句理由，存成一條 `USER` 前提；論點本文留空，持股頁顯示「還沒有論點本文」與「複製討論包」。

貼回與手寫的文字進證據包時一律是資料，不是指令（`run.md` 第 4 步已經這樣寫）。

### 1.9 審查的建議什麼時候給使用者

審查有結論之後，照下面的順序判斷（修 P2、N5、N6）。「建議」只指往下的檔位（出清、減半）；回到標準與提高到 125% 一律只進月報，條件照舊。

**先看有沒有資格**（沒有就只放網站）：三票同一個檔位、和目前狀態不同、資料沒有缺漏、有一條「不成立的前提」（§1.6 第 1 點的定義）、而且那條前提不在靜默期內（§1.10）。

**有資格之後，當天通知還是等月報**：

| 情況 | 怎麼給 |
|---|---|
| 觸發原因是月審（月報前一天） | 進隔天的月報（照舊） |
| 觸發原因是財報後、提前審查、或你定的「重新審查」條件，而且這檔最近 30 個日曆天內沒有發過 AI 發起的當天通知（`aiNotifiedAt`） | **當天通知**（乙類，§1.10）；`aiNotifiedAt` 記今天 |
| 同上，但 30 天內已經發過 | 記著（`aiTier.suggest = true`），進下一份月報 |
| 這檔有還沒回覆的慢規則通知 | 不另發，更新那則通知上「照 AI」的選項（現有的 `refreshOwnAiChoice`） |
| 這檔有還沒回覆的乙類通知 | 不另發；檔位變了就更新那一則 |

- 月中記著等月報的建議，只有被「之後一次有三票結論的審查」取代；月底那次沒有一致結論時留著進月報。已經用當天通知給過的不再進月報。
- 時間：財報多半在美股收盤後公布，當天的每日流程（UTC 23:30）開審查，第二次排程（UTC 01:30，台灣早上 9:30）套用並推 LINE，當晚開盤前使用者來得及決定。

**當天通知的頻率上限**（使用者 2026-11-15 決定，取代「F25 每檔每月最多 1 則」）：

| 通知 | 上限 |
|---|---|
| 你定的條件成立（甲類） | 不設上限（每條條件只成立一次） |
| AI 發起的當天通知（乙類） | 每檔 30 個日曆天最多 1 則，超過的進月報 |
| 硬事件（F19）、慢規則變動 ≥ 總資產 5% | 照舊，不算在上面 |

### 1.10 兩種失效通知

#### 甲類：你定的條件成立

「已經決定的方向」第 6 點：照當時的決定執行，不重新討論。

- 什麼時候發：`ACTIVE` 或 `REVIEW_ONLY` 的條件標成 `MET`，而且 `action` 是出清或減半、換算出來要賣的股數大於 0。當天通知（由月審確認成立的，進隔天的月報，項目相同）。
- `action` 是「重新審查」：不發通知，當天開一次審查（觸發原因 `CONDITION`；不受第 2 章 L1 提前審查的頻率上限限制）。
- 換算出來不用賣（例如動作是減半、但已經在減半狀態）：不發通知（設計 §2.5：不用操作的事不發通知）；條件照樣標成立，下一份月報的狀態文字加一行「MU：你定的條件『…』成立；目前已經是減半，不用再賣」。
- log 寫 `BREAK_NOTICE`（`type: 'A'`）。

通知（`kind: URGENT`）與項目（`f: 'F25'`，新的 `ItemKind`：`OWN_COND`）：

| 欄位 | 文字 |
|---|---|
| 通知標題 | `MU：你定的出場條件成立` |
| 項目標題 | `MU：你在 2026-11-20 定的條件「毛利率低於 70%」成立` |
| 理由（`why`），依 `met_basis` | `XBRL`：`最新一季毛利率 68.4%（10-Q 2027-01-08）`；`PRESS`：`最新一季毛利率 68.4%（依財報新聞稿 8-K 2027-01-06；10-Q 出來後再核對）`；`FILING_VOTE`：`8-K 2027-01-06 的原文，3 票確認（引用在網站）`；`REVIEW_VOTE`：`2027-01-07 的審查 3 票確認（引用在網站）` |
| 選項一（**預設**） | `照當時的決定：出清，賣 50 股`（`id: 'DO'`，帶 `APPLY_TIER`） |
| 選項二 | `這次不做`（`id: 'SKIP'`）：**要寫一句理由**（1～200 字），沒寫不能送出 |
| LINE | `【當天】MU：你定的出場條件成立` ／ `你在 11/20 定的「毛利率低於 70%」→ 出清` ／ 清單與連結照現有格式 |

- 預設選「照當時的決定」（使用者 2026-11-15 決定；現在 AI 類的項目預設是「不做」）。仍然要使用者按、自己下單。
- 影子紀錄：「照規則」那條線記當時的決定（`ruleChoice: 'DO'`），沒有 AI 那條線。
- 回應寫 log 的 `RESPONSE`（`FOLLOW` 或 `SKIPPED`＋理由）。一次性：選了不做，這條條件也不會再觸發。
- 不附「拿去討論」。

#### 乙類：AI 判斷前提不成立，沒有對應的條件

- 什麼時候發：§1.9。log 寫 `BREAK_NOTICE`（`type: 'B'`）。

通知（`kind: URGENT`；月報裡是同一種項目）與項目（`f: 'F24'`，`kind: 'AI_ONLY'`）：

| 欄位 | 文字 |
|---|---|
| 通知標題 | `MU：AI 審查認為你的前提不成立`（只有預設前提的股票：`MU：AI 審查認為預設前提不成立`） |
| 項目標題 | `MU：前提「HBM 長約有價格保護」3 票都判不成立` |
| AI 那一行（`aiLine`） | `AI 建議減半，賣 25 股` |
| 理由（`why`） | `依據：8-K 2027-01-06（引用在網站）。你沒有為這件事定過出場條件，由你決定。`（只有預設前提的股票再加：`這檔還沒有你的論點，檢查的是系統預設前提。`） |
| 按鈕一 | `照 AI（減半，賣 25 股）`（`id: 'AI'`） |
| 按鈕二 | `拿去討論`：複製討論包（`BREAK`），通知留在「等你決定」 |
| 按鈕三 | `不同意，不動`（`id: 'SKIP'`）：要寫一句理由（1～200 字） |
| LINE | `【當天】MU：AI 審查認為你的前提不成立` ／ `前提「HBM 長約有價格保護」：3 票判不成立` ／ `AI 建議減半，賣 25 股（要不要做由你決定）` ／ 連結 |

- 預設不動（項目的 `choice` 是 `SKIP`，照舊）。
- **回應只有三種**，都寫進 log 的 `RESPONSE`，下一次審查的證據包看得到（§1.6）：

| 回應 | 怎麼做 | 效果 |
|---|---|---|
| 照做（`FOLLOW`） | 按「照 AI」 | 照現有的檔位效果：減半 → 慢規則進減半狀態；出清 → 移出自選、論點檔結案 |
| 修正論點（`REVISE`） | 「拿去討論」之後在編輯論點頁貼回並確認，勾著「這是對通知 #N 的回應」 | 部位不動；通知結案；`thesis.afterBreak` 加 1、記日期；持股頁與之後的討論包顯示「失效後修改第 N 次」。**新的論點如果還留著被判不成立的那條前提（同一個 `id`），當成不同意處理**（進靜默期，理由記「修正論點但保留這條前提」） |
| 不同意（`DISAGREE`） | 按「不同意，不動」並寫理由 | 部位不動；通知結案；這條前提進靜默期 |

- 月報裡的乙類項目：使用者回覆月報時沒動它（沒按照 AI、沒寫理由）→ 記成 `SKIPPED`，和不同意一樣進靜默期（AI 建議是一次性的，設計 §2.3.1）。
- 當天通知一直沒回：照現有的 2 個交易日提醒一次；之後不再提醒，下一次審查的證據包寫「上次的失效通知沒有回應」（`NONE`）。底線仍是慢規則。

#### 靜默期（「不同意」之後多久不再為同一個理由通知）

- 同一個理由＝同一條前提（`premiseId`）。
- 期間：從不同意那天起，到「**滿 45 天之後出現的第一份財報類申報**（10-Q、10-K、8-K Item 2.02）」的前一天為止，最長 100 個日曆天。也就是到下一季的數字出來。45 天是為了跳過同一季後來才補上的 10-Q／10-K。
- 實作：不同意時寫 `disputes`（`until` = 那天加 100 天）；每日流程看到這檔有新的財報類申報、而且距 `since` 已滿 45 天 → 把 `until` 改成前一天。過期的項目留著給網站顯示，判斷時只看 `until` ≥ 審查的日期的。
- 靜默期內：審查照跑、結果在網站；只因為這條前提不成立的建議不通知、不進月報。
- 例外（照常給）：別條前提不成立；AI 的檔位比不同意時更重（減半 → 出清）；硬事件（本來就是另一條路）。

### 1.11 財報新聞稿當天確認財報類條件（P3）

財報新聞稿（8-K Item 2.02 的 EX-99.1）沒有 XBRL，數字要用讀的。做一個小的三票擷取，AI 只抄數字，計算與比對都由程式做。

| 項目 | 內容 |
|---|---|
| 功能代號 | `OWN_EARNINGS`（白話：財報數字擷取），prompt `own_earnings_v1`，Sonnet 獨立 3 票，等級 A3，`verdicts: ['EXTRACTED', 'INSUFFICIENT']` |
| 什麼時候開 | 自選股當天有新的 8-K Item 2.02，同一批新申報裡沒有 10-Q／10-K，而且這檔有至少一條你定的（`ACTIVE`）財報類條件，指標在可算的範圍內 |
| 可算的指標 | `GrossMarginPct`、`OperatingMarginPct`、`NetMarginPct`、`RevenueYoY`、`EPSDiluted`、`Revenue`。`CfoToNetIncome` 不支援（新聞稿的現金流多半是累計），等 10-Q／10-K |
| 證據包 | 這份 8-K 的本文與 EX-99.1；XBRL 八季表（對照用）。**EX-99.1 的取法要改**：現在只取前 30,000 字（`edgar.ts` `fetchFilingDoc`），財務報表常在後段；改成開頭 15,000 字＋從第一個符合 `consolidated statements? of (operations|income|earnings)` 的位置起 45,000 字（找不到就取前 60,000 字） |
| AI 輸出 | `payload`：`{ "period_end": "2026-11-27", "figures": [{ "item": "revenue", "current_text": "13,640", "year_ago_text": "8,709", "scale": 1000000, "evidence_ids": ["E1"] }] }`。`item` 只能是 `revenue`、`gross_profit`、`cost_of_revenue`、`operating_income`、`net_income`、`eps_diluted`；只取 GAAP、單季；數字照原文的寫法抄（`current_text`），不換算、不計算 |

**程式檢查**（任何一項不過就當成沒有擷取，條件照舊等 10-Q／10-K，只記錄）：

1. 每個數字的 `current_text`、`year_ago_text` 都要出現在它引用的那段原文裡（引用本身照常做逐字檢查）。
2. 三票都合格，`period_end` 相同，每個項目換算後的數值三票相差不超過 0.1%。
3. `period_end` 比 XBRL 表最新一季晚 80～100 天（確實是下一季）。
4. **去年同季的數字要和 XBRL 已有的值相符**：金額差 0.5% 以內，每股盈餘差 0.01 以內。對不上的項目不採用（擋抄錯欄、單位錯、抄到非 GAAP）。XBRL 沒有去年同季值的項目也不採用。
5. 通過的項目由程式算指標：毛利 = `gross_profit`，沒有就用 `revenue − cost_of_revenue`；各種比率用本季的數字相除；營收年增率用 XBRL 的去年同季。
6. 和條件的門檻比：`quarters` 大於 1 的，本季用擷取的數字、更早的季用 XBRL。

**成立**：條件標 `MET`、`met_basis = PRESS`，發甲類通知（理由寫「依財報新聞稿…10-Q 出來後再核對」）。
**10-Q／10-K 出來後**：程式用 XBRL 再比一次，寫 `verified_at`。一致就在說明加「10-Q 核對一致」；不一致（XBRL 算出來沒有過門檻）就在說明寫明兩個數字、log 記一筆、下一份月報的狀態文字加一行。不會自動撤回已經做的事。
**不成立或沒擷取到**：什麼都不做；10-Q／10-K 出來時照原本的方式比對。

觀察項（沒勾的財報類條件）不走這條路，它們只是審查的輸入（§1.5）。

- 帳戶狀態新欄位：`OwnMeta.earlyReviewAt: string | null`。

### 2.5 掃描標的 `condition_ids`：留著

掃描的證據包裡，自選股的條件清單（`facts` 的 K 開頭）改成放這兩種：

- 事件類的觀察項（`PROPOSED`，§1.5）。
- 你定的、「只在審查時檢查」的條件（`REVIEW_ONLY`）。

你定的、可以由申報確認的條件（`ACTIVE`）不放：它們照舊由「新申報是確認來源」直接開條件確認（F25），不經過 Haiku。

掃描標到某一條時（`applyEventScan`）：

| 標到的來源 | 做法 |
|---|---|
| 申報原文（8-K） | 寫一筆 `sec_events`：`code = CONDITION_HINT`、`detail_code` = 條件的列編號、狀態 `NEW` → 是提前審查的一個原因（§2.4，同一個 30 天上限）。審查時由三票判斷那條條件成不成立（§1.6） |
| 新聞標題 | 同樣寫一筆，狀態 `INFO`：只記進論點檔的事件，不提前審查（審查要引用申報原文才能通知，只有標題拿不出引用） |

### 2.6 掃描失敗、漏看的處理（S1、S5、S6）

**標記分開**（`flow_state`）：

| 鍵 | 記什麼 | 什麼時候往前推 |
|---|---|---|
| `edgar:<代號>`（原有） | 規則分類看過的最新申報（`acceptedAt`） | 照舊：每天規則段做完（`markSeen`） |
| `scan8k:<代號>`（新） | 掃描看過的最新 8-K（`acceptedAt`） | **掃描有合格結論時**。沒有這個鍵時，第一次用當時的 `edgar:<代號>`，不追溯 |
| `news:<代號>`（原有，改內容） | 掃描看過的最新標題的**發布時間**（ISO 時間，不是日期） | 掃描有合格結論時。舊值是日期的，當成那一天的 23:59:59Z |

**收集**（`startScan`）：

- 8-K：每個對象「`acceptedAt` 比 `scan8k` 新、而且有 `SCAN_ITEMS` 裡的項目」的申報（從全部申報裡找，不是只看當天新的），**由舊到新**，不設每檔 3 份的上限。一次掃描最多 10 份原文（所有對象合計）；裝不下的留到下一次，寫進紀錄。
- 新聞：每檔發布時間比 `news` 新的標題，最多取最新的 30 則；超過的略過，在證據包的備註寫「略過 N 則較舊的標題」（標題只能當初判，不排隊）。`parseRss` 要留下完整的發布時間。
- 證據包的 `rule.detail.cursors` 記下每檔這次看到的最新 `acceptedAt` 與標題時間。
- 已經有一份掃描在等結果時不再開新的。

**套用**（`applyEventScan`）：

- 合格結論＝至少一票格式合格，而且不是逾時、觸發失敗、整份退回。合格 → 寫事件、把兩個標記推到 `cursors`、失敗次數歸零。
- 不合格 → 標記不動，失敗次數加 1（`flow_state` 的 `scan:fails`，記次數與這批文件的清單）。下一次掃描會重新收集同一批加上新的。
- 掃描沒開成（`startRun` 丟錯）也算一次失敗。

**重掃與告警**：

- 每天第一次流程開掃描（照舊）。第二次排程時，當天的掃描如果沒有合格結論（含逾時），重開一次。
- **同一批文件連續 2 次沒有合格結論 → 推告警**（`kind: SCAN_FAILED`），文字：
  `每日掃描連續 2 次沒有結論：MU 的 8-K 2027-01-06（Item 5.02）、NVDA 的 12 則新聞標題還沒有被 AI 看過。規則分類照常；下一次流程會重掃。`
  第一次失敗不推（和每日流程的做法一致）。之後每多失敗一次再推一次，直到成功。
- 網站的 AI 紀錄：沒有合格結論的掃描顯示「掃描失敗，下一次重掃」，不顯示「沒有值得標的事」。

**條件確認（F25）取文件的上限**（`startOwnRuns` 的 `slice(0, 3)`）：改成取全部相關的新申報，最多 8 份；超過時記一筆告警（`F25_OVERFLOW`，寫明哪幾份沒放進去）。
