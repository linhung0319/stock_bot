### 1.2 論點檔：一個組出來的檢視

每一檔自選股一份論點檔。它不是一張新表，是一個函式從五個地方組出來的（「已經決定的方向」第 3 點）：

```
thesisFile(db, acct, ticker) →
  帳戶狀態  acct.own[代號]            現行的論點、前提、靜默期、上限用的日期
  own_conditions                     條件
  sec_events                         事件
  ai_runs                            歷次 L2 的執行與結論
  own_thesis_log（新表）              論點的每一版、失效通知、使用者的回應、開檔與結案
```

- 放在 `worker/src/app/thesis.ts`（讀 D1，所以不在引擎裡；引擎仍是純函式）。L2 各功能的證據包（F24、F7、F25、自選股的 F19）、討論包、持股頁都從這個函式取資料（計畫 T25）。
- **現行的論點與前提留在帳戶狀態**：引擎與證據包本來就從 `acct.own[代號].premises` 讀；而且復原快照、把股數改成 0 又復原時，論點要跟著帳戶一起回來（設計 §10 第 39 點）。
- **歷史放 `own_thesis_log`**（只增加）。

**論點檔的編號**（`fileId`）＝`<代號>@<開檔的訊號日>`，例如 `MU@2026-11-15`，存在 `acct.own[代號].fileId`（`newOwnMeta` 建立）。條件與 log 都帶 `file_id`。

- **結案**：這檔從 `acct.own` 消失（移出自選、照建議出清、股數改 0）就是結案，不用另外改條件的狀態：所有讀條件的地方都只讀「`file_id` 等於這檔現在的 `fileId`」的列，所以舊條件自然不再被監測（修 N8）。再加回是新的 `fileId`，舊的那一份仍可在網站看。復原快照時 `acct.own[代號]` 連同原本的 `fileId` 一起回來，條件也就接回來。
- 結案時 log 寫一筆 `CLOSE`（在存帳戶的地方比較存檔前後的自選名單；`ledgerStore.ts` `saveAccount`）。
- **舊資料**：部署後第一次每日流程，沒有 `fileId` 的自選補上 `<代號>@<那天的訊號日>`，並把 `own_conditions` 裡同代號、`file_id` 是空的、狀態不是 `REPLACED` 的列補上同一個編號。

> **2026-11-16 使用者同意改，T44**（起因：T41 第 7 條——賣光再買回時，上一段的論點、前提、條件、為什麼賣，畫面上都找不到，討論包也從「還沒有寫下論點」開始）：結案的規則不變（再加回仍是新的論點檔，舊的不接回來沿用；舊條件不恢復監測），但新的那一份**看得到上一份**：
> - **記下來**：結案時（`ops.ts` 的 `removeOwnPick`）`Account.ownClosed[代號]` 多記 `last`＝那一刻的論點本文（`{ text, setAt, version }`，沒有本文是 null）與自己的前提（`origin` 不是系統預設的，`{ id, text }`）。跟著帳戶走（復原快照時一起倒回）；T44 之前結案的沒有 `last`，當成沒有記到論點。
> - **上一份**（`thesis.ts` 的 `prevFileOf`／`loadPrevFile`）＝這檔現在是自選、而且 `ownClosed` 記著一份編號和現在不同的論點檔。當時的出場條件從 `own_conditions` 讀 `file_id` 等於上一份編號、你定的、`ACTIVE`／`REVIEW_ONLY`／`MANUAL`（當時監測中），以及 `MET`（已成立，寫成立日）；只顯示，不監測。結案的原因：自己賣光（`SOLD_OUT`）／移出自選（`REMOVED`）／AI 審查建議出清、你照做（`EXIT_AI`）／你定的出場條件成立、出清（`EXIT_CONDITION`）／硬事件審查建議出清、你照做（`HARD_EVENT`）。
> - **持股頁**：這一份還是「只有預設」時，「還沒有你的論點」下面一塊「上一次持有時（M/D 開檔 → M/D 賣光）」：那時的論點本文與自己的前提、當時監測中的出場條件、結案的原因，並寫明「只是紀錄：不沿用、舊條件不恢復監測」。這一份已經有論點之後，同一塊收合放在論點那一塊最下面（還是找得到）。「還沒有論點的自選」那一行（帳戶頁的清單、快照結果頁的清單）在上一份有論點時寫「上次持有時有論點」。
> - **討論包**（§1.7）：有上一份時多一節「## 上一次持有時的論點」（在「我買進時的想法」之後、「我的論點」之前；四種情境都放）。前提**不帶編號**，免得和這一份收尾區塊的 `[P2]` 混在一起。`NEW` 情境的開場改成從「上次為什麼賣、這次為什麼買回」問起。固定指示不改（這一節自己寫明用途），仍是 `discussion_v3`。
> - **編輯論點頁**（§1.8）：上一份有論點本文或自己的前提時，「新的」那一欄上面給「帶入上次的論點」：把上次的本文與前提填進右邊，前提一律當成新的（不帶上一份的編號，存檔時發這一份的新編號）；出場條件不帶，要重新寫。
> - **L2 的證據包不放上一份**：`thesisFile` 只組現在這一份，定期審查、減半檢視、條件確認、硬事件的證據包都不讀 `ownClosed`。

**論點檔的種類**（程式判斷，不存）：前提裡至少一條 `origin` 不是 `SYSTEM_DEFAULT` → 「有論點」；否則「只有預設」。

### 1.5 條件

#### 欄位（`own_conditions`，migration 加欄位）

| 欄位 | 說明 |
|---|---|
| 原有：`ticker`、`run_id`、`cond_id`、`direction`、`kind`（`XBRL`／`EVENT`／`PRICE`）、`text`、`check_json`、`tier_if_met`、`status`、`created_at`、`met_at`、`note`、`origin` | `origin`：條件的文字是誰寫的。`USER` = 你寫的（經 AI 改寫格式）；`AI` = 審查建議的。`tier_if_met` 對 AI 建議的條件是「AI 建議成立時做什麼」，只當勾選時的預設值 |
| 新：`file_id` | 屬於哪一份論點檔 |
| 新：`accepted_at` | 你勾選的時間。**有值就是「你定的條件」**，不論文字是誰寫的 |
| 新：`action` | 成立時做什麼：`EXIT`（出清）／`HALF`（減半）／`REVIEW`（重新審查）。勾選時定，之後可改 |
| 新：`premise_id` | 對應哪一條前提（可以是空的） |
| 新：`supersedes` | AI 建議「用這條取代那一條」時，被取代的列編號 |
| 新：`met_basis` | 成立是怎麼確認的：`XBRL`（程式比對 10-Q／10-K）／`PRESS`（財報新聞稿擷取，§1.11）／`FILING_VOTE`（申報原文三票）／`REVIEW_VOTE`（審查三票） |
| 新：`verified_at` | `PRESS` 成立的條件，10-Q／10-K 出來後核對的時間 |

「誰定的、哪一天」＝`origin` ＋ `accepted_at`；顯示成「你寫的，11/20 定」或「AI 建議，你在 11/20 勾選」。

#### 怎麼確認（由條件本身推出來，不另存；函式 `confirmMode`）

| 條件 | 確認方式 | 顯示 |
|---|---|---|
| `kind = XBRL` | 程式比對財報數字（新 10-Q／10-K；財報新聞稿當天見 §1.11） | 新財報出來時比對 |
| `kind = EVENT`，`confirm_by` 裡有申報類型（`8-K`、`10-Q`、`10-K`、`SEC`） | 新申報出現 → 條件確認（F25）三票讀原文 | 新申報出來時由 AI 確認 |
| `kind = EVENT`，`confirm_by` 只有 `earnings_call`、`major_news` | 只在審查時由三票判斷（P4） | 只在定期審查時檢查 |
| `kind = PRICE` 或沒通過格式檢查 | 不確認 | 只記錄 |

#### 狀態

| `status` | 意思 | 會不會自己發通知 |
|---|---|---|
| `PROPOSED` | 建議中：審查建議、你還沒勾選。也就是**觀察項** | 不會（見下） |

| `REVIEW_ONLY` | 只在審查時檢查（你定的；確認方式是第三種） | 審查三票確認成立時發甲類通知 |
| `MANUAL` | 只記錄（價格條件、沒通過檢查的） | 不會 |
| `MET` | 已成立。一次性，不會再觸發；要再監測就重新定一條 | — |
| `RETIRED` | 你撤下，或被你勾選的新條件取代 | — |
| `EXPIRED` | 建議中的過期了 | — |
| `REPLACED` | 舊資料：改版前被整組替換的 | — |

#### 從「建議」到「監測中」

1. **審查不再整組替換條件。** 每次審查最多提 3 條「建議新增」（`payload.proposed_conditions`，§1.6），可以註明想取代哪一條（`supersedes`）。只有三票一致的審查（含一致選「不動」）才寫入，取自和結論同檔位的第一張合格票；票數不一致、資料缺漏、不合格、逾時的審查不動條件（修 N4、P5）。
2. 寫入時狀態是 `PROPOSED`。這次審查有寫入至少一條時，這檔原本還在 `PROPOSED` 的標成 `EXPIRED`（prompt 請 AI 把還適用的觀察項原樣再提，算在 3 條內）。這次一條都沒提時，舊的留著。
3. **你勾選**（持股頁）：選成立時做什麼（出清／減半／重新審查；預設帶 AI 建議的檔位）→ 寫 `accepted_at`、`action`，狀態依確認方式變成 `ACTIVE`／`REVIEW_ONLY`／`MANUAL`。有 `supersedes` 的，被取代的那條標 `RETIRED`。從此是你定的條件，之後的審查換不掉。log 寫 `CONDITION`。
4. **沒勾的是觀察項，自己不會發通知**（使用者 2026-11-15 決定；比「已經決定的方向」第 5 點的字面多一步，理由：沒表決的條件不能直接叫人賣，但整個丟掉會讓沒寫論點的股票失去條件監測）：
   - 財報類的觀察項：下一次審查組證據包時，程式用當時的財報數字算好「成立／不成立／資料還沒更新」，放進證據包（`facts` 的 W 開頭）。
   - 事件類的觀察項：交給每日掃描當觀察清單；標到之後怎麼提前開審查、頻率上限多少，在第 2 章定。
   - 觀察項成立與否只是給審查的輸入；要不要通知仍看 §1.9 的門檻（前提不成立）。
5. **上限**：一檔的 `ACTIVE`＋`REVIEW_ONLY` 最多 8 條；滿了要先撤下一條才能再勾。`PROPOSED` 最多 3 條（一次審查的量）。

- 當天通知一直沒回：照現有的 2 個交易日提醒一次；之後不再提醒，下一次審查的證據包寫「上次的失效通知沒有回應」（`NONE`）。底線仍是慢規則。

#### 靜默期（「不同意」之後多久不再為同一個理由通知）

- 同一個理由＝同一條前提（`premiseId`）。
- 期間：從不同意那天起，到「**滿 45 天之後出現的第一份財報類申報**（10-Q、10-K、8-K Item 2.02）」的前一天為止，最長 100 個日曆天。也就是到下一季的數字出來。45 天是為了跳過同一季後來才補上的 10-Q／10-K。
- 實作：不同意時寫 `disputes`（`until` = 那天加 100 天）；每日流程看到這檔有新的財報類申報、而且距 `since` 已滿 45 天 → 把 `until` 改成前一天。過期的項目留著給網站顯示，判斷時只看 `until` ≥ 審查的日期的。
- 靜默期內：審查照跑、結果在網站；只因為這條前提不成立的建議不通知、不進月報。
- 例外（照常給）：別條前提不成立；AI 的檔位比不同意時更重（減半 → 出清）；硬事件（本來就是另一條路）。
- **前提沿用編號、但字改了（2026-11-16 使用者同意改，T42）**：編輯論點時 `mapPremises` 判定「沿用編號、但字改了」（只改標點或空白的不算）的前提，`disputes` 裡這條前提還在期間內的那一筆結束：`until` 改成前一天，記 `ended = { date, reason: '前提的字改了' }`；持股頁不再寫靜默中。理由：舊的「不同意」針對的是舊的字，不能蓋住意思已經變了的新前提。已經提早結束的那一筆，之後的財報類申報不再改它。**回應乙類通知的那一次存檔也一樣（T46）**：被判不成立的那條前提字改了，不會因為「留著同一個編號」而開一段新的靜默期。

### 1.11 財報新聞稿當天確認財報類條件（P3）

財報新聞稿（8-K Item 2.02 的 EX-99.1）沒有 XBRL，數字要用讀的。做一個小的三票擷取，AI 只抄數字，計算與比對都由程式做。

| 項目 | 內容 |
|---|---|
| 功能代號 | `OWN_EARNINGS`（白話：財報數字擷取），prompt `own_earnings_v1`，Sonnet 獨立 3 票，等級 A3，`verdicts: ['EXTRACTED', 'INSUFFICIENT']` |
| 什麼時候開 | 自選股當天有新的 8-K Item 2.02，同一批新申報裡沒有 10-Q／10-K，而且這檔有至少一條你定的（`ACTIVE`）財報類條件，指標在可算的範圍內 |
| 可算的指標 | `GrossMarginPct`、`OperatingMarginPct`、`NetMarginPct`、`RevenueYoY`、`EPSDiluted`、`Revenue`。`CfoToNetIncome` 不支援（新聞稿的現金流多半是累計），等 10-Q／10-K |
| 證據包 | 這份 8-K 的本文與 EX-99.1；XBRL 八季表（對照用）。**EX-99.1 的取法要改**：現在只取前 30,000 字（`edgar.ts` `fetchFilingDoc`），財務報表常在後段；改成開頭 15,000 字＋從第一個符合 `consolidated statements? of (operations|income|earnings)` 的位置起 45,000 字（找不到就取前 60,000 字） |
| AI 輸出 | `payload`：`{ "period_end": "2026-11-27", "figures": [{ "item": "revenue", "current_text": "13,640", "year_ago_text": "8,709", "scale": 1000000, "evidence_ids": ["E1"] }] }`。`item` 只能是 `revenue`、`gross_profit`、`cost_of_revenue`、`operating_income`、`net_income`、`eps_diluted`；只取 GAAP、單季；數字照原文的寫法抄（`current_text`），不換算、不計算 |

**程式檢查**（任何一項不過就當成沒有擷取，條件照舊等 10-Q／10-K，只記錄）：

1. 每個數字的 `current_text`、`year_ago_text` 都要出現在它引用的那段原文裡（引用本身照常做逐字檢查）。
2. 三票都合格，`period_end` 相同，每個項目換算後的數值三票相差不超過 0.1%。
3. `period_end` 比 XBRL 表最新一季晚 80～100 天（確實是下一季）。
4. **去年同季的數字要和 XBRL 已有的值相符**：金額差 0.5% 以內，每股盈餘差 0.01 以內。對不上的項目不採用（擋抄錯欄、單位錯、抄到非 GAAP）。XBRL 沒有去年同季值的項目也不採用。
5. 通過的項目由程式算指標：毛利 = `gross_profit`，沒有就用 `revenue − cost_of_revenue`；各種比率用本季的數字相除；營收年增率用 XBRL 的去年同季。
6. 和條件的門檻比：`quarters` 大於 1 的，本季用擷取的數字、更早的季用 XBRL。

**成立**：條件標 `MET`、`met_basis = PRESS`，發甲類通知（理由寫「依財報新聞稿…10-Q 出來後再核對」）。
**10-Q／10-K 出來後**：程式用 XBRL 再比一次，寫 `verified_at`。一致就在說明加「10-Q 核對一致」；不一致（XBRL 算出來沒有過門檻）就在說明寫明兩個數字、log 記一筆、列進「要看的事」（§3.6.6 的 `PRESS_MISMATCH`）。不會自動撤回已經做的事。
**不成立或沒擷取到**：什麼都不做；10-Q／10-K 出來時照原本的方式比對。

觀察項（沒勾的財報類條件）不走這條路，它們只是審查的輸入（§1.5）。

### 2.3 由規則先判斷的

比照會計師辭任的 `classify401`：能從申報本身看出來的不靠 Haiku（S3）。寫在 `secEvents.ts`。

1. **8-K 的 Item 編號直接對到類別與細項**（`quickHits` 加）：1.02、1.03、1.05、2.04、2.05、2.06、3.01，對照見 §2.2。公司自己選的項目，不用再判。這幾項裡原本就在 `SCAN_ITEMS` 的（1.02、1.03、2.05、2.06）照樣送給 Haiku 看（可能另外標出硬事件候選）；1.05、2.04、3.01 不加進 `SCAN_ITEMS`。
2. **8-K Item 5.02 的執行長、財務長離任**（新函式 `classify502(text)`，要讀原文，所以 5.02 加進 `needsCover`）：
   - 取 Item 5.02 那一節：從 `item\s*5\.?02` 起到下一個 `item\s*\d\.\d{2}` 或 8,000 字。
   - 職稱：執行長 `chief executive officer|principal executive officer|\bCEO\b`；財務長 `chief financial officer|principal financial officer|\bCFO\b`。
   - 離任：`resign|retire|step(ped|ping)? down|terminat|depart|ceas\w* to serve|remov\w+|separat\w+|will leave|leaving|not (stand|seek) (for )?re-?(election|appointment)`。
   - 職稱和離任的字出現在同一節、相距 300 字以內 → 記 `MGMT_CHANGE`／`CEO_DEPART` 或 `CFO_DEPART`（`sub` = `8K_5.02_CEO_DEPART`、`8K_5.02_CFO_DEPART`，`by_rule = 1`）。
   - 會有誤判（例如同一段提到執行長簽了別人的離職協議）。代價是多一次提前審查，受 §2.4 的頻率上限限制，可以接受；實作時用幾份真實的 5.02 當測試資料調正規表示式。
   - 5.02 照樣送給 Haiku；兩邊標到同一份申報時，提前審查只算一次（照申報編號去重）。
3. **13D**：申報類型是 `SC 13D` 或 `SCHEDULE 13D`（不含 `/A` 的修正；實作時用實際資料確認 EDGAR 現在用哪個名稱）→ 記 `ACTIVIST`／`SC_13D`，只記錄。13G 不記。
4. **財測下修不做規則後備**：關鍵字誤判太多。漏標的代價有上限——下一次審查的證據包會帶那份 8-K 的原文（§1.6）。

規則段寫入 `sec_events` 時的狀態（`applyRuleEvents`）：對象是自選股、而且細項是可提前的 → `NEW`（等 §2.4 處理）；其餘新類別 → `INFO`。

### 2.4 提前開審查（L1、L0 交給 L2）

「已經決定的方向」第 8 點。交接經過共用的資料：事件先寫進 `sec_events`，另一個函式讀它來開審查（和開硬事件法庭 `startCourts` 同一個做法）。新函式 `startEarlyReviews`（`ownAi.ts`）。

**候選**：自選股的 `sec_events`，狀態 `NEW`、細項在 §2.2 標「是」的那幾種、來源是申報（`accession` 是 `edgar:` 開頭或申報編號；新聞標題標到的在寫入時就是 `INFO`，只記進論點檔）或價格規則（`source` 是 `PRICE`，§3.6.1）、事件日在最近 10 個日曆天內。第 3 章的 L0 觸發也走同一個函式、同一個上限。

**開不開**（照順序看，第一個符合的就決定）：

| 情況 | 做法（事件標 `HANDLED`，`handled_note` 寫原因） |
|---|---|
| 這檔今天已經開了審查（財報後、月審），或已經有一次審查的決策日 ≥ 事件日（那份原文已經在它的證據包裡） | 不開。「已經在 <run_id> 的證據包裡」 |
| 只限價格類（`PRICE_DROP`）：這檔最近 30 個日曆天內跑過減半檢視（F7） | 不開。「30 天內已經做過減半檢視」 |
| 只限價格類：上次有結論的審查之後沒有新的申報或事件（§3.7「新證據」的 `FILING`、`EVENT` 都沒有，也不是 `NEVER`） | 不開。「沒有新的申報可以檢查」；列進「要看的事」（§3.6.6 的 `PRICE_NO_FILING`） |
| 月審在接下來 3 個交易日內 | 不開。「留給月審」 |
| 這檔最近 30 個日曆天內提前開過（`acct.own[代號].earlyReviewAt`） | 不開。「30 天內已經提前審查過，留給下一次審查」 |
| 其餘 | 開一次審查，觸發原因 `EARLY`；`earlyReviewAt` 記今天。「提前審查 <run_id>」 |

- **頻率上限**：每檔 30 個日曆天最多 1 次提前審查，L1 與 L0 的觸發合併計算（使用者 2026-11-15 決定）。不算在內的：財報後的審查、月審、你定的「重新審查」條件觸發的審查（§1.10）、論點變動後的審查（§3.6.5，它有自己的 30 天上限）。
- 沒開成的事件留在論點檔，下一次審查的證據包看得到（§1.6 的 `V` 與 8-K 原文）。
- 提前審查的證據包和一般審查相同，題目加一句「這次是提前審查，原因：<事件的說明>」，`rule.detail` 記觸發的事件編號。
- 結論怎麼用：§1.9（符合門檻可以當天通知）。
- 只有預設前提的股票也一樣。
- 帳戶狀態新欄位：`OwnMeta.earlyReviewAt: string | null`。

### 2.5 掃描標的 `condition_ids`：留著

掃描的證據包裡，自選股的條件清單（`facts` 的 K 開頭）改成放這兩種：

- 事件類的觀察項（`PROPOSED`，§1.5）。
- 你定的、「只在審查時檢查」的條件（`REVIEW_ONLY`）。

你定的、可以由申報確認的條件（`ACTIVE`）不放：它們照舊由「新申報是確認來源」直接開條件確認（F25），不經過 Haiku。

掃描標到某一條時（`applyEventScan`）：

| 標到的來源 | 做法 |
|---|---|
| 申報原文（8-K） | 寫一筆 `sec_events`：`code = CONDITION_HINT`、`detail_code` = 條件的列編號、狀態 `NEW` → 是提前審查的一個原因（§2.4，同一個 30 天上限）。審查時由三票判斷那條條件成不成立（§1.6） |
| 新聞標題 | 同樣寫一筆，狀態 `INFO`：只記進論點檔的事件，不提前審查（審查要引用申報原文才能通知，只有標題拿不出引用） |

### 2.6 掃描失敗、漏看的處理（S1、S5、S6）

**標記分開**（`flow_state`）：

| 鍵 | 記什麼 | 什麼時候往前推 |
|---|---|---|
| `edgar:<代號>`（原有） | 規則分類看過的最新申報（`acceptedAt`） | 照舊：每天規則段做完（`markSeen`） |
| `scan8k:<代號>`（新） | 掃描看過的最新 8-K（`acceptedAt`） | **掃描有合格結論時**。沒有這個鍵時，第一次用當時的 `edgar:<代號>`，不追溯 |
| `news:<代號>`（原有，改內容） | 掃描看過的最新標題的**發布時間**（ISO 時間，不是日期） | 掃描有合格結論時。舊值是日期的，當成那一天的 23:59:59Z |

**收集**（`startScan`）：

- 8-K：每個對象「`acceptedAt` 比 `scan8k` 新、而且有 `SCAN_ITEMS` 裡的項目」的申報（從全部申報裡找，不是只看當天新的），**由舊到新**，不設每檔 3 份的上限。一次掃描最多 10 份原文（所有對象合計）；裝不下的留到下一次，寫進紀錄。
- 新聞：每檔發布時間比 `news` 新的標題，最多取最新的 30 則；超過的略過，在證據包的備註寫「略過 N 則較舊的標題」（標題只能當初判，不排隊）。`parseRss` 要留下完整的發布時間。
- 證據包的 `rule.detail.cursors` 記下每檔這次看到的最新 `acceptedAt` 與標題時間。
- 已經有一份掃描在等結果時不再開新的。
- 對象是自選股與動能持股。排名 6～10 的候選股不再每天掃（T21 的結論）：動能進場前的回看是另一份掃描，有自己的標記 `lookback:<代號>`，不動這裡的標記與失敗次數（`momentum_ai_design_2026-11-15.md` §3.2）。

**套用**（`applyEventScan`）：

- 合格結論＝至少一票格式合格，而且不是逾時、觸發失敗、整份退回。合格 → 寫事件、把兩個標記推到 `cursors`、失敗次數歸零。
- 不合格 → 標記不動，失敗次數加 1（`flow_state` 的 `scan:fails`，記次數與這批文件的清單）。下一次掃描會重新收集同一批加上新的。
- 掃描沒開成（`startRun` 丟錯）也算一次失敗。

**重掃與告警**：

- 每天第一次流程開掃描（照舊）。第二次排程時，當天的掃描如果沒有合格結論（含逾時），重開一次。
- **同一批文件連續 2 次沒有合格結論 → 推告警**（`kind: SCAN_FAILED`），文字：
  `每日掃描連續 2 次沒有結論：MU 的 8-K 2027-01-06（Item 5.02）、NVDA 的 12 則新聞標題還沒有被 AI 看過。規則分類照常；下一次流程會重掃。`
  第一次失敗不推（和每日流程的做法一致）。之後每多失敗一次再推一次，直到成功。
- 網站的 AI 紀錄：沒有合格結論的掃描顯示「掃描失敗，下一次重掃」，不顯示「沒有值得標的事」。

**條件確認（F25）取文件的上限**（`startOwnRuns` 的 `slice(0, 3)`）：改成取全部相關的新申報，最多 8 份；超過時記一筆告警（`F25_OVERFLOW`，寫明哪幾份沒放進去）。

**硬事件法庭（F19）沒有結論時**：重開與告警（`HARD_COURT_FAILED`）、有結論後只有新的申報才重開、事件 10 天過期、轉交事件的原文怎麼取，寫在 `momentum_ai_design_2026-11-15.md` §3.5（T21 定的；`startCourts` 是共用的，自選股也適用）。自選股硬事件的通知沒有新增上限（§1.9 照舊）。

### 3.2 慢規則的定位

「已經決定的方向」第 2 點：自選股的重點是論點，慢規則是輔助。寫清楚它做什麼、不做什麼。參數（`SLOW`：-20%、200 日、10 天、15 個交易日）與狀態機不動，重放驗收的結果不能變。

慢規則對自選股只做三件事：

1. **觸發**：減半時開減半檢視（F7）。
2. **底線**：通知的預設選項。使用者沒有另外決定時照它做（§3.4）。
3. **狀態**：記這檔是標準還是減半；AI 的檔位照設計 §2.2 的對應換成股數。

它不是論點的證據。所有 L2 的 prompt 都寫「價格跌了不是論點壞了的證據」（照舊）；證據包裡慢規則的數字放在規則狀態（`facts` 的 F、R 開頭），不放在前提的證據。

**預設選項不改，仍是「照規則」**（使用者 2026-11-15 決定）。理由：

- F7 選「不動」的標準是「跌幅主要來自大盤或產業、前提都還成立」。B-1、B-5 裡慢規則有用的 2000–2002、2008、2022 正是這種下跌；V 型反彈（2020、2025/4）時不動才對，但 AI 分不出這兩種。
- TradingAgents 回測（2026-11-07）：AI 判斷時點 5/9，價格規則 7/9；當時同意的做法是「價格規則成立而且跌得夠深，AI 說持有也減」。
- F7 一年約 3 次，「照 AI 不動」是加分還是扣分要 5 年以上才看得出來（`ai_layer_design` §7 的往前驗證）。

主從改在**呈現與流程**：通知先寫論點檢查的結果，再列規則的底線（§3.4）；LINE 等論點檢查回來才推（§3.5）。

### 3.3 減半檢視（F7）要改的

prompt 升成 `own_drop_v2`（實作時改；這次討論不動 prompt）。什麼時候開不變：慢規則每一次新觸發減半（當天通知的與等月報的），同一檔同一個訊號日只開一次。

**證據包**（由論點檔組，計畫 T25）在現有的價格、規則狀態、跌幅拆解（`A1`～`A5`）、最近一次審查的摘要、新聞標題之外：

| 改什麼 | 內容 |
|---|---|
| 加：論點檔種類、論點本文與最近 3 次審查的結論和使用者的回應、靜默中的前提 | 格式同 §1.6（`T0`、`thesis:<fileId>` 那份 `note`） |
| 加：你定的條件與觀察項 | `facts` 的 `C`、`W`，同 §1.6。只當背景：F7 不確認條件成不成立（那是審查與條件確認的事），輸出沒有 `condition_checks` |
| 加：上次有結論的審查之後的事件 | `facts` 的 `V`，同 §1.6 |
| 改：之後的申報原文 | 現在是「上次審查之後的 8-K、10-Q、10-K 最多 3 份」。數量不變，順序照 §1.6（最新的 Item 2.02、有標記的、其餘） |
| 加：系統預設前提的程式結果（只有預設的股票） | `D1`～`D3`（§1.12） |
| 拿掉：R1 | `ownRuleFacts` 的 `R4`（§3.9） |

**可以選的檔位**（`policy.verdicts`）：有論點的股票 `EXIT`、`HALF`、`HOLD`（照舊）；**只有預設前提的股票只有 `EXIT`、`HALF`**（使用者 2026-11-15 決定：AI 能對底線提異議，是因為它檢查了使用者的論點；沒有論點就沒有東西可檢查）。題目多一句「這檔沒有使用者的論點，只能選照規則減半或出清」。

**程式怎麼用結論**（`dropDecision` 改寫；修 K4）。結果是下面五種之一，寫進帳戶狀態的 `dropReview`（見下）：

| 結果 | 條件 |
|---|---|
| `EXIT`（建議出清） | 三票都選 `EXIT`、資料沒有缺漏，而且有一條「不成立的前提」，定義同 §1.6 第 1 點（三票都判同一條 `BROKEN`，每一票都至少有一條通過檢查、來源是申報原文或財報表的引用） |
| `HOLD`（建議不動） | 三票都選 `HOLD`、資料沒有缺漏；三票的 `cause_class` 都是 `MARKET` 或 `SECTOR`；沒有任何一票把任何前提判成 `BROKEN`（被引用檢查降級的也算判過）；而且**程式核對跌幅拆解**：拆解算得出來、個股是跌的、個股自身的跌幅不超過整段跌幅的一半（`attr.stock < 0 && attr.idio >= 0.5 * attr.stock`；拆解的期間照舊，從 52 週高點那天到今天） |
| `AGREE`（同意減半） | 三票都選 `HALF` |
| `NONE`（沒有可用的結論） | 其餘：票數不一致、三票 `EXIT` 或 `HOLD` 但沒過上面的條件、資料缺漏、不合格、逾時、被退回、沒開成 |
| `PENDING` | 開了、還沒有結果 |

- 轉交硬事件法庭（`escalate_to_F19`）照舊，和上面的結果無關。
- `EXIT` 另外寫 `aiTier`（`tier: 'EXIT'`、`premiseId`、`trigger: 'DROP'`、`suggest: false`），之後加回時看得到（§3.4）。`HOLD`、`AGREE`、`NONE` 不動 `aiTier`。

**帳戶狀態新欄位**（`OwnMeta.dropReview`，每檔最多一筆，對應目前這一次減半）：

```
dropReview: {
  session: string            // 觸發減半的訊號日
  runId: string | null
  status: 'PENDING' | 'HOLD' | 'EXIT' | 'AGREE' | 'NONE'
  cause: string | null       // 和結論同檔位的第一張合格票的 cause_class
  premiseId: string | null   // EXIT 時：不成立的那條前提
  told: boolean              // 這個結果有沒有跟著通知推過 LINE（§3.5）
} | null
```

- `startDropRuns` 開成時寫 `PENDING`；沒開成（或 AI 層沒設定）寫 `NONE`。`applyOwnDrop` 套用時改成結果；執行逾時或被退回時改成 `NONE`（和標記逾時同一個地方）。
- 清掉：這檔的減半項目被回覆之後；慢規則下一次切換或和尚未下單的那次互相抵銷時。

### 3.4 慢規則通知上的 AI 那一行與選項

原則：**「照 AI」只來自看過這次觸發的結論**（使用者 2026-11-15 決定；修 K1、K2、K5）。`ownAiChoice` 改寫，`refreshOwnAiChoice` 照新規則重算還沒回覆的通知。

#### 減半（F7 項目）

項目標題：`MU：比 52 週高點低 22.4% → 慢規則減半`（等月報的照舊在後面加「（MM-DD 觸發，變動 < 5%，併入月報）」）。通知標題照舊（`MU 慢規則減半`）。理由（`why`）：`收盤距 52 週高點跌 ≥ 20%。慢規則是底線：你沒有另外決定時照它做。`

選項的順序固定：**照規則（預設，`choice` 與 `ruleChoice` 都是 `RULE`）**、照 AI（有才列）、這次不做。

| `dropReview.status` | AI 那一行（`aiLine`） | 「照 AI」選項 |
|---|---|---|
| `PENDING` | `AI 論點檢查進行中，台灣 09:30 前更新` | 沒有 |
| `HOLD` | `論點檢查（3 票）：跌幅主要是產業一起跌；你的 3 條前提都沒有被判不成立。AI 建議不動`（`MARKET` 時寫「大盤一起跌」） | `照 AI：不動`（`tier: 'HOLD'`，不下單）。選項說明：`AI 判斷的是論點有沒有壞，不是會不會繼續跌。大盤或產業帶動的下跌，正是慢規則在 2000–2002、2008、2022 年有用的情況。` |
| `EXIT` | `論點檢查（3 票）：前提「HBM 長約有價格保護」不成立。AI 建議出清，賣 50 股` | `照 AI：出清，賣 50 股`（`tier: 'EXIT'`，效果照舊：移出自選、論點檔結案）。項目另外有「拿去討論」（討論包 `BREAK`，依據是這次 F7 的引用） |
| `AGREE` | `論點檢查（3 票）：同意減半（歸類：公司基本面）`（歸類照 `CAUSE_TEXT`） | 沒有 |
| `NONE` | `AI 論點檢查沒有一致結論，照規則` | 沒有 |
| 沒有 `dropReview`（舊通知） | 不顯示 | 沒有 |

- 只有預設前提的股票：理由後面加 `這檔還沒有你的論點，AI 只檢查系統預設前提。`（`HOLD` 不會出現，§3.3）。
- **觸發之後另外有審查回來**（等月報的那幾週內常見；條件：`aiTier.date` ≥ `dropReview.session`、`aiTier.trigger` 不是 `DROP`、符合 §1.9 的資格，靜默期不看）：
  - 檔位是出清 → 那一行與選項換成出清（文字同上表 `EXIT`，前面寫審查的日期）。
  - 檔位是減半（有不成立的前提）→ 拿掉「不動」選項，那一行改成 `MM-DD 的審查認為前提「…」不成立，同意減半`。
  - 其他（沒有不成立的前提）→ 不影響 F7 的結果。
- 靜默期（§1.10）不擋這一行：它附在規則的通知上，不是 AI 另外發的通知。那條前提在靜默中時，後面加 `（你在 MM-DD 對這條前提表示不同意）`。
- LINE 多一行（放在下單清單後面）：`AI 論點檢查：建議不動（預設仍是照規則），到網站決定`／`AI 論點檢查：前提不成立，建議出清（預設仍是照規則），到網站決定`／`AI 論點檢查：同意減半`／`AI 論點檢查還沒有結論`。

**「這次不做」要寫一句理由**（1～200 字，沒寫不能送出；使用者 2026-11-15 決定，改設計 §2.3.1）。只限減半項目；整則通知選「這次不做」時，裡面有減半項目也要寫。「照 AI」不用寫。加回、動能、核心的項目照舊不用。規則狀態照舊前進（設計 §2.3.1）。

**回應寫進論點檔**（`own_thesis_log`）：

- 項目帶「出清」那一行時，通知產生或更新成出清的那一刻寫 `BREAK_NOTICE`（`type: 'B'`、`withRule: true`、`premiseId`、`tier: 'EXIT'`）。
- 回覆時寫 `RESPONSE`：`type: 'R'`（慢規則通知）、`outcome`：`RULE`（照規則）／`FOLLOW`（照 AI）／`SKIPPED`（這次不做）、`reason`、`aiOffered`（`HOLD`／`EXIT`／空）。
- **AI 建議出清、使用者選了照規則或這次不做** → 那條前提進靜默期（§1.10 的規則；理由記使用者寫的，沒寫的記「照規則減半，沒有照 AI 出清」），免得下一次審查又為同一條前提通知。
- 慢規則通知不能用「修正論點」結案：編輯論點頁不顯示「這是對通知 #N 的回應」；改完論點仍要回通知選一項。這檔有還沒回覆、帶「出清」那一行的慢規則通知時存論點，`thesis.afterBreak` 照樣加 1。
- 影子紀錄照舊三條線（照規則、照 AI、實際）。

**慢規則通知產生時，同一檔有還沒回覆的乙類通知**（§1.10）：乙類那一則標 `SUPERSEDED`，它的內容併進慢規則項目——AI 建議出清的，依上面「觸發之後另外有審查回來」處理；AI 建議減半的，那一行寫 `MM-DD 的審查認為前提「…」不成立，同意減半`。回應照這一節的規則寫 log。反過來（慢規則通知還沒回覆時審查回來）照 §1.9 的表，不另發。

#### 加回（F8 項目）

- 「照 AI」選項（維持減半／出清）只在這個情況列：`aiTier` 的檔位是減半或出清、有 `premiseId`（三票判同一條前提不成立，§1.6 第 1 點）、而且那條前提還在現行的前提裡。那一行：`MM-DD 的審查認為前提「…」不成立：AI 建議維持減半`（或出清與股數）。
- 其他情況只有規則一行。審查在減半狀態下選了「減半」但沒有不成立的前提，不算異議（修 K5）。
- 那條前提在靜默中時照列，後面加 `（你在 MM-DD 對這條前提表示不同意）`。
- 未解除的硬事件標記、已成立的條件的註記照舊。預設照規則、不用寫理由、推播時間照舊。

### 3.6 新的觸發與「要看的事」

#### 3.6.1 個股自身大跌（取代自選股的 F20）

K6：原本的門檻（21 個交易日跌 20%）對自選股永遠不會比慢規則早。改成扣掉產業之後的跌幅，標準、減半兩種狀態都適用（補 K7）。使用者 2026-11-15 決定門檻 10 個百分點：這個觸發只開審查、不下單，寧可早一點。

- **定義**（純函式，放 `worker/src/ai/detect.ts`，用現有的 `attribution(axis, close, ticker, 核心 ETF, 產業 ETF, i - 21, i)`）：`stock ≤ -0.10` 而且 `idio ≤ -0.10`。也就是最近 21 個交易日自己跌 10% 以上，而且比產業 ETF 多跌 10 個百分點以上（沒有產業 ETF 時比核心 ETF）。常數 `IDIO_DROP = { days: 21, stock: -0.10, idio: -0.10 }`。算不出來（資料不足）就不成立。
- **對象**：自選股。動能持股的 F20 改成程式產生的一行，不呼叫 AI（§2.8）。
- **什麼時候算**：每天第一次流程，原本 `startDropRuns` 裡 F20 的位置。成立時寫一筆 `sec_events`：

  | 欄位 | 值 |
  |---|---|
  | `accession` | `price:<代號>:<訊號日>` |
  | `form`、`source` | `RULE`、`PRICE`（新的來源值） |
  | `code`、`detail_code`、`sub` | `PRICE_DROP`、`IDIO_21D`、`RULE_IDIO_21D` |
  | `by_rule`、`display_only` | 1、0 |
  | `detail` | `最近 21 個交易日：個股 -18.2%，產業（SOXX）-5.1%，個股自身 -13.1%` |
  | `status` | `NEW` |

- **不寫的情況**：這檔最近 30 個日曆天內已經有一筆 `PRICE_DROP`；同一天慢規則觸發減半（那天跑 F7）。
- **之後**：由 `startEarlyReviews`（§2.4）處理，和 L1 的事件共用每檔 30 天 1 次的上限。價格類多兩種不開的情況（已寫進 §2.4 的表）：30 天內跑過減半檢視；上次有結論的審查之後沒有新的申報或事件（§3.7「新證據」的前兩項）。後一種沒有東西可讀，審了也只能說「價格跌了」，所以列進「要看的事」（§3.6.6 的 `PRICE_NO_FILING`），請使用者拿去 claude.ai 討論（那邊可以上網）。
- 開成的提前審查：題目加 `原因：最近 21 個交易日個股自身跌 13.1%`，證據包加這 21 天的跌幅拆解（`A1`～`A5`，和 F7 同一個函式）。

頻率的粗估（MU、NVDA、MSFT、META，2013–2026，產業一律用 XLK，扣掉和慢規則減半同一天的；暫時的腳本，沒有 commit）：

| 門檻 | 每檔每年成立 | 其中在「標準」狀態 |
|---|---|---|
| 10 個百分點（採用） | 約 1.5 次（MU 2.9、NVDA 1.2、MSFT 0.3、META 1.7） | 約 0.6 次，其中一半在之後 3 個月內走到慢規則減半 |
| 15 個百分點 | 約 0.8 次 | 14 年四檔合計 11 次 |

實際開的審查更少（30 天上限、沒有新申報的不審、財報後的審查已經看過的不審）。

#### 3.6.2 財報門檻條件的進度

不發通知、不開審查，只記錄與顯示：讓使用者在事先定的出場條件成立之前就看得到它快到了。

- `own_conditions` 加欄位 `progress_json`：`{ at: 訊號日, basis: 'XBRL' | 'PRESS', period: 季末日, values: [最近幾季的數值，新到舊], level: 門檻, streak: 已連續幾季符合, need: 要連續幾季 }`。
- 什麼時候寫：新的 10-Q／10-K 出現、程式比對財報類條件時（`ownXbrlConditions`），以及財報新聞稿擷取成功時（§1.11）。對 `ACTIVE` 與 `PROPOSED` 的財報類條件都算，不只在成立時。
- 持股頁在條件旁顯示：`最新一季 71.2%（門檻 70%）；已連續 1／2 季`。畫成條由 T34 決定。
- 只有「要連續 N 季（N ≥ 2）、已經 N−1 季」的你定的條件列進「要看的事」（`COND_NEAR`）。不定「差幾個百分點算接近」：每種指標要各定一個，沒有依據。

#### 3.6.3 部位大小

不開審查（審查只能判斷前提，不能判斷部位大小），只列一行。併進計畫 T35（集中度檢查）。

- 條件：這檔自選的市值占總資產 ≥ 標準比重的 2 倍，而且還沒到單檔上限（15%，到了由 F10 處理）。
- `OwnMeta.sizeFlag: boolean`：往上越過 2 倍時設成 true 並列一次（`SIZE_2X`）；跌回 1.5 倍以下設回 false。
- 討論包的例行情境多一句（已寫進 §1.7）。

#### 3.6.4 審查失敗的告警

排程之下，「很久沒有審查」只會來自失敗。比照每日掃描（§2.6）。

- 同一檔的審查（F24，任何觸發原因）**連續 2 次沒有結論** → 推告警（`kind: REVIEW_FAILED`）：`MU 的 AI 審查連續 2 次沒有結論（11-28 逾時、12-05 資料缺漏）。規則照常；下一次審查在 <原因>。`之後每多失敗一次再推一次，直到有一次跑完。
- 算失敗的：逾時、觸發失敗、整份退回、三票格式都不合格、資料缺漏。票數不一致不算失敗（它是跑完了的結果）。沒開成照舊每次都告警（現有的 `FLOW_ERROR`），也計入次數。
- 次數記在 `flow_state` 的 `review:fails:<代號>`（次數與每次的日期、原因）；跑完一次就歸零。
- **連續 3 次票數不一致** → 列進「要看的事」（`NO_CONSENSUS`）。次數記在 `review:splits:<代號>`，有一次三票一致就歸零。

#### 3.6.5 論點變動後的審查

寫完或改完論點，隔天就有每條前提的檢查結果，不用等到月底（使用者 2026-11-15 決定）。

- `POST /api/ops/own-thesis` 存檔時，前提有新增或撤下，或沿用編號但字改了（去掉空白與標點後不同；2026-11-16 使用者同意加，T40，§1.8）→ `OwnMeta.thesisReviewDue` 記訊號日。只改論點本文、只改前提的標點或空白、只勾選條件不算。
- 下一次每日第一次流程（`startOwnRuns`）：有 `thesisReviewDue` 的股票——今天已經因為別的原因開了審查，或 `thesisReviewAt` 在 30 個日曆天內 → 只清掉 `thesisReviewDue`（月底檢查點會把論點變動當成新證據，§3.7）；否則開一次審查，觸發原因 `THESIS`，`thesisReviewAt` 記今天，清掉 `thesisReviewDue`。
- 上限：每檔 30 個日曆天 1 次，不占提前審查的額度（§2.4）。
- 結論怎麼用：照 §1.9，和財報後、提前審查同一列。

### 3.7 定期審查的頻率：月底檢查點

使用者 2026-11-15 決定（改設計 §2.0、§2.2 的「F24 每月」）：**月報前一天不再每檔都審，有新證據才審**。理由：同一批文件重讀一次，結論不同就是雜訊，還多一次誤報的機會；有新申報的月份照審，所以第 2 章「漏標的事留給下一次審查」仍然成立。專業做法是每季加事件，但他們平常有分析師盯著；這裡月底檢查點就是那個人。

**有結論的審查**：三票一致（含一致選「不動」）。票數不一致、資料缺漏、不合格、逾時不算（和 §1.5 寫入條件的標準相同）。

**新證據**（函式 `newEvidence(file, filings)`，回傳原因的清單；相對於這檔最近一次有結論的審查）：

| 原因 | 定義 |
|---|---|
| `NEVER` | 這份論點檔還沒有過有結論的審查 |
| `FILING` | 有申報日比那次審查的決策日晚的 8-K、10-Q、10-K（含修正） |
| `EVENT` | `sec_events` 有建立時間比那次審查晚的列（任何狀態；來源是 `PRICE` 的不算） |
| `THESIS` | 論點或前提改過（`thesis.version` 和那次審查證據包記下的不同），或那次審查之後有條件的變動（log 的 `CONDITION`） |
| `STALE` | 距那次審查的決策日滿 100 個日曆天 |
| `UNKNOWN` | 申報清單抓不到。當成有新證據，照審（審查自己會標資料缺漏，並計入 §3.6.4 的次數） |

新聞標題不算（不能當引用，§1.6）。慢規則有還沒列進清單的減半或加回也不算（減半有 F7；加回看的是既有的結論，§3.4）。

**月報前一天**（`startOwnRuns`）：今天還沒有因為別的原因開審查的自選股，逐檔算 `newEvidence`。

- 有任何一項 → 開審查（觸發原因照舊叫 `MONTHLY`）。證據包的 `rule.detail` 記下原因清單與當時的 `thesisVersion`。
- 一項都沒有 → 不開。紀錄寫 `MU：11-06 的審查之後沒有新的申報、事件或論點變動，這個月不審查`；`OwnMeta.reviewSkip` 記 `{ month, since }`，持股頁顯示 `這個月沒有新證據，沿用 11-06 的審查`。
- 月報用什麼：`aiTier` 與記著等月報的建議照舊（§1.9）；沒審的月份就是上一次的。

不變的：財報後的審查、提前審查（§2.4）、你定的「重新審查」條件觸發的審查、論點變動後的審查（§3.6.5）。§2.4 的「月審在接下來 3 個交易日內 → 留給月審」照舊成立：那筆事件本身就是新證據。

已知的代價：提高到 125%（F23）只在有審查的時候評估，安靜的月份可能晚一兩個月才提，接受。

估計一年跳過三到五成的月份（大型股一年約 8～15 份 8-K；沒有量過）。上線後從紀錄看實際比例。

## 4. AI 配合的通用規則

從第 1～3 章抽出不限於自選股的結論（使用者 2026-11-15 同意）。這一章沒有新的決定，都是前面同意過的結論換個寫法。

**怎麼用**：計畫的 T21（動能）、T22（核心）拿它當檢查表。每一條回答下面其中一種，寫進各自的設計文件：

- **適用，現況符合**：附程式位置。
- **適用，現況不符合**：附位置與要怎麼改；要改已決定的設計的，標出來請使用者決定。
- **不適用**：附理由（例如動能沒有論點檔、使用者不寫前提）。
