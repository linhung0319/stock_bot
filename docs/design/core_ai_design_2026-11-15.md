# 核心：三層配合的設計（2026-11-15）

> 狀態：使用者 2026-11-15 同意（計畫 T22，全部照建議）；還沒實作。
> 依據：`docs/plan/thesis_plan_2026-11-15.md`（稱呼、已經決定的方向十一點）、`own_thesis_design_2026-11-15.md` 第 4 章的通用規則 G1～G25、`design_v2_momentum_2026-11-07.md` §2.0、§2.1、§2.1.1、§2.3.1、§2.5、§4.4、§10 第 12、16、34 點、`ai_layer_design_2026-11-08.md` §3.3、F5／F6 與 F10～F13 卡片、§8.1、§9.2、`docs/test-records/` 的 B-5、B-6、B-7、`usage_walkthrough` §5。
> 和舊文件的關係：崩盤規則的 AI 檢視（F5／F6）的排程、顯示、影子紀錄、每月評語、總經資料不足時的行為，以及崩盤項目「這次不做」之後、月報暫停後重算、啟動期間核心怎麼收錢，**這份和 `design_v2`、`ai_layer_design` 的卡片不同時，以這份為準**。沒提到的照舊。
> 不動的：崩盤規則本身（每月換股日看 VOO 前一日收盤對 200 日均線、核心一半換現金、動能減半、回到均線之上恢復；自選桶不受影響）；入金出金的分配順序；單檔上限與跨桶上限 15%→10%；AI 的權限（只說明＋影子紀錄，不能否決或延後；LINE 只附一行「AI 檢視：照做／延後」）；三桶比例是風險預算、不為比例下單。
> 讀者：之後做實作的工作階段。檔案位置是 2026-11-15 的。
> 稱呼：L0 = 規則層；L2 = 重 AI（三票）。核心沒有 L1 的 AI（§3.9 拿掉每月評語之後）。「檢視」指崩盤規則的 AI 檢視（`CRASH_REVIEW`）。「切換」指崩盤規則啟動或解除。「訊號日」指當月最後一個交易日（月報用它的收盤）。
> 檢視的結果分三種：**跑完、有意見**（`Outcome.status` 是 `AGREED`，三票都是 `FOLLOW` 或都是 `DELAY`）；**跑完、沒有意見**（`SPLIT` 票數不一致，或 `INSUFFICIENT` 三票都是證據不足）；**沒有結論**（`TIMEOUT`、`NO_RESULT`、`INVALID`）。只有第三種會重開。

背景數字：2000–2026 崩盤規則啟動 17 次、解除 17 次，一年約 1.3 個切換項目，每次動到帳戶 25～38%。17 次啟動裡 3 次是真空頭、13 次買回更貴（`ai_layer_design` §3.3）。這份設計的方向：規則照舊；AI 留在說明；把「切換那幾次」的檢視做到一定出現、失敗看得出來、事後比得出成績；另外補上規則層缺的資料檢查與幾處和設計不合的地方。

## 3. 設計

### 3.1 檢視什麼時候開

`startCrashRuns` 改寫成「先列出需要檢視的切換，再決定開不開」。同一段邏輯在每天第一次流程（UTC 23:30，`startNew`）與第二次排程（UTC 01:30）各跑一次；第三次排程（UTC 03:30）不開新的執行（`own_thesis` §2.7）。

**需要檢視的切換**（函式 `crashNeeds(sc)`，回傳 0～2 筆 `{ month, direction, kind, basis }`）：

| `kind` | 什麼時候成立 | `month`、`direction` | `basis` |
|---|---|---|---|
| `PREVIEW`（預估） | 下一個交易日是當月最後一個交易日，而且 `crashDirection(acct, view)` 不是 `NONE` | `monthOfSignal(下一個交易日)`、`crashDirection` 的結果 | 今天（訊號日的前一天） |
| `MAKEUP`（已經切換） | 帳戶裡最新一份月報通知（`n.monthly` 有值、`kind` 是 `MONTHLY`）狀態是 `PENDING`，有沒被取消的 F5 或 F6 項目，而且那一項不是 §3.6 重列的 | 那份月報的 `monthly.input.month`、項目是 F5 → `ON`、F6 → `OFF` | 那份月報的訊號日（`n.date`） |

`MAKEUP` 不看今天是不是月底：月報晚一天才出（C3b）、或使用者隔天還沒回覆，都成立。

**對每一筆**，查這個月份＋方向的所有 `CRASH_REVIEW` 執行（`pack.rule.detail.month`、`direction`；不分 `kind`、不分 `as_of`），照順序：

| 情況 | 做法 |
|---|---|
| 有一筆跑完了（有意見或沒有意見） | 不開（修 C3a） |
| 有一筆還在等結果 | 不開 |
| 沒有結論的已經有 3 筆 | 不開（告警見下面） |
| 總經資料不足（§3.5） | 不開；照 §3.5 重抓、告警 |
| 其他 | 開。`pack.rule.detail` 記 `{ direction, month, kind, basis, try: 第幾次 }` |

- 題目（`crashPack` 的 `question`）在 `PREVIEW` 時前面加一句：`這是依 <basis> 的收盤預估的：訊號日（<下一個交易日>）收盤如果仍在均線的同一側，規則會切換。`
- 證據照舊（基準率表、儀表板、SPY 的新聞標題）。`MAKEUP` 用這個月份已經存的儀表板（`loadSnapshot(month)`），沒有才重算。
- 不會切換的月份不開任何 AI（§3.9），儀表板照樣算、照樣存（§3.5）。
- 月報前一天的儀表板在 `crashNeeds` 之前算（現有的 `buildSnapshot`＋`saveSnapshot`）。

**效果**：

| 情況 | 檢視 |
|---|---|
| 預估到、訊號日真的切換 | 前一天 23:30 開，24 小時後月報產生時讀結果。第一次沒有結論 → 01:30 重開（前一天的 01:30 仍看得到同一個 `PREVIEW`，因為最近一個已收盤的交易日沒變） |
| 沒預估到、切換了 | 月報產生後同一次流程補開（`MAKEUP`）；沒有結論 → 01:30 重開 |
| 預估會切換、沒切換 | 檢視留在紀錄。網站的 AI 紀錄在顯示時判斷：這個月份已經有月報、月報裡沒有同方向的 F5／F6 → 標 `預估會啟動（解除），訊號日沒有切換，沒有用到`。不存欄位 |
| 方向相反（前一天與訊號日之間帳戶的崩盤狀態被改回去，例如復原快照） | 方向比對不到，當成沒預估到，補開 |
| 月報晚出 | `MAKEUP` 照樣成立 |
| 月報暫停中（`monthlyBlocked`） | 還沒有月報通知，不開；重算出月報後下一次流程補開 |

**沒有結論的告警**（次數從這個月份＋方向的執行數出來，不另存）：

- 連續 2 次沒有結論 → 推告警（`kind: CRASH_REVIEW_FAILED`）：
  `崩盤規則啟動的 AI 檢視連續 2 次沒有結論（逾時、逾時）。規則照常，月報照規則出；下一次流程會再開一次。`
- 第 3 次也沒有結論 → 再推一次，最後一句換成 `已經停止重試。`
- 第一次失敗不推（和每日流程的做法一致）；現有的 `AI_TIMEOUT` 告警照舊。

### 3.2 結果怎麼回到月報

**月報產生前**（`flow.ts` `monthEndInputs`）：`crashOpinionFor` 改名 `crashReviewFor(db, month, direction)`，回傳這個月份＋方向的檢視狀態（下面的 `CrashReviewInfo`），不再只回傳三票一致的意見。`MonthlyContext.crashOpinion` 換成 `crashReview?: CrashReviewInfo`（舊通知的 `crashOpinion` 讀的時候當成 `{ state: 'OPINION', opinion }`）。

```
CrashReviewInfo = {
  state: 'OPINION' | 'NO_OPINION' | 'PENDING' | 'FAILED' | 'NO_DATA' | 'OFF',
  opinion?: '照做' | '延後',      // OPINION 才有
  votes?: string,                 // 「3 票一致」「照做 2、延後 1」「3 票都是證據不足」
  runId?: string,                 // 最近一筆執行（任何狀態）
  kind?: 'PREVIEW' | 'MAKEUP',
  basis?: string,                 // 檢視依哪一天的收盤
  fails?: string[],               // FAILED：每次的原因
  late?: boolean,                 // 使用者回覆之後才回來
  told?: boolean                  // LINE 已經帶過這個意見
}
```

| `state` | 什麼時候 |
|---|---|
| `OPINION` | 有一筆跑完、有意見 |
| `NO_OPINION` | 有一筆跑完、沒有意見（票數不一致或三票證據不足） |
| `PENDING` | 有一筆還在等結果 |
| `FAILED` | 只有沒有結論的執行（1～3 筆），而且沒有在跑的 |
| `NO_DATA` | 因為總經資料不足沒開（§3.5） |
| `OFF` | AI 層沒設定（`routineReady` 是 false）或沒有任何執行 |

`itemsFromPlan` 把它存在 F5／F6 項目的新欄位 `crashReview`；`aiLine` 只有 `OPINION` 時寫（`AI 檢視：照做`／`AI 檢視：延後`，和現在相同，LINE 讀的就是它）；`runIds` 只要有 `runId` 就帶（不限三票一致）。

**月報產生後**：新的 applier `applyCrashReview`（登記在 `APPLIERS[CRASH_REVIEW]`），每筆執行有結果時跑一次：

1. 找這個月份的月報通知裡同方向、沒被取消的 F5／F6 項目。找不到（月報還沒出、或這個月沒切換）→ 只標成已套用。
2. 項目的 `crashReview.state` 已經是 `OPINION` 或 `NO_OPINION` → 不動（G15）。
3. 否則用 `crashReviewFor` 重算，更新項目的 `crashReview`、`aiLine`、`runIds`，並重算通知的 `runIds`（`syncRunIds`）。

### 3.6 崩盤項目按「這次不做」之後

照設計 §2.3.1（策略類的差額下一份月報再列）做（修 C9；使用者 2026-11-15 確認）。效果上「這次不做」等於延後一個月：下個月規則還在同一個狀態就再列一次，已經翻回去就不用做。這和 AI 的「延後」同義，`ai_layer_design` §9.2 提過「跟著 AI 按這次不做等於從後門給了延後權」；§3.4 的紀錄就是用來看這件事。

### 3.7 月報暫停後重算

崩盤規則用訊號日的判斷，不用重算那天的（修 C10；使用者 2026-11-15 確認）。排名本來就是用訊號日的（`monthly.input.order`），崩盤規則比照。

- 均線算不出來時照 §3.10。
- `explain.ts` `crash()` 的文字用 `input.crash` 的日期與數字（`VOO 11-30 收盤 512.30，低於 200 日均線 520.11`），不用顯示當下的 view。

同樣的情況在依波動度減碼也有（重算時 `excessVolOf(view)` 用的是重算那天）。那是動能的範圍，這份不決定，列在「還沒決定的」給 T23。

### 3.8 啟動期間核心怎麼收錢

上線的清單改成和設計 §2.1 第 1 點、回測一致（修 C11；使用者 2026-11-15 確認）。只動 `composeWithCore`（上線的清單），不動 `planDay`（重放、回測）。

崩盤規則啟動中（`ctx.crash`）、清單做完有多的錢（`inv`）時：

| 這份清單 | 多的錢怎麼分 |
|---|---|
| 切換那一份（有 F5 項目，含重列的） | 照舊：一半買核心 ETF、一半放短債（核心整個重分成一半一半；設計 §10 的「崩盤規則切換時的現金」） |

- 錢不夠時照舊先用短債。
- 既有的情境測試裡，啟動期間、不是切換月的清單會變（買 VOO 的那一行變成買短債），照新行為更新並在 commit 說明。重放驗收不受影響。

### 3.10 核心 ETF 的資料檢查

規則層新增的檢查，崩盤規則本身不動（修 C12）。

**純函式** `coreDataCheck(view, core, bench, bond)`（新檔 `worker/src/data/coreCheck.ts`；`view.close` 是還原權值，配息不會造成差距），回傳問題的清單：

| 代碼 | 條件 | 意思 |
|---|---|---|
| `MA_SHORT` | 核心 ETF 到今天為止不滿 200 根有效的收盤（`sma` 回 NaN） | 均線算不出來 |
| `DAY_GAP` | 核心 ETF 與基準（SPY）最近一天的報酬差超過 1 個百分點 | 最新一根可能有錯 |
| `MA_GAP` | 兩者「收盤 ÷ 200 日均線 − 1」的差超過 1.5 個百分點 | 歷史資料可能有錯（少調整一次配息或分割） |
| `BOND_JUMP` | 短債 ETF 最近一天的報酬絕對值超過 1% | 短債的價格可能有錯（只影響換算股數） |
| `NO_BENCH` | 基準沒有今天的價格 | 這次沒辦法比（只記在流程紀錄，不告警） |

常數 `CORE_CHECK = { dayGap: 0.01, maGap: 0.015, bondJump: 0.01 }`。VOO 和 SPY 追蹤同一個指數，平常日報酬差在 0.1 個百分點以內；門檻取寬，是為了只抓資料錯誤。SPY 和 VOO 來自同一個來源（Yahoo）：這個檢查抓得到單一代號的錯，抓不到整個來源的錯。

**每天**（`processSessions` 每個交易日）：有 `DAY_GAP`、`MA_GAP`、`BOND_JUMP`、`MA_SHORT` → 推告警（`kind: CORE_PRICE_SUSPECT`；同一天同樣的文字不重複，現有的去重）：
`VOO 的價格和 SPY 對不上：11-30 日報酬 VOO -3.10%、SPY +0.20%（平常差不到 0.1 個百分點），可能是資料錯誤。崩盤規則照這個價格判斷；月報日之前請到券商核對 VOO 的收盤價。`
（`MA_GAP`：`…相對 200 日均線 VOO -1.2%、SPY +0.9%…`；`BOND_JUMP`：`SGOV 一天變動 2.3%，可能是資料錯誤；清單裡短債的股數請核對。`）
每日訊號照常產生，不擋流程。

**月報訊號日**：檢查的結果存進 `MonthlyContext.coreCheck?: string[]`（代碼）。

- 這個月崩盤規則切換、而且有 `DAY_GAP` 或 `MA_GAP` → F5／F6 項目的 `note`：`VOO 的價格和 SPY 對不上（日報酬 VOO -3.10%、SPY +0.20%），下單前請核對券商顯示的 VOO 收盤價；對不上就選「這次不做」並寫理由。`LINE 的月報在下單清單後面加一行：`注意：VOO 的價格資料可能有誤，下單前先看網站。`
- 月報照規則出，不延後、不改判斷（使用者 2026-11-15 決定；不採「當天不產生訊號」：Yahoo 的錯不修正會一直卡住，而且使用者下單前本來就會在券商看到價格）。

**均線算不出來**（`MA_SHORT`）：`report.ts` 與 `crashAi.ts` `crashDirection` 改用新函式 `crashDecision(close, i, prev)` → `{ below, ok }`：`sma` 是 NaN 時 `below = prev`（維持原狀態）、`ok = false`。`crashRuleOn`（重放用）不動。`ok` 是 false 的月報另外推告警（`kind: CORE_MA_MISSING`）：
`VOO 的 200 日均線算不出來（只有 143 根日線）。崩盤規則這個月維持原狀態（啟動中）。`

### 3.11 入金、出金、改比例的說明

三桶比例由誰看：規則在入金出金時看（分配就是拉回，設計 §2.1.1）；平常不為比例下單，也不加提醒（使用者 2026-11-15 決定）。只補清單上的說明，都在網站的清單頁，不進 LINE。

- **入金、出金、改比例的清單**（`explain.ts` 的 F11、F12、F13）：`facts` 加一列 `做完之後`，值：`自選 23.1%（預算 20%）、動能 28.4%（30%）、核心 48.5%（50%）`。純函式 `bucketSharesAfter(acct, view, composed)`：把清單（`n.preview`，回覆後用 `n.composed`）照訊號日價格套到目前的持股上，算三桶占總資產的比例（出金先扣掉要轉出的金額）。
- **改比例的相對回撤狀態**（補做設計 §2.1 第 7 點；修 C13）：Strategy 的比例有變時，F13 的 `facts` 加一列 `動能相對大盤`，值由策略檢討的狀態（`flow_state` 的 `strategyReview`：`rel`、`peak`、`eventStart`）算：在落後事件中 → `比高點落後 32%（這次從 2025-03-10 開始）`；不在 → `比高點落後 4%，不在落後事件中`。原本那句固定提醒留著。示範模式沒有這個狀態，不顯示。
- **改比例的影子紀錄**：`changeRatio` 產生通知時不再寫那筆 0 股的紀錄。回覆時（`respond`）對 F13 項目，照合成後的清單（`n.composed.merged`，含核心）每一檔寫一筆：`f: 'F13'`、`rule: 0`（沒改的話不動）、`ai: null`、`actual`：那一檔的股數、`choice: 'RATIO'`、`note`：`20% / 30% / 50% → 20% / 0% / 80%`。這樣現有的影子算法（1、3、6 個月）就算得出「如果沒改」。取消改比例時的作廢記號照舊。

## 4. 不做的與理由

| 項目 | 理由 |
|---|---|
| 讓 AI 否決或延後崩盤規則；LINE 多放票數或理由 | 已決定（設計 §10 第 12 點）。這份沒有改 |
| 預估時加緩衝帶（VOO 離均線很近就先開檢視） | 沒預估到的情況已經由補開＋等到 01:30 再推處理，當天早上就有結果；緩衝帶每年會多開約一次用不到的完整檢視 |
| 不會切換的月份的 AI 評語 | §3.9 |
| 核心太小、三桶偏離太大的提醒 | 比例是風險預算不是目標（設計 §2.1 第 4 點）；帳戶頁已經有各桶占比對預算；B-6 測過大額出金不會把核心掏空；看了也沒有系統會做的動作 |
| VOO 的第二個價格來源 | §3.10 的 SPY 對照不用多抓資料就能抓到單一代號的錯；整個來源出錯時現有的「價格不是最新」檢查多半會先擋下 |
| ALFRED vintage、每天自存高收益債利差（`ai_layer_design` F5／F6 卡片） | 上線時決策日就是今天，FRED 現在的值就是當時看得到的值；vintage 只有回測 AI 才用得到，而檢視的權限不靠回測。「真空頭開始時的值」是修正後的數字，網站已經標明 |
| AI 對入金、出金、改比例表示意見 | `ai_layer_design` F11～F13 卡片已決定；改比例是使用者的偏好，AI 容易順著說 |
| 減少來回的規則改動（緩衝、連續兩個月確認、分批） | 回測凍結；設計 §10 第 16 點把它列成低優先的回測題目 |
| 對不上時當天不產生訊號 | §3.10 |

專業做法的對照（憑設計時的了解，沒有另外查證；`ai_layer_design` §8.1 的文獻是當時查的）：用均線做大盤減碼的系統化策略，訊號後的人工覆核通常只查資料與執行（價格來源交叉核對、配息與分割有沒有調整、訊號日對不對）；「這次該不該跟」通常不做裁量覆核，因為規則的價值在事先承諾，真的要覆蓋會留紀錄並事後檢討覆蓋的成績；訊號觸發時附一頁總經與信用的情境說明給決策者知情，不改訊號；現金部位放短天期國庫券；比例偏離多用現金流再平衡。這份設計和它一致：AI 留在說明（§3.1～§3.3），新增的是資料檢查（§3.10）與覆蓋的紀錄（§3.4、§3.6）。
