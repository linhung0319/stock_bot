## 1. 網頁證據

### 1.1 原則

> **2026-11-20 同一天改過一次**（使用者提出並同意）：第一版是「審查之前先開一個搜尋任務，抓到的全部放進證據包」。使用者的疑慮：他要的是 AI **讀了現有的證據、想查證時**才去找；先搜再審的話，找的人沒讀過申報、抓到的不管有沒有用都塞給每個子代理、讀到一半也不能追問。疑慮成立，改成下面的「讀完再找」。保留第一版的只有一件：原文要經過 Worker。

1. **AI 讀完證據包再決定要找什麼。** 審查裡的分析師可以用 WebSearch 找網址，也可以從證據包附的目錄挑文件（§1.2）。
2. **原文一律經過 Worker。** 分析師把要讀的網址送給 Worker 的「取文件」端點（§1.5），Worker 檢查清單、當場抓、存快照、加進這次執行的證據包、把全文回給它。AI 不用 WebFetch、不用 curl 讀別的網站；雲端環境照舊只允許 Worker，不用改。
3. **三票照舊不上網、不取文件**：多方、空方、三票經理讀的是「原本的證據包＋分析師取回的文件」，三票看的是同一份資料（G14）。`check.ts` 的逐字引用檢查不改，比對的是 Worker 自己抓的字。
4. **抓得到 ≠ 可信**：來源分級（§1.3），權限跟著級別走（§1.6）。
5. 抓不到的來源不硬抓、不換方法繞過（不偽裝登入、不用第三方的全文代理）。搜尋結果的標題只是線索，不是證據。

為什麼不讓排程自己讀網頁（雲端環境加允許網域、WebFetch）：WebFetch 給模型的是另一個模型整理過的字（§0.3），引用對不上原文，網站上也沒有快照可以對。

| `MEDIA` 媒體 | 有編輯、會寫明消息來源的產業媒體 | `techpowerup.com`。~~`datacenterdynamics.com`~~（M1 兩篇都 403）、~~`businesskorea.co.kr`~~（M1 兩篇都內文太短）拿掉 |
| （不列入） | 評論、預測、社群：`fool.com`、`stocktwits.com`、`247wallst.com`、`tikr.com`、`seekingalpha.com` 等（程式裡的 `WEB_EXCLUDED`） | 抓得到也不抓，**每檔的 `domains` 也加不進來**；標題照舊只當初判 |

- **誰維護**：使用者。改清單＝改這個檔案、commit、部署（和改規則一樣走 git，有紀錄）。
- **加網域的流程**：取文件的端點每次把「不在清單而被拒絕的網址」記下來（`web_docs` 的 `status = 'NOT_LISTED'`，只存網址與標題）；運作統計列出最近 90 天被略過最多的網域與抓取失敗的網域。使用者看了決定要不要加；在 repo 開 Claude Code 說「把 X 加進清單」即可（先用 `/admin/web/test` 探一次文章頁，抓不到就不加）。
- **被擋的大型媒體**（Reuters、Bloomberg、WSJ…）不列入：列了也抓不到。它們的標題照舊出現在 RSS 與搜尋結果裡，當初判。

**每檔的來源**（跟著論點檔，存在 `OwnMeta.webSources`；使用者同意才生效，G16）：

| 欄位 | 內容 | 上限 |
|---|---|---|
| `peers` | 同業：`{ name, edgar?: 代號, yahoo?: Yahoo 代號 }`。有 `edgar` 的走 S1，有 `yahoo` 的走 S2 | 4 家 |
| `domains` | 這檔專用的一手網域（公司與同業的新聞室、投資人關係網站），級別一律 `PRIMARY` | 6 個 |

來源由草稿提出（第 2 章）或使用者在編輯論點頁自己填；存檔前程式先探一次（抓不到的標出來，仍可存，但寫明「目前抓不到」，G24）。只有預設前提的股票沒有 `webSources`，也就沒有網頁證據（它的三條預設前提本來就是申報與財報查得到的）。

### 1.4 抓取與快照

函式 `fetchWebDoc(fetcher, url, now)`（`worker/src/data/webDoc.ts`，從量測用的 `webProbe.ts` 改）與新表 `web_docs`。

**抓取的規則**：

- 只收 `https`、公開主機（`safeWebUrl`）；網域要在共用清單或這檔的 `domains` 裡；`NAMED` 的路徑限制照清單的 `note`。
- 逾時 15 秒；最多讀 2 MB；跟著轉址，但**轉址後的主機也要在清單內**，否則當成失敗。
- 只收 HTML。PDF 與其他格式 → `status = 'UNSUPPORTED'`（不解析 PDF）。
- 內文（超過 200 字的段落合計）少於 1,500 字 → `status = 'THIN'`（多半是付費牆、同意頁、要 JavaScript）。
- **發布日**：`findPublished`（meta、JSON-LD 的 `datePublished`、`<time datetime>`）；都沒有時（T51，M1：一手新聞室多半如此）用**第一段內文之前 15 行內、單獨一行的日期**（`findPublishedInText`，可以帶 Published／Posted／Date 與後面的時間；前一行是 Updated／Modified 的不算；`published_from = 'text'`）。RSS 來的另有 RSS 的發布時間：兩個都有而且差超過 3 天 → 用比較晚的那個，並標 `date_conflict`。都沒有 → `published = null`。量測端點 `/admin/web/test` 用同一套認法。
- **快照從標題開始**（T51）：快照的文字從第一段內文之前、最靠近它的標題那一行開始（og:title、`<h1>`、`<title>` 以及它們用「 | 」「 - 」切開的每一段），去掉前面的選單；找不到就從頭。`title` 存的也是那一行（沒有網站名稱）。
- 轉址一次一次跟（最多 5 次），**每一站**都要在清單內（含 `paths`）才繼續抓，所以不會去碰清單外的主機。
- 同一個網站一次執行最多抓 4 篇；失敗不重試。
- 快照存的文字最多 30,000 字（開頭起算）；給 AI 的長度另有上限（§1.5）。截掉的都標記（G23）。

**`web_docs`**（只增加；市場資料類，上線後留著）：

| 欄位 | 說明 |
|---|---|
| `id` | `web:<網址的 SHA-256 前 16 碼>`，也是證據包的 `source_id` |
| `url`、`final_url`、`domain`、`tier` | |
| `ticker`、`file_id` | 為哪一檔抓的（同一個網址為兩檔各抓一次時各存一列） |
| `via` | `MENU`（從目錄挑的）／`SEARCH`（分析師找到的網址）／`MANUAL`（使用者在網站貼的網址，第二階段才做） |
| `ref` | 哪一次執行要的（`run_id`） |
| `premise_id`、`cond_id` | 分析師說它和哪一條有關（可以是空的；只是線索） |
| `title`、`published`、`published_from`、`date_conflict` | |
| `fetched_at`、`session` | 抓取時間、訊號日 |
| `status` | `OK`／`THIN`／`BLOCKED`（HTTP 4xx、5xx）／`UNSUPPORTED`／`NOT_LISTED`／`NO_DATE`／`TOO_OLD`／`ERROR` |
| `http_status`、`chars`、`truncated`、`text_sha256` | |
| `text` | 純文字（只有 `OK` 的存） |
| `row_id`、`error`、`used_by`（T51 加） | `row_id` 是每一列的編號（`id` 不唯一：同一個網址為兩檔各存一列、沒抓成的每次各一列）；`error` 是沒抓成的原因（`NOT_LISTED` 另外寫 `EXCLUDED` 不列入或 `PATH` 路徑不收）；`used_by` 是第一次把它放進證據包的執行（T52 的端點寫），下面「保留」用 |

- **不重抓**：同一檔同一個網址已經有 `OK` 的列就用那一列（文章改版不追；被引用的就是當時抓到的那一版）。網址先整理（去掉 `#` 與 `utm_` 參數）再算 `id`。資料庫用部分唯一索引保證同一檔同一個 `id` 最多一列有全文的 `OK`。沒抓成的不算，下次照樣再試。
- 同一個網站一次執行抓滿 4 篇之後，`fetchWebDoc` 回 `LIMIT`、不去抓、不寫 `web_docs`（由端點記在執行紀錄，§1.5）。
- `fetchWebDoc` 可以帶決策日與 `notBefore`：發布日晚於決策日 → `ERROR`、早於 `notBefore` → `TOO_OLD`（§1.5 的規則；`notBefore` 由 T52 的端點照上次審查算）。
- **repo 是公開的**：快照只在 D1。匯出（`EXPORT_TABLES` 加 `web_docs`）落在 `records/`，不進 git。
- **網站怎麼顯示**：審查紀錄頁列出這次分析師取回的文件（標題、來源、級別、發布日、抓取日、連結）與被引用的片段；不提供整篇全文的頁面（著作權；要看全文點連結）。抓不到與不在清單的網址列在下面「沒有讀到的」，寫原因。
- **保留**：被任何一次審查的證據包用過的永久留著（之後要能對引用）；沒被用過的 `OK` 文件 180 天後刪掉 `text`、留列（`purgeUnusedWebText`；T51 只寫了函式，接進每日流程等 T52 開始寫 `used_by` 再接，否則會清掉被用過的）。清掉全文的列不再擋重抓。

**怎麼進證據包**：不預先放。分析師要了才取（§1.5），取回的文件記在那次執行的 `added_docs`。`PackDoc` 的樣子：`kind: 'web'`（新的種類），`source_id` = `web_docs.id`，`date` = 發布日，`title` 寫「〔網頁｜<級別的白話>｜<label>〕<標題>（發布 <日期>，<抓取日> 抓）」，`url`、`fetched_at` 照填。**認不出發布日的取不到**（`check.ts` 要日期 ≤ 決策日；拿抓取日充當會讓三年前的舊文變成「新證據」）。

### 1.5 取文件（Worker 的端點）與分析師的找資料步驟

**端點** `POST /ai/task/<任務編號>/docs`（和取證據包、送回結果同一把金鑰；雲端排程本來就只連得到 Worker）：

```json
{ "want": [ { "menu": "M1", "for": "P5", "why": "一句" },
            { "url": "https://www.trendforce.com/presscenter/news/…", "title": "搜尋結果的標題", "for": "C12", "why": "一句" } ] }
```

回應：

```json
{ "docs": [ { "source_id": "web:3fa9…", "kind": "web", "tier": "NAMED", "date": "2026-09-30", "title": "…", "text": "…", "truncated": false } ],
  "refused": [ { "url": "…", "reason": "NOT_LISTED | BLOCKED | THIN | UNSUPPORTED | NO_DATE | TOO_OLD | LIMIT | ERROR" } ],
  "left": { "docs": 5, "chars": 41000 } }
```

| 規則 | 內容 |
|---|---|
| 哪些任務可以用 | 定期審查（`OWN_REVIEW`）、減半檢視（F7）、論點草稿（`OWN_DRAFT`）。其他功能的任務呼叫 → 403 |
| 什麼時候可以用 | 任務已經取過證據包、還沒送回結果、還沒逾時。之後呼叫 → 410 |
| 每次執行的上限 | 最多取回 **8 份**、合計 **60,000 字**；最多呼叫 6 次。超過的回 `LIMIT`（G23：記在執行紀錄裡） |
| 每份的長度 | 網頁取開頭 12,000 字；同業申報取開頭 15,000 字（財報新聞稿的重點在前段，後面的報表我們不比對）。截掉的標 `truncated`，標題寫明 |
| 網頁的條件 | §1.4 的抓取規則；網域要在清單或這檔的 `domains`；要認得出發布日，而且發布日 ≤ 決策日（`NO_DATE`、之後的當成 `ERROR`）；發布日早於「上次有結論的審查」超過 120 天 → `TOO_OLD`（舊文不能當新證據；沒有上一次審查時算最近 365 天） |
| 存在哪裡 | 每一筆（含被拒絕的）寫進 `web_docs`（§1.4）；取回的文件另外記在這次執行的 `ai_runs.added_docs`（`source_id`、誰要的、`for`、`why`）。表決時 `check.ts` 比對的原文＝證據包的文件＋`added_docs` 指到的文件 |
| 證據包的雜湊 | 原本的 `pack_hash` 不變（它是程式準備的那一份）；另存 `added_hash`（取回的文件的雜湊） |
| 同一個網址 | 這檔已經有 `OK` 的快照 → 直接回那一份，不重抓 |

**誰可以找**：只有分析師（審查與減半檢視）或研究員（草稿）那一個子代理。`run.md` 第一句的「不要上網找資料」改成：「只有功能的 prompt 指定的那個角色可以用 WebSearch；任何角色都不要用 WebFetch 或 curl 讀 Worker 以外的網址，要讀原文一律向 Worker 取」。多方、空方、三票經理的指示照舊寫明不上網、不取文件。

**分析師的步驟**（寫進 `own_review_v3`；prompt 這次不動，實作時寫）：

1. 讀完證據包，列出**要查的問題**（最多 6 個）：哪一條前提或條件，現有的文件為什麼不夠判斷，什麼樣的資料可以顯示它成立、什麼樣的可以顯示它不成立（**兩個方向都要找**，`ai_layer` §2.6）。沒有要查的就跳過，照現在的方式寫摘要。
2. 先看目錄有沒有對得上的（同業申報、清單內的 RSS 連結）；不夠再用 WebSearch（最多 6 次），優先挑證據包裡列出的清單內網域。
3. 向 Worker 取文件。被拒絕的照實記下原因，不換別的方法讀。讀了之後可以再找、再取，直到上限。
4. 摘要多一段「這次另外找的資料」：每個問題找了什麼、取到哪幾份、哪些沒取到與原因。**搜尋結果的標題與沒取到全文的網頁，只能寫成「有這樣的標題」，不能當事實。**
5. 送回的結果多一個 `lookups`：`{ "questions": […], "queries": […], "wanted": [{ url 或 menu, for, why, got: source_id 或拒絕的原因 }] }`，存進執行紀錄，網站的審查紀錄頁列出來（「AI 這次另外找了什麼、為什麼」）。

**哪些前提與條件算「需要外部資料」**（§1.7 的時機與「要看的事」用；分析師自己不受這張表限制，任何一條覺得要查都可以查）：

- 你的前提（不含系統預設）最近一次檢查是三票一致的「證據不足」（`PREMISE_NO_DATA`，T47）；
- 還沒被檢查過的你的前提；
- 你定的條件裡指名了網頁來源的（§1.6）。

**失敗**（G22）：端點出錯或全部被拒絕 → 分析師照原本的證據包寫摘要，審查照常；`lookups` 留下紀錄，網站寫「想找 N 份，取到 0 份：<原因>」，和「沒有要找的」分得出來。

**安全**：分析師會讀到網頁內文、再決定下一步找什麼，被網頁裡的字帶偏的可能比「只送回網址清單」高。後果的上限：Worker 只抓清單內的 https 網址、每次執行 8 份；取回的文件和申報一樣是資料（`run.md` 第 4 步）；三票不上網。證據包沒有金額與股數（只有比重），就算被誘導把內容塞進要取的網址，也只送得到清單內的網域。

### 1.6 網頁證據能觸發什麼（X2、X3；使用者 2026-11-20 選定）

`reviewDecision` 判「不成立的前提」（`own_thesis_design` §1.6 第 1 點）與「你定的條件由審查確認成立」（第 2 點）時，合格的引用來源從「`filing` 或 `xbrl`」放寬成下表。三票一致、同一條前提（G14）、通過逐字檢查，這些都不變。

| 引用來自 | 判前提不成立（→ 乙類，預設不動） | 確認你定的條件成立（→ 甲類，預設照當時的決定） |
|---|---|---|
| 自己或同業的申報、財報表（`filing`、`xbrl`） | 可以（照舊） | 可以（照舊） |
| 網頁，`PRIMARY` 或 `NAMED` | 可以 | **只有條件指名了這個網域時**可以 |
| 網頁，`MEDIA` | 可以，但三票各自至少要引用 **2 份不同網域**的文件（單一媒體的一篇報導不夠） | 不行（除非條件指名了它） |
| 新聞標題、搜尋結果的標題、不在清單的網頁、認不出日期的網頁 | 不行（照舊只是初判） | 不行 |

- **條件怎麼「指名來源」**：事件類條件的 `check.confirm_by` 多一種寫法 `web:<網域>`（例如 `["web:trendforce.com"]`）。改寫（`own_check`）時 AI 可以提出，**使用者勾選條件時看得到並可以改**；網域要在清單或這檔的 `domains` 裡，否則擋下。`confirmMode` 多一種結果：`confirm_by` 有 `web:` 的 → `REVIEW_ONLY`，顯示「審查時用 <來源> 的網頁檢查」（G24：寫的就是實際在做的事）。成立時 `met_basis = 'WEB_VOTE'`。
- **不每天監測**：網頁來源的條件只在審查時檢查（審查前會先跑搜尋與 RSS）。要每天盯網頁等於每天多一次雲端執行，不做。
- **通知的文字**（其餘照 `own_thesis_design` §1.10）：
  - 乙類的理由：`依據：TrendForce 2026-09-30 的新聞稿（網頁；引用與連結在網站）。你沒有為這件事定過出場條件，由你決定。`
  - 甲類的理由（`WEB_VOTE`）：`TrendForce 2026-09-30 的新聞稿，3 票確認（網頁；引用與連結在網站）`
  - 依據裡同時有申報與網頁時，申報寫在前面。
- **頻率上限不變**：乙類每檔 30 天 1 則；甲類不設上限。靜默期照舊（同一條前提）。
- `RAISE`（提高到 125%）與「回到標準」不能只靠網頁證據：每條前提 `HOLDS` 的引用裡至少要有一條來自申報或財報表（往上加碼的門檻不放寬）。

### 1.7 什麼時候會去找

找資料不是另一次執行，是審查的一個步驟。所以問題變成「什麼時候開審查」：

| 時機 | 做法 |
|---|---|
| **月底檢查點**（`own_thesis_design` §3.7：有新證據才審） | `newEvidence` 多兩個原因，都由程式判斷：`PEER`（同業有申報日比上次審查晚的 8-K Item 2.02）；`WEB_DUE`（這檔有「需要外部資料」的前提或條件，而且距上次有結論的審查滿 25 天）。也就是：**有這種前提的股票每個月都審**，因為不去找就不會知道有沒有新東西 |
| 財報後的審查、提前審查、你定的「重新審查」條件、論點變動後的審查 | 照舊開；分析師照 §1.5 可以找。不多等任何一次排程（G7） |
| **個股自身大跌、沒有新申報可檢查**（原本只列進「要看的事」的 `PRICE_NO_FILING`） | 這檔有論點（不是只有預設前提）→ 改成照 `own_thesis_design` §2.4 開提前審查（同一個 30 天上限），題目寫明「沒有新的申報，請分析師找有沒有清單內來源的消息」。只有預設前提的照舊列 `PRICE_NO_FILING` |
| 減半檢視（F7） | 照舊在觸發那天跑，分析師可以找。推播時間的規則不變（§3.5：只等到固定的時間） |

沒有另外的搜尋上限：每次執行最多取 8 份，審查本身的頻率由原有的上限管（提前審查每檔 30 天 1 次等）。

### 1.8 哪些功能可以用（對照 G1～G25）

| 功能 | 用不用 | 理由與對應的規則 |
|---|---|---|
| 定期審查（F24） | **用**（分析師可以找） | 這是起因。G10：目錄由 `thesisFile` 組；G11：`newEvidence` 多 `PEER`、`WEB_DUE`；G12：改寫（§1.9）；G14：三票看同一份；G15、G19 不變 |

| 減半檢視（F7） | **用**（分析師可以找） | 「為什麼跌」正是最需要查證的時候；找資料是同一次執行裡的步驟，不多等一次排程。G1：減半通知的推播時間不變；G5：找來的文件用來檢查論點，不是替價格找理由 |

| 每日掃描（F18） | 不用 | 一票 Haiku 只分類申報與標題；加全文會讓每天的量變大，而它的輸出只是標記 |

| 崩盤檢視（F5／F6） | 不用 | 權限只有說明＋影子；輸入是總經序列 |
| 論點草稿（第 2 章） | **用**（研究員可以找） | 同一個端點、同一個上限 |

### 1.9 通用規則怎麼改

- **G12 改寫**：「會改變下單的結論，引用要來自**程式自己抓、存了快照的原文**：申報、財報表，或清單內網域、認得出發布日的網頁全文（級別決定能做什麼，`web_evidence_design` §1.6）。標題、搜尋結果、AI 的摘要只能當初判。」
- **新增 G26**：「AI 可以決定要找什麼，但不直接讀網路上的原文：原文由程式抓、存快照、加進證據包再給它。只有一個角色能找，表決的每一票看同一份資料。」
- G9 的延伸：「有沒有新東西值得審」由程式判斷（同業有新申報、滿 25 天），不另外開一次 AI 去問。
- 「已經決定的方向」第 9 點改成：「不做：**表決的三票**上網；AI 直接讀網頁（原文一律經過 Worker）；AI 擋掉慢規則。」

### 1.11 不做的與理由

- **雲端排程自己讀網頁**（環境加允許網域、WebFetch 或 curl）：先不做，理由在 §1.1。**如果跑兩三個月後，運作統計顯示分析師想取的重要來源 Worker 一直抓不到**，再做第二階段：請使用者在環境加那幾個網域，實測 WebFetch 與 curl 讀不讀得到；讀得到的內容也只當**初判**（寫進摘要、列進「要看的事」），不能當引用——它是模型轉述的，沒有快照可以對。使用者 2026-11-20 表示可以接受整理過的內容；這裡的意思是它可以用來提醒，但不讓它直接變成賣出建議的依據。
- **審查之前先開一次搜尋、把抓到的全部放進證據包**（這份文件的第一版）：拿掉，理由在 §1.1 開頭。
- **三票各自找資料**：不做。三票看的資料不同，「一致」就不是對同一份證據的一致。
- **connector 當證據來源**：內容只存在雲端那一次執行裡，Worker 拿不到、對不了引用；免費等級的資料商多半只有標題與摘要。排程裡的 connector 維持全部移除（帳號之後新接的 connector 預設會被帶進排程，要再確認）。
- **付費新聞**：不變（`design_v2` §10 第 23 點）。
- **解析 PDF**（很多亞洲公司的財報新聞稿只有 PDF）：Worker 裡做不划算；先看運作統計有多少 `UNSUPPORTED` 再說。
- **使用者自己貼網址當證據**（`via = 'MANUAL'`）：表先留欄位，畫面第二階段再做。

## 2. stock bot 草擬論點（X4；使用者 2026-11-20 選定）

### 2.1 定位

- **改掉的**：2026-11-15 的方案 B（論點只在 claude.ai 討論、stock bot 不寫論點）與「請 AI 草擬前提拿掉」。
- **沒有改的**：論點是使用者的（`own_thesis_design` §1.4）。草稿不是論點：**每一條都要使用者明白同意才生效**，沒有任何一條會自己變成前提或條件；審查不能改論點、不能新增前提，這一點也不變——草稿是另一個功能、只在使用者要的時候或新增自選時產生。
- **留著的第二條路**：討論包、貼回、`/thesis`（T48）、編輯論點頁的手寫，程式都不拆。想和 AI 爭辯的時候用那一條。
- 為什麼這次的草稿和 11-15 拿掉的那個不同：當時的草擬只有一票、只看這家公司的申報、題目寫死「使用者想加進自選但沒寫理由」（P7），寫出來的是通用句。這次有買進時的一句話、上一份論點檔、同業與產業的文件，而且輸出要帶「怎樣算不成立」與來源。品質仍然要看實際結果（§2.4 第 7 點的成績表）。

### 2.2 草稿任務（`OWN_DRAFT`）

| 項目 | 內容 |
|---|---|
| 白話名稱 | 草擬論點 |
| 等級與票數 | A2（只說明；使用者同意才有效果），**一份**，不是三票 |
| prompt | `ai/prompts/own_draft_v1.md` |
| 找資料 | 和審查同一套（§1.5）：研究員讀完證據包後可以用 WebSearch、向 Worker 取文件，同樣的上限。沒有另外的前置執行，使用者按了就是一次執行 |
| 證據包 | `thesisFile`（買進時的一句話、上一份論點檔、現行的前提與條件、事件、歷次審查與使用者的回應）、價格與規則狀態、XBRL 八季、最近一份 10-Q／10-K 的 MD&A、最近的 8-K、目錄（§1.2；還沒有同業時目錄只有這檔的 RSS）。**只放比重，不放金額與股數**（和討論包相同） |
| 流程（各用獨立的子代理） | ① 研究員（Sonnet）：讀證據包、找資料（§1.5）、寫事實摘要。之後的角色不上網。② **反方先寫**（Sonnet）：這家公司最可能讓持有者後悔的三件事，各附證據；以及「如果現在沒有持股，今天用這個價格會不會買」的反方答案。③ 正方（Sonnet）：持有的理由，必須回應反方的三件事。④ 主筆（Opus）：寫草稿 |
| 輸出（`payload`） | 見下 |

```json
{
  "thesis": "一段，300 字以內",
  "premises": [{
    "text": "…（200 字以內）",
    "keep_id": "P2 或 null（沿用現行的哪一條；沒改字才能寫）",
    "breaks_if": "什麼情況算不成立（要寫成查得到的事）",
    "checkable_by": "XBRL | FILING | PEER_FILING | WEB | NONE",
    "source_hint": "查得到的話，是哪個來源（例如 trendforce.com、SK 海力士的財報新聞稿）",
    "evidence_ids": ["E1"]
  }],
  "exits": [{ "text": "查得到的事", "action": "EXIT | HALF | REVIEW", "premise_index": 0, "evidence_ids": ["E2"] }],
  "sources": { "peers": [{ "name": "…", "edgar": "…", "yahoo": "…" }], "domains": ["…"] },
  "against": ["反方最強的三點，各一句，附 evidence_ids"],
  "would_buy_today": { "answer": "YES | NO | UNSURE", "why": "一句" },
  "not_checkable": ["寫不成查得到的事、但主筆認為重要的觀察，各一句"]
}
```

**程式檢查**（不過的整份退回、記錄、照 G22 告警，不給使用者半份草稿）：

- 外殼與 `evidence` 照 `check.ts`（引用逐字出自證據包）。
- 前提 3～5 條、出場條件 2～6 條；字數上限同 `parseThesisBlock`。
- 每一條前提都要有 `breaks_if` 與 `checkable_by`。**`NONE` 最多 1 條**（寫不成查得到的事的放 `not_checkable`，不當前提）。
- 至少一條出場條件的動作是出清或減半，而且是財報數字的門檻（之後由程式比對，不靠 AI 判）。
- `against` 要 3 點，每點至少一條通過檢查的引用。沒有反方的草稿不收。
- `sources` 的網域要通過 `safeWebUrl`；不在共用清單的標「新的來源，存檔前會先試抓」。

### 2.3 使用者怎麼同意

草稿存在新表 `own_drafts`（`ticker`、`file_id`、`run_id`、`created_at`、`status`：`READY`／`USED`／`DISMISSED`／`EXPIRED`、`payload`、`based_on_version`），不進帳戶狀態。

- **在哪裡看**：編輯論點頁（`#/h/<代號>/thesis`）。有 `READY` 的草稿時，右邊「新的」那一欄上面多一塊「stock bot 的草稿（M/D）」：
  1. 最上面是**反方的三點**與「今天沒有持股會不會買」的答案（先看反方，再看草稿；這是防線，對應討論包固定指示的第 1、3 點）。
  2. 論點本文：一個「用這段」的按鈕，按了才填進右邊的論點欄，填進去之後可以改。
  3. 前提逐條：每條顯示文字、「怎樣算不成立」、查得到的來源（或紅字「stock bot 監測不了這一條」）、引用（可展開）。每條一個勾選，**預設都不勾**。勾了才填進右邊；可以改字。
  4. 出場條件逐條：同上，預設不勾，動作可以改。
  5. 同業與來源：逐個勾選。
  6. `not_checkable`：只顯示，不能勾（提醒使用者這些要自己留意）。
- 勾選、修改之後，照**現有的**預覽與存檔流程走（`POST /api/ops/own-thesis`）：前提的對應（`mapPremises`）、出場條件整組送改寫再到持股頁確認（`planExits`、`own_check`）、論點變動後的審查，全部不變。所以**出場條件要過兩關**：在草稿上勾、改寫後在持股頁再確認一次。
- 前提的 `origin`：原樣勾選的記 `AI_DRAFT_ACCEPTED`（這個值本來就有），改過字的記 `USER`。`breaks_if` 存進前提的 `breaksIf`（欄位本來就有，進審查的證據包）。論點的 `source` 多一個值 `DRAFT`。
- 存檔後草稿標 `USED`；「不用這份草稿」→ `DISMISSED`；30 天沒處理 → `EXPIRED`。新的草稿回來時舊的 `READY` 標 `EXPIRED`。草稿是照哪一版論點寫的（`based_on_version`）和現在不同時，頁面寫「這份草稿是照第 N 版寫的，之後你改過論點」。

### 2.4 怎麼避免 AI 出題又改考卷

問題有兩層：(a) 寫前提的 AI 把題目出得容易過；(b) 判前提的 AI 偏袒 AI 寫的字。對應的做法：

| # | 做法 | 擋的是 |
|---|---|---|
| 1 | **每一條都要使用者勾選才生效**，預設不勾；沒勾的不存在 | (a)：題目最後是使用者選的 |
| 2 | **考卷盡量由程式改**：草稿至少一條出清或減半的出場條件是財報數字門檻，成立與否由程式比對 XBRL；前提標 `checkable_by`，`NONE` 最多一條 | (b)：能不靠 AI 判的就不靠 |
| 3 | 每條前提都要寫 `breaks_if`，而且反方先寫、草稿必須附反方三點 | (a)：不能只寫「需求持續成長」這種證偽不了的句子 |
| 4 | **判的人看不到出題的過程**：審查的證據包只有前提的文字與 `breaks_if`，沒有草稿的理由、引用、正反方的全文；審查判成立或不成立都要自己從證據包找逐字引用（照舊）；論點那一份 note 照舊不能當證據 | (b) |
| 5 | **AI 不會自己改題目**：沒有定期重寫；審查不能改前提（照舊）。草稿只在新增自選時（一次）與使用者按下時產生 | (a)：題目不會跟著答案漂 |
| 6 | **前提被判不成立之後的草稿另外處理**：這檔有還沒回覆的乙類通知時，不自動產生草稿；使用者自己按的話，草稿最上面固定寫「前提 P2 剛被判不成立。在這之後改論點，很容易只是替繼續持有找新理由」，草稿**不能沿用被判不成立的那一條**（程式擋：`keep_id` 不能是它；文字很像的標出來），存檔照舊算「失效後修改」並計次 | (a) 最危險的情況 |
| 7 | **分開記成績**：運作統計加一段，依前提的來源（你寫的／原樣勾選的草稿）分開列審查的結果（成立、不成立、證據不足的次數）。草稿的前提如果幾乎都判成立、而你寫的不是，就是出題偏鬆的訊號 | 兩者；事後看得到 |
| 8 | 草稿與審查用不同的 prompt、不同的執行；審查三票，草稿一份 | (b) |

做不到的事也寫清楚：出題與判題是同一家的模型，系統性的盲點（兩邊都相信同一個錯的說法）這些做法擋不掉。底線仍然是慢規則與使用者定的、由程式比對的條件。

### 2.5 什麼時候產生

| 時機 | 做法 |
|---|---|
| **新的自選**（新的 `fileId`：快照新增、建立帳戶、轉入、認養、清單外買進歸自選） | 當天的每日流程自動開一次（每份論點檔只自動一次）。在那之前使用者已經自己存了論點 → 不開 |
| **使用者按「請 stock bot 草擬」**（持股頁、還沒有論點的清單、編輯論點頁） | 立刻開。每檔 7 個日曆天最多 1 次；有還在跑的就不重開 |
| 論點滿一年（`THESIS_OLD`）、`PREMISE_NO_DATA`、`NO_CONSENSUS` | 「要看的事」那一行多一個「請 stock bot 草擬」的連結；不自動開 |
| 有還沒回覆的乙類通知 | 不自動開；手動可以（§2.4 第 6 點） |
| 定期 | **不做**（§2.4 第 5 點） |

- 草稿回來：列進「要看的事」（新的 `DRAFT_READY`：`MU 的論點草稿好了，等你看（12/20 之後不再列）`）。**使用者自己按的**另外推一則 LINE（一行加連結；那是他在等的回覆）；自動開的不推，月報的「要看的事」那一行會算到。
- 草稿失敗（退回、逾時）：使用者按的 → 網站那個按鈕旁邊寫原因與「再試一次」，並推一則 LINE；自動的 → 記錄，照 G22 連續 2 次告警。

## 3. 成本與次數

**沒量過的**：任何一種執行用掉多少訂閱額度（T10 當時分不出來，使用者決定不單獨量）。下面只有次數、時間、字數；token 用英文約 4 字一個粗估，也沒量過。

**不多任何一種新的雲端執行**（第一版的搜尋任務拿掉了）。變的是：

| 變化 | 多少 |
|---|---|
| 一次審查多讀的字 | 最多 60,000 字（§1.5 的上限），由 6 個子代理各讀一次（分析師、多方、空方、三票）。現有的證據包在 MU 那次約 5 萬字，所以最壞是一次審查讀的量變成約 2.2 倍；分析師沒有要查的時候不變 |
| 一次審查多花的時間 | 沒量過。分析師多幾次 WebSearch 與取文件（Worker 每篇 0.2～1.5 秒）；原本是 6 分 40 秒 |
| 審查的次數 | 有「需要外部資料」前提的股票，月底檢查點從「有新申報才審」變成每個月都審：每檔每年從估計的 6～8 次回到 12 次（那個「跳過三到五成」本來也沒量過）。財報後 4 次、提前審查多半 0～3 次不變；大跌無申報改開提前審查，但受同一個 30 天上限 |
| 草稿 | 每份論點檔自動 1 次＋使用者按的（每檔每週最多 1 次）。結構是研究員＋反方＋正方＋主筆，沒量過 |

以 4 檔自選、都有這種前提估：一年約 4 ×（12＋4＋2）≈ 70 次審查，每次最多多讀 6 萬字 × 6 人。實際多讀多少看分析師取了幾份——執行紀錄有 `added_docs`，運作統計直接列每次取了幾份、幾個字（T57）。

排程的上限（每個排程每小時 30 次觸發）不受影響。額度用完時新的執行被拒絕（`FIRE_FAILED`），和現在一樣照規則。
