### 0.5 實測：Worker 從 Cloudflare 抓不抓得到全文（2026-11-20，`/admin/web/test`，0.14.1）

「抓得到」＝HTTP 200、轉成純文字後超過 200 字的段落合計 ≥ 1,500 字。每個網址只試一次，沒有重試；樣本很小，只能看方向。

| 來源 | 結果 |
|---|---|
| Yahoo RSS 標題的連結（MU、NVDA、`000660.KS` SK 海力士、`005930.KS` 三星，各取最新 3 則，共 12 則） | 8 則抓得到全文與發布日：Yahoo 上的新聞稿、fool.com、stocktwits.com、tikr.com、247wallst.com。4 則抓不到：都是 Yahoo 轉載通訊社的文章，只有開頭一小段（0～1,400 字）。**韓國代號的 RSS 可以用**（15、16 則） |
| TrendForce 新聞稿（`/presscenter/news/…`）與新聞（`/news/…`） | 抓得到，全文 3,200～6,000 字，JSON-LD 有發布日。付費報告頁（`/research/download/…`）只有摘要 |
| dramexchange.com 週報 | 抓得到（1,846 字），**認不出發布日** |
| techpowerup.com、datacenterdynamics.com 的文章 | 抓得到，有發布日（`<time>`） |
| nvidianews.nvidia.com、semiconductors.org（SIA）、businesskorea.co.kr | 列表頁抓得到（文章頁沒另外試；SIA 的日期認錯成 2018） |
| reuters.com（401）、bloomberg.com（403）、wsj.com（401）、koreaherald.com（403）、biz.heraldcorp.com（403）、mobileworldlive.com（403）、digitimes.com（Access denied）、eetimes.com（520） | **被擋** |
| cnbc.com、asia.nikkei.com、news.skhynix.com、news.samsung.com、thelec.net 的列表頁 | 回 200 但沒有內文（要 JavaScript）；文章頁沒試，不能下結論 |
| investors.micron.com、en.yna.co.kr | 試的網址是 404（網址是猜的），不能下結論 |
| sec.gov 的網頁（不是 EDGAR 的 API） | 403（探測用的是瀏覽器的 User-Agent；EDGAR 那條路照舊用宣告的 User-Agent，沒有問題） |

**讀法**：

1. 產業報價這一類（TrendForce）抓得到，而且有日期——這正是「產業新聞類條件」最需要的來源。
2. 大型通訊社與財經媒體一律被擋。它們擋的是機房的 IP 與沒有登入的讀者；雲端排程的沙盒也是機房 IP，會不會比較好**沒量過**。
3. **抓得到不等於可信**：RSS 連結抓得到的多半是 fool.com、stocktwits 這種評論文。所以清單要分級，不能「抓得到就算證據」。
4. 沒量的：公司投資人關係網站的文章頁、PDF（Worker 不解析 PDF）、同一個網站連續抓多篇會不會被擋、雲端排程在加了允許網域之後 WebFetch 讀不讀得到。

## 1. 網頁證據

### 1.1 原則

1. **原文一律由程式（Worker）抓，放進證據包。** 三票的審查照舊只讀證據包、不上網；`check.ts` 的逐字引用檢查一行都不改。使用者在網站上看到的快照，就是 AI 讀的那一份。
2. **AI 只做一件新的事：找網址**（搜尋任務，§1.5）。它送回的標題與理由是資料，不是證據。
3. **抓得到 ≠ 可信**：來源分級（§1.3），權限跟著級別走（§1.6）。
4. 抓不到的來源不硬抓、不換方法繞過（不偽裝登入、不用第三方的全文代理）。抓不到的只留標題與網址當「初判」。

為什麼不照前一個工作階段的做法（雲端環境加允許網域 → 排程自己讀、引用 → Worker 再抓同一個網址驗證）：WebFetch 給模型的是另一個模型整理過的字（§0.3），引用對不上原文；排程和 Worker 兩次抓到的頁面也可能不同（動態內容、地區、擋機器人的頁面）。結果是「能驗證的」仍然只有 Worker 抓得到的那些，卻多了一次環境設定的變更與一條驗證流程。

### 1.4 抓取與快照

函式 `fetchWebDoc(fetcher, url, now)`（`worker/src/data/webDoc.ts`，從量測用的 `webProbe.ts` 改）與新表 `web_docs`。

**抓取的規則**：

- 只收 `https`、公開主機（`safeWebUrl`）；網域要在共用清單或這檔的 `domains` 裡；`NAMED` 的路徑限制照清單的 `note`。
- 逾時 15 秒；最多讀 2 MB；跟著轉址，但**轉址後的主機也要在清單內**，否則當成失敗。
- 只收 HTML。PDF 與其他格式 → `status = 'UNSUPPORTED'`（不解析 PDF）。
- 內文（超過 200 字的段落合計）少於 1,500 字 → `status = 'THIN'`（多半是付費牆、同意頁、要 JavaScript）。
- **發布日**：`findPublished`（meta、JSON-LD 的 `datePublished`、`<time datetime>`）。RSS 來的另有 RSS 的發布時間：兩個都有而且差超過 3 天 → 用比較晚的那個，並標 `date_conflict`。都沒有 → `published = null`。
- 同一個網站一次流程最多抓 4 篇，中間隔 1 秒；失敗不重試（下一次搜尋或 RSS 再出現時再試）。
- 存的文字最多 30,000 字（開頭起算），超過的截掉並標記（G23：`truncated = 1`，證據包的標題寫「（只有前 30,000 字）」）。

**`web_docs`**（只增加；市場資料類，上線後留著）：

| 欄位 | 說明 |
|---|---|
| `id` | `web:<網址的 SHA-256 前 16 碼>`，也是證據包的 `source_id` |
| `url`、`final_url`、`domain`、`tier` | |
| `ticker`、`file_id` | 為哪一檔抓的（同一個網址為兩檔各抓一次時各存一列） |
| `via` | `RSS`／`SEARCH`／`MANUAL`（使用者在網站貼的網址，第二階段才做） |
| `ref` | 搜尋任務的 `run_id`，或 RSS 的來源編號 |
| `premise_id`、`cond_id` | 搜尋任務說它和哪一條有關（可以是空的；只是線索） |
| `title`、`published`、`published_from`、`date_conflict` | |
| `fetched_at`、`session` | 抓取時間、訊號日 |
| `status` | `OK`／`THIN`／`BLOCKED`（HTTP 4xx、5xx）／`UNSUPPORTED`／`NOT_LISTED`／`ERROR` |
| `http_status`、`chars`、`truncated`、`text_sha256` | |
| `text` | 純文字（只有 `OK` 的存） |

- **不重抓**：同一檔同一個網址已經有 `OK` 的列就用那一列（文章改版不追；被引用的就是當時抓到的那一版）。
- **repo 是公開的**：快照只在 D1。匯出（`EXPORT_TABLES` 加 `web_docs`）落在 `records/`，不進 git。
- **網站怎麼顯示**：審查紀錄頁列出這次證據包裡的網頁文件（標題、來源、級別、發布日、抓取日、連結）與被引用的片段；不提供整篇全文的頁面（著作權；要看全文點連結）。抓不到與不在清單的網址列在下面「沒有讀到的」，寫原因。
- **保留**：被任何一次審查的證據包用過的永久留著（之後要能對引用）；沒被用過的 `OK` 文件 180 天後刪掉 `text`、留列。

**進證據包的條件**（`thesisFile` 組的時候）：`status = 'OK'`、`published` 不是空的、`published` ≤ 決策日、而且在「上次有結論的審查的決策日」之後（沒有上一次時取最近 120 天）。最多 8 份，順序：`PRIMARY` → `NAMED` → `MEDIA`，同級新的在前；超過的記在證據包的說明裡（G23）。

`PackDoc`：`kind: 'web'`（新的種類），`source_id` = `web_docs.id`，`date` = `published`，`title` 寫「〔網頁｜<級別的白話>｜<label>〕<標題>（發布 <日期>，<抓取日> 抓）」，`url`、`fetched_at` 照填。**認不出發布日的不進證據包**（`check.ts` 要日期 ≤ 決策日；拿抓取日充當會讓三年前的舊文變成「新證據」）；它們列在網站的「沒有讀到的」，原因寫「認不出發布日」。

### 1.5 搜尋任務（`WEB_SEARCH`，L1）

| 項目 | 內容 |
|---|---|
| 白話名稱 | 找資料 |
| 等級與票數 | A1（只轉交），一票，Sonnet，不開子代理 |
| prompt | `ai/prompts/web_search_v1.md`；`run.md` 第一句的「不要上網找資料」改成「除非功能的 prompt 明寫可以用 WebSearch；任何情況都不要用 WebFetch 或 curl 讀 Worker 以外的網址」 |
| 證據包 | 這檔的名稱與代號；**需要外部資料的前提與條件**（下面）；`webSources`（同業、專用網域）；共用清單的網域（讓它優先找抓得到的）；上次搜尋已經抓過的網址（不要重複） |
| 要它做的 | 對每一條各搜尋 1～3 次，只用 WebSearch。挑「可能顯示這條成立或不成立」的結果，**兩個方向都找**（中立原則，`ai_layer` §2.6） |
| 輸出（`payload`） | `{ "found": [{ "url", "title", "for": "P5" 或 "C12", "why": "一句" }], "queries": ["…"] }`，`found` 最多 12 筆。不寫結論、不判前提、不摘要內容 |
| 程式怎麼用 | 逐筆：網址格式不對的丟掉；不在清單 → `NOT_LISTED`（存標題與網址）；在清單 → `fetchWebDoc`（最多 8 篇，`PRIMARY` 優先）。`title`、`why` 一律當資料顯示，不當證據 |

**哪些前提與條件「需要外部資料」**：

- 你的前提（不含系統預設）最近一次檢查是三票一致的「證據不足」（就是 `PREMISE_NO_DATA`，T47）；
- 還沒被檢查過的你的前提（新的論點檔第一次）；
- 你定的條件裡指名了網頁來源的（§1.6 的 `confirm_by` 有網域）、狀態是 `REVIEW_ONLY` 的。

一條都沒有 → 這檔不開搜尋（G11）。

**失敗**（G22）：逾時、被退回、格式不合 → 這次沒有新的網頁文件，審查照開（它本來就不依賴搜尋）；紀錄寫「找資料沒有結果：<原因>」，不當成「沒找到東西」。連續 2 次失敗 → 列進現有的 AI 告警。搜尋成功但 0 篇抓得到 → 記「找到 N 個網址，都不在清單或抓不到」，那幾條前提的 `PREMISE_NO_DATA` 照舊列。

**安全**：搜尋結果與網頁內文都是外部文字。搜尋任務送回的只有網址清單（程式逐欄檢查），就算它被搜尋結果裡的字帶偏，最壞的結果是抓到不相干的清單內網頁；網頁內文進證據包時和申報一樣是資料（`run.md` 第 4 步）。現有的審查任務技術上也能搜尋（只靠 prompt 擋，T49 記過）：後果仍有上限——它搜到的東西不在證據包裡，當不了引用。

### 1.6 網頁證據能觸發什麼（X2、X3；使用者 2026-11-20 選定）

`reviewDecision` 判「不成立的前提」（`own_thesis_design` §1.6 第 1 點）與「你定的條件由審查確認成立」（第 2 點）時，合格的引用來源從「`filing` 或 `xbrl`」放寬成下表。三票一致、同一條前提（G14）、通過逐字檢查，這些都不變。

| 引用來自 | 判前提不成立（→ 乙類，預設不動） | 確認你定的條件成立（→ 甲類，預設照當時的決定） |
|---|---|---|
| 自己或同業的申報、財報表（`filing`、`xbrl`） | 可以（照舊） | 可以（照舊） |
| 網頁，`PRIMARY` 或 `NAMED` | 可以 | **只有條件指名了這個網域時**可以 |
| 網頁，`MEDIA` | 可以，但三票各自至少要引用 **2 份不同網域**的文件（單一媒體的一篇報導不夠） | 不行（除非條件指名了它） |
| 新聞標題、搜尋結果的標題、不在清單的網頁、認不出日期的網頁 | 不行（照舊只是初判） | 不行 |

- **條件怎麼「指名來源」**：事件類條件的 `check.confirm_by` 多一種寫法 `web:<網域>`（例如 `["web:trendforce.com"]`）。改寫（`own_check`）時 AI 可以提出，**使用者勾選條件時看得到並可以改**；網域要在清單或這檔的 `domains` 裡，否則擋下。`confirmMode` 多一種結果：`confirm_by` 有 `web:` 的 → `REVIEW_ONLY`，顯示「審查時用 <來源> 的網頁檢查」（G24：寫的就是實際在做的事）。成立時 `met_basis = 'WEB_VOTE'`。
- **不每天監測**：網頁來源的條件只在審查時檢查（審查前會先跑搜尋與 RSS）。要每天盯網頁等於每天多一次雲端執行，不做。
- **通知的文字**（其餘照 `own_thesis_design` §1.10）：
  - 乙類的理由：`依據：TrendForce 2026-09-30 的新聞稿（網頁；引用與連結在網站）。你沒有為這件事定過出場條件，由你決定。`
  - 甲類的理由（`WEB_VOTE`）：`TrendForce 2026-09-30 的新聞稿，3 票確認（網頁；引用與連結在網站）`
  - 依據裡同時有申報與網頁時，申報寫在前面。
- **頻率上限不變**：乙類每檔 30 天 1 則；甲類不設上限。靜默期照舊（同一條前提）。
- `RAISE`（提高到 125%）與「回到標準」不能只靠網頁證據：每條前提 `HOLDS` 的引用裡至少要有一條來自申報或財報表（往上加碼的門檻不放寬）。

### 1.7 什麼時候找、多久一次

| 時機 | 做什麼 |
|---|---|
| **月底檢查點的前一個交易日**（月報前兩天，UTC 23:30 的每日流程） | 每一檔有「需要外部資料」的前提或條件的自選：抓 S1、S2，開搜尋任務。01:30 套用搜尋結果、抓網頁。隔天月底檢查點算 `newEvidence` 時多一個原因 `WEB`（有新的、合格的網頁文件或同業申報）→ 照審 |
| **財報後的審查、提前審查、你定的「重新審查」條件、論點變動後的審查** | 開審查的同一次流程先抓 S1、S2（程式，幾秒）；**不另外開搜尋**（不讓當天通知多等一次排程，G7），用最近 35 天內搜尋抓到的文件 |
| **個股自身大跌、沒有新申報可檢查**（原本只列進「要看的事」的 `PRICE_NO_FILING`） | 改成：抓 S1、S2 並開一次搜尋；01:30 套用後如果有合格的新文件 → 這就是新證據，照 `own_thesis_design` §2.4 開提前審查（同一個 30 天上限）；沒有 → 照舊列 `PRICE_NO_FILING`，文字加「也沒有找到清單內來源的新消息」 |
| 減半檢視（F7） | 不搜尋；證據包帶最近 35 天內已經存的網頁文件與同業申報（由 `thesisFile` 組） |

- **搜尋的上限**：每檔 30 個日曆天最多 2 次（月底 1 次＋大跌觸發 1 次）。被上限擋掉的寫進紀錄（G8）。
- 沒有「需要外部資料」的前提或條件的月份不搜尋；S1、S2 也只為有 `webSources` 的檔跑。

### 1.8 哪些功能可以用（對照 G1～G25）

| 功能 | 用不用 | 理由與對應的規則 |
|---|---|---|
| 定期審查（F24） | **用**（S1、S2、S3） | 這是起因。G10：由 `thesisFile` 組；G11：`newEvidence` 多 `WEB`；G12：改寫（§1.9）；G14、G15、G19 不變 |
| 你定的條件（F25 的事件條件） | **用，但只在審查時**（指名來源的網頁，§1.6） | G16：來源由使用者勾選時確認；G24：顯示「審查時檢查」 |

| 個股自身大跌的提前審查 | **用**（觸發一次搜尋） | G6：搜尋結果寫進 `web_docs`，另一個函式讀來開審查；G8：合併計算上限 |
| 硬事件法庭（F19） | 不用 | 硬事件由申報的類型定義（重編、會計師辭任、延遲申報、被收購）；放空報告之類要每天搜尋才有意義，成本與誤報都高 |

### 1.9 通用規則怎麼改

- **G12 改寫**：「會改變下單的結論，引用要來自**程式自己抓、存了快照的原文**：申報、財報表，或清單內網域、認得出發布日的網頁全文（級別決定能做什麼，`web_evidence_design` §1.6）。標題、搜尋結果、AI 的摘要只能當初判。」
- **新增 G26**：「AI 不讀網路上的原文；需要網路資料時，AI 只找網址，原文由程式抓進證據包。」

### 1.11 不做的與理由

- **雲端排程自己讀網頁**（環境加允許網域、WebFetch 或 curl）：先不做，理由在 §1.1。**如果跑兩三個月後，運作統計顯示重要的來源 Worker 一直抓不到**，再做第二階段：請使用者在環境加那幾個網域，實測 WebFetch 與 curl 讀不讀得到；讀得到的內容也只當**初判**（進論點檔的事件、列進「要看的事」、可以觸發提前審查），不能當引用——它是模型轉述的，沒有人能對原文。使用者 2026-11-20 表示可以接受整理過的內容；這裡的意思是它可以用來「提醒與觸發」，但不讓它直接變成賣出建議的依據。
- **connector 當證據來源**：內容只存在雲端那一次執行裡，Worker 拿不到、對不了引用；免費等級的資料商多半只有標題與摘要。排程裡的 connector 維持全部移除（帳號之後新接的 connector 預設會被帶進排程，要再確認）。
- **付費新聞**：不變（`design_v2` §10 第 23 點）。
- **解析 PDF**（很多亞洲公司的財報新聞稿只有 PDF）：Worker 裡做不划算；先看運作統計有多少 `UNSUPPORTED` 再說。
- **使用者自己貼網址當證據**（`via = 'MANUAL'`）：表先留欄位，畫面第二階段再做。

## 2. stock bot 草擬論點（X4；使用者 2026-11-20 選定）

### 2.1 定位

- **改掉的**：2026-11-15 的方案 B（論點只在 claude.ai 討論、stock bot 不寫論點）與「請 AI 草擬前提拿掉」。
- **沒有改的**：論點是使用者的（`own_thesis_design` §1.4）。草稿不是論點：**每一條都要使用者明白同意才生效**，沒有任何一條會自己變成前提或條件；審查不能改論點、不能新增前提，這一點也不變——草稿是另一個功能、只在使用者要的時候或新增自選時產生。
- **留著的第二條路**：討論包、貼回、`/thesis`（T48）、編輯論點頁的手寫，程式都不拆。想和 AI 爭辯的時候用那一條。
- 為什麼這次的草稿和 11-15 拿掉的那個不同：當時的草擬只有一票、只看這家公司的申報、題目寫死「使用者想加進自選但沒寫理由」（P7），寫出來的是通用句。這次有買進時的一句話、上一份論點檔、同業與產業的文件，而且輸出要帶「怎樣算不成立」與來源。品質仍然要看實際結果（§2.4 第 7 點的成績表）。

### 2.2 草稿任務（`OWN_DRAFT`）

| 項目 | 內容 |
|---|---|
| 白話名稱 | 草擬論點 |
| 等級與票數 | A2（只說明；使用者同意才有效果），**一份**，不是三票 |
| prompt | `ai/prompts/own_draft_v1.md` |
| 前置 | 先抓 S1、S2 並開搜尋任務（§1.5；這時「需要外部資料的」是買進時的一句話與公司的主要業務）；搜尋套用、網頁抓完之後才開草稿。自動開的跨兩次排程（23:30 搜尋 → 01:30 開草稿 → 03:30 套用）；使用者按的當場開搜尋，Worker 收到搜尋結果後接著開草稿（不等排程） |
| 證據包 | `thesisFile`（買進時的一句話、上一份論點檔、現行的前提與條件、事件、歷次審查與使用者的回應）、價格與規則狀態、XBRL 八季、最近一份 10-Q／10-K 的 MD&A、最近的 8-K、同業申報、網頁文件。**只放比重，不放金額與股數**（和討論包相同） |
| 流程（各用獨立的子代理） | ① 分析師（Sonnet）：事實摘要，只用證據包。② **反方先寫**（Sonnet）：這家公司最可能讓持有者後悔的三件事，各附證據；以及「如果現在沒有持股，今天用這個價格會不會買」的反方答案。③ 正方（Sonnet）：持有的理由，必須回應反方的三件事。④ 主筆（Opus）：寫草稿 |
| 輸出（`payload`） | 見下 |

```json
{
  "thesis": "一段，300 字以內",
  "premises": [{
    "text": "…（200 字以內）",
    "keep_id": "P2 或 null（沿用現行的哪一條；沒改字才能寫）",
    "breaks_if": "什麼情況算不成立（要寫成查得到的事）",
    "checkable_by": "XBRL | FILING | PEER_FILING | WEB | NONE",
    "source_hint": "查得到的話，是哪個來源（例如 trendforce.com、SK 海力士的財報新聞稿）",
    "evidence_ids": ["E1"]
  }],
  "exits": [{ "text": "查得到的事", "action": "EXIT | HALF | REVIEW", "premise_index": 0, "evidence_ids": ["E2"] }],
  "sources": { "peers": [{ "name": "…", "edgar": "…", "yahoo": "…" }], "domains": ["…"] },
  "against": ["反方最強的三點，各一句，附 evidence_ids"],
  "would_buy_today": { "answer": "YES | NO | UNSURE", "why": "一句" },
  "not_checkable": ["寫不成查得到的事、但主筆認為重要的觀察，各一句"]
}
```

**程式檢查**（不過的整份退回、記錄、照 G22 告警，不給使用者半份草稿）：

- 外殼與 `evidence` 照 `check.ts`（引用逐字出自證據包）。
- 前提 3～5 條、出場條件 2～6 條；字數上限同 `parseThesisBlock`。
- 每一條前提都要有 `breaks_if` 與 `checkable_by`。**`NONE` 最多 1 條**（寫不成查得到的事的放 `not_checkable`，不當前提）。
- 至少一條出場條件的動作是出清或減半，而且是財報數字的門檻（之後由程式比對，不靠 AI 判）。
- `against` 要 3 點，每點至少一條通過檢查的引用。沒有反方的草稿不收。
- `sources` 的網域要通過 `safeWebUrl`；不在共用清單的標「新的來源，存檔前會先試抓」。

### 2.3 使用者怎麼同意

草稿存在新表 `own_drafts`（`ticker`、`file_id`、`run_id`、`created_at`、`status`：`READY`／`USED`／`DISMISSED`／`EXPIRED`、`payload`、`based_on_version`），不進帳戶狀態。

- **在哪裡看**：編輯論點頁（`#/h/<代號>/thesis`）。有 `READY` 的草稿時，右邊「新的」那一欄上面多一塊「stock bot 的草稿（M/D）」：
  1. 最上面是**反方的三點**與「今天沒有持股會不會買」的答案（先看反方，再看草稿；這是防線，對應討論包固定指示的第 1、3 點）。
  2. 論點本文：一個「用這段」的按鈕，按了才填進右邊的論點欄，填進去之後可以改。
  3. 前提逐條：每條顯示文字、「怎樣算不成立」、查得到的來源（或紅字「stock bot 監測不了這一條」）、引用（可展開）。每條一個勾選，**預設都不勾**。勾了才填進右邊；可以改字。
  4. 出場條件逐條：同上，預設不勾，動作可以改。
  5. 同業與來源：逐個勾選。
  6. `not_checkable`：只顯示，不能勾（提醒使用者這些要自己留意）。
- 勾選、修改之後，照**現有的**預覽與存檔流程走（`POST /api/ops/own-thesis`）：前提的對應（`mapPremises`）、出場條件整組送改寫再到持股頁確認（`planExits`、`own_check`）、論點變動後的審查，全部不變。所以**出場條件要過兩關**：在草稿上勾、改寫後在持股頁再確認一次。
- 前提的 `origin`：原樣勾選的記 `AI_DRAFT_ACCEPTED`（這個值本來就有），改過字的記 `USER`。`breaks_if` 存進前提的 `breaksIf`（欄位本來就有，進審查的證據包）。論點的 `source` 多一個值 `DRAFT`。
- 存檔後草稿標 `USED`；「不用這份草稿」→ `DISMISSED`；30 天沒處理 → `EXPIRED`。新的草稿回來時舊的 `READY` 標 `EXPIRED`。草稿是照哪一版論點寫的（`based_on_version`）和現在不同時，頁面寫「這份草稿是照第 N 版寫的，之後你改過論點」。

### 2.4 怎麼避免 AI 出題又改考卷

問題有兩層：(a) 寫前提的 AI 把題目出得容易過；(b) 判前提的 AI 偏袒 AI 寫的字。對應的做法：

| # | 做法 | 擋的是 |
|---|---|---|
| 1 | **每一條都要使用者勾選才生效**，預設不勾；沒勾的不存在 | (a)：題目最後是使用者選的 |
| 2 | **考卷盡量由程式改**：草稿至少一條出清或減半的出場條件是財報數字門檻，成立與否由程式比對 XBRL；前提標 `checkable_by`，`NONE` 最多一條 | (b)：能不靠 AI 判的就不靠 |
| 3 | 每條前提都要寫 `breaks_if`，而且反方先寫、草稿必須附反方三點 | (a)：不能只寫「需求持續成長」這種證偽不了的句子 |
| 4 | **判的人看不到出題的過程**：審查的證據包只有前提的文字與 `breaks_if`，沒有草稿的理由、引用、正反方的全文；審查判成立或不成立都要自己從證據包找逐字引用（照舊）；論點那一份 note 照舊不能當證據 | (b) |
| 5 | **AI 不會自己改題目**：沒有定期重寫；審查不能改前提（照舊）。草稿只在新增自選時（一次）與使用者按下時產生 | (a)：題目不會跟著答案漂 |
| 6 | **前提被判不成立之後的草稿另外處理**：這檔有還沒回覆的乙類通知時，不自動產生草稿；使用者自己按的話，草稿最上面固定寫「前提 P2 剛被判不成立。在這之後改論點，很容易只是替繼續持有找新理由」，草稿**不能沿用被判不成立的那一條**（程式擋：`keep_id` 不能是它；文字很像的標出來），存檔照舊算「失效後修改」並計次 | (a) 最危險的情況 |
| 7 | **分開記成績**：運作統計加一段，依前提的來源（你寫的／原樣勾選的草稿）分開列審查的結果（成立、不成立、證據不足的次數）。草稿的前提如果幾乎都判成立、而你寫的不是，就是出題偏鬆的訊號 | 兩者；事後看得到 |
| 8 | 草稿與審查用不同的 prompt、不同的執行；審查三票，草稿一份 | (b) |

做不到的事也寫清楚：出題與判題是同一家的模型，系統性的盲點（兩邊都相信同一個錯的說法）這些做法擋不掉。底線仍然是慢規則與使用者定的、由程式比對的條件。

## 3. 成本與次數

**沒量過的**：任何一種執行用掉多少訂閱額度（T10 當時分不出來，使用者決定不單獨量）。下面只有次數與時間，額度要等跑一個月後看 claude.ai 用量頁的整體變化（和 `SETUP.md` 現在的做法相同）。

| 執行 | 一次多久 | 多常 | 以 4 檔自選估一個月 |
|---|---|---|---|
| 搜尋任務（一票 Sonnet，不開子代理，幾次 WebSearch） | 沒量過。連線測試（含一次 WebSearch）是 24～47 秒，可以當下限 | 每檔每月最多 1 次（有需要外部資料的前提才開）＋大跌觸發最多 1 次 | 0～8 次，通常 ≤ 4 |
| 審查（F24）多出來的 | 一次審查 6 分 40 秒（4 份文件時）。證據包最多多 8 份網頁、4 份同業申報，會變長，多多少沒量過 | 原本因為「沒有新證據」跳過的月份，有新的網頁文件時會多審 | 最多每檔每月 1 次（上限就是回到「每月都審」） |
| 草稿（分析師＋反方＋正方＋主筆；子代理的數目比一次審查少兩個） | 沒量過 | 每份論點檔自動 1 次＋使用者按的（每檔每週最多 1 次） | 上線時 4 次，之後很少 |
| Worker 抓網頁 | 每篇 0.2～1.5 秒（§0.5） | 每檔每次最多 8＋6 篇 | 不用額度；請求數遠低於現在月底的約 510 個 |

排程的上限（每個排程每小時 30 次觸發）：月底前一天 4 檔各開一次搜尋，加上原有的執行，離上限很遠。額度用完時新的執行會被拒絕（`FIRE_FAILED`）：搜尋與草稿失敗不影響規則與原本的審查。
