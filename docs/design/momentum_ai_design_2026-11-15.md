# 動能：三層配合的設計（2026-11-15）

> 狀態：使用者 2026-11-15 同意（計畫 T21，全部照建議）；還沒實作。
> 依據：`docs/plan/thesis_plan_2026-11-15.md`（稱呼、已經決定的方向十一點）、`own_thesis_design_2026-11-15.md` 第 4 章的通用規則 G1～G25、`design_v2_momentum_2026-11-07.md` §2.0、§2.3.1、§2.4、§3～§7、`ai_layer_design_2026-11-08.md` 的 F1、F2、F4、F18～F21 卡片、`docs/test-records/` 的 B-2、B-8、B-9。
> 和舊文件的關係：動能的進場審查（F1）、動能持股的硬事件（F19）、單月大跌說明（F20）、擬事件打分、候選股的每日掃描、策略檢討說明（F21）的做法，**這份和 `design_v2`、`ai_layer_design` 的卡片不同時，以這份為準**。沒提到的照舊。F19 法庭的幾處改動是共用函式，自選股也適用（§3.5 會標）。
> 不動的：動能規則本身（選股與排名、進場前 5、出場名次 15、lazy、依波動度減碼與緩衝 0.10、崩盤時減半）；F1 可以否決、F19 只限三個代碼並由使用者確認、F2／F3／F4 沒有 AI。
> 讀者：之後做實作的工作階段。檔案位置是 2026-11-15 的。
> 稱呼：L0 = 規則層；L1 = 輕 AI（一票）；L2 = 重 AI（三票一致）。「法庭」指 F1 的進場否決法庭（`MOM_ENTRY`）或 F19 的硬事件法庭（`HARD_EVENT`），會寫明是哪一個。「有結論」指三票一致（`Outcome.status` 是 `AGREED` 或 `INSUFFICIENT`）；票數不一致、資料缺漏、格式不合格、逾時、沒觸發成功都不算。

背景數字（B-9，2009–2026 共 17.7 年）：進場審查約 138 次（每年 7.8 次）；被收購、會計類、單日跳漲在要進場的前 5 名裡命中 0 次；照卡片定義會開法庭的約每年 0.2 次；動能持股的硬事件每年不到 0.1 次。`EARNINGS_DIVERGENCE` 與 `REGULATORY` 沒有測過。所以這份設計的方向是：AI 的範圍不擴大，把少數會發生的那幾次做對，把對結果沒有影響的執行拿掉。

## 3. 設計

### 3.1 動能的證據由一個函式組

新檔 `worker/src/app/momEvidence.ts`，把 `momAi.ts` 的 `entryEvidence` 搬過來擴充。F1 的規則偵測與法庭、F19 對動能持股的法庭、§3.6 的大跌那一行都用它（修 Q18）。它是即時組出來的，不存成物件。

```
momEvidence(env, fetcher, view, axis, ticker, benchmark, want: { docs: boolean, xbrlTable: boolean })
→ {
  cik, filings,            // 365 天內、決策日以前的申報
  hits: EntryHit[],        // 規則偵測（現有的全部）＋ sec_events 轉來的命中（下面）
  events: SecEventRow[],   // 這一檔 180 天內的 sec_events（含 INFO），顯示用
  docs: PackDoc[],         // want.docs 時：命中對應的申報原文、EPS 表、新聞標題
  xbrl: PackDoc | null,    // want.xbrlTable 時：XBRL 季度表（F19 的重大性數字）
  omitted: string[],       // 因為上限沒放進去的文件（「8-K 2027-01-06」）
  dataQuality, notes, r12
}
```

- **申報編號正規化**（修 Q1）：`sec_events.accession` 是 `edgar:` 開頭的去掉前綴再對申報清單；`nasdaq-rss:` 開頭的是新聞；其他（`price:`、執行編號）沒有原文。寫成一個函式 `accOf`，`startCourts` 也用它。
- **`sec_events` 轉來的命中**：這一檔、`source = 'SCAN'`、而且是下表其中一種。不看 `status`（F1 用過之後會標 `HANDLED`，§3.2）。

  | `sec_events.code` | 條件 | 變成的命中 | 往回看幾天（`event_date`） |
  |---|---|---|---|
  | `ACCOUNTING`、`REGULATORY`、`PENDING_MA`（掃描的三種候選） | — | 同一個代碼，`byRule: false` | 180、180、365（`HIT_WINDOW`；`REGULATORY` 新增 180） |
  | `GUIDANCE_CUT` | `detail_code` 是 `CUT` 或 `WITHDRAWN`（`own_thesis` §2.2），而且來源是申報（`form` 不是 `NEWS`） | `code: 'EARNINGS_DIVERGENCE'`、`sub: 'SCAN_GUIDANCE_CUT'`、`byRule: false` | 100 |

  每筆命中多一個欄位 `basis: 'FILING' | 'NEWS' | 'CALC'`：申報來的是 `FILING`，新聞標題來的是 `NEWS`，程式算的（單日跳漲、EPS 背離、股數）是 `CALC`。現有從申報分類來的命中都是 `FILING`。
- **原文的上限**（修 Q19）：一份法庭的證據包最多 6 份申報原文。順序：要法庭判斷的命中對應的申報（新到舊）→ 有 `EARNINGS_DIVERGENCE` 命中時最近一份 8-K 2.02。放不下的寫進 `omitted`，證據包的備註加一句「略過 N 份：…」，`mom_reviews.note` 也帶這一句。
- **抓不到資料**（修 Q9）：申報清單抓不到時 `dataQuality.filings = 'missing'`，回傳多一個 `filingsMissing: true`。呼叫端不能把它當成「沒有命中」（§3.3 的表）。

### 3.2 進場前回看（取代候選股的每日掃描）

使用者 2026-11-15 決定（改設計 §2.0 的 F18、§6.3「對持股與排名 6～10 的候選股」）。理由：掃了一整年的五檔候選，只有進場的那幾檔（每年約 8 檔）用得到，而且名單是上月底的（Q3）；改成進場前回看，涵蓋所有進場股，掃描量也變少。代價：新聞標題只剩回看當時 RSS 上的那十幾則，但標題本來就不能單獨支持否決（§3.3）。

**平常**：`scanTargets` 只回傳自選股與動能持股（拿掉 `CAND`；型別留著給舊資料）。規則分類段對候選股也不再跑（F1 本來就自己往回 365 天重新分類）。

**月報前一天（UTC 23:30，`momPreview`）**，對象是「這個月會進場的」加「被規則否決或要開法庭的那幾檔的遞補者」（現有的 `previewOrder`）：

1. 逐檔跑 `momEvidence`（規則偵測）。照 §3.3 的表下結論；要法庭而且已經有 `FILING` 或 `CALC` 命中的，當場開法庭。
2. 開一份**回看掃描**（`EVENT_SCAN`，`newRunId(session, EVENT_SCAN, 'LOOKBACK')`，`rule.detail.kind = 'LOOKBACK'`），和每日掃描分開，不動每日掃描的標記與失敗次數。內容：
   - 每檔的 8-K：`acceptedAt` 比 `lookback:<代號>` 新、而且（申報日在最近 30 個日曆天內、有 `SCAN_ITEMS` 裡的項目）或（最近 100 天內最新的一份、有 Item 2.02）。每檔最多 3 份（2.02 那一份優先，其餘新到舊），整份最多 12 份；放不下的寫進 `rule.detail.omitted` 與那一檔的 `mom_reviews.note`（「回看略過 N 份」）。
   - 每檔目前 RSS 上的新聞標題（一份文件）。
   - `facts` 的對象列用新的角色 `ENTRY`（「動能進場候選（本月）」）。
   - 沒有任何文件就不開。
3. prompt 用 `event_scan_v2`（`own_thesis` §2.2 已經要升版）：多說明 `ENTRY` 這個角色；類別與細項不變。

**套用回看掃描**（`applyEventScan`，`rule.detail.kind === 'LOOKBACK'`）：

- 有合格結論（定義同 `own_thesis` §2.6）→ 事件寫進 `sec_events`（`source = 'SCAN'`，欄位照 `own_thesis` §2.2）。狀態：§3.1 那張表的四種、而且來源是申報 → `NEW`；其餘 → `INFO`。`lookback:<代號>`（`flow_state`，記這次看到的最新 `acceptedAt`）往前推。
- 沒有合格結論 → 標記不動。第二次排程（UTC 01:30）重開一次；再沒有 → 那幾檔的 `mom_reviews.note` 加「進場前回看沒有結論」，推告警（`kind: F1_LOOKBACK_FAILED`）：
  `進場前回看連續 2 次沒有結論：MU 的 8-K 2026-11-20（Item 5.02）、8-K 2026-10-28（Item 2.02）還沒有被 AI 看過。規則偵測照常；月報照規則出。`

**第二次排程（UTC 01:30）**：套用結論之後跑新函式 `momRecheck`（條件和 `momPreview` 相同：下一個交易日是當月最後一個交易日，或今天就是月報訊號日；見下面「月報當天才進榜的」）。對這個月的 `mom_reviews` 逐列：

| 情況 | 做法 |
|---|---|
| `PENDING`，但那次法庭沒有結論，`court_tries < 2` | 重開一次（`court_tries` 加 1） |

### 3.4 有新證據才重開進場法庭

使用者 2026-11-15 決定（改設計 §6.2「下個月重新審查，或在 `lift_condition` 成立時解除」；修 Q5）。理由和 `own_thesis` §3.7 相同：同一批文件重讀一次，結論不同就是雜訊。

每個月的審查照樣做（規則偵測每次重算）；只有「要開法庭」那一步先看能不能沿用。

- **證據指紋**（`mom_reviews.evidence_key`）：這次要法庭判斷的命中，各取一個字串、排序後用 `;` 接起來。
  - 申報來的：`<code>|<sub>|<申報編號>`。
  - 單日跳漲：`ONE_OFF_JUMP|JUMP|<最大單日的日期>`（由 `jumpMetrics` 的 `j1Ago`、`j3Ago` 換成日期，取命中的那一個）。

  - 新聞來的不算進指紋。
- **上一次有結論的法庭**（`prev`）：這一檔最近一列「`source = 'AI'`、有 `run_id`、不是沿用的」`mom_reviews`（不限月份）。`courtVerdict` 的 `source` 因此要改：三票一致就記 `AI`，包含三票一致的「證據不足」（結論是准許；現在記成 `DEFAULT`）。票數不一致、逾時等照舊記 `DEFAULT`。

  | 原因 | 定義 |
  |---|---|
  | `NEVER` | 沒有 `prev` |
  | `HITS` | 指紋和 `prev.evidence_key` 不同 |

- **新開的法庭沒有結論**：有 `prev` → 沿用 `prev`（不能讓一次逾時把否決蓋掉），`note` 寫明；沒有 `prev` → 照規則准許（§3.3）。
- 規則直接下的結論（否決、資料可疑、准許）每個月重算，不沿用。

效果：帶著命中的股票大約每季（新財報）重審一次，加上有新命中的時候。

## 4. 不做的與理由

| 項目 | 理由 |
|---|---|
| 動能的論點檔、使用者定的條件、討論包 | 動能以規則為主，使用者不寫前提；沒有可以檢查的論點 |
| 動能持股的提前審查，或把財測下修、高層異動變成出場建議 | §3.6 |
| 新增硬事件代碼（破產、下市通知、資安） | §3.6 |
| AI 對出場（F2）、比例回調（F3）、依波動度減碼（F4）表示意見 | 設計已決定；「這檔還會漲，留著」是看多判斷，超出 AI 只能拿掉的範圍 |
| 讓晚到的否決自動重算月報 | 一年不到一次；自動改已經發出的清單，比讓使用者按一次「排除」風險大 |
| 把擬事件打分做成真的（每檔備證據） | §3.7 |
| 改 `EARNINGS_DIVERGENCE` 的偵測定義 | 沒有頻率的數字，先量（還沒決定的） |
| 同業、客戶、供應商的消息，內部人交易 | 和 `own_thesis` §2.9 相同 |
| 同產業最多幾檔之類的集中度規則 | 設計 §5：回測過，當規則有害。計畫 T35 的集中度檢查只說明 |

專業做法的對照（憑設計時的了解，沒有另外查證）：規則為主的動能策略，人工覆核通常只做交易前的資料與公司行動檢查、把被收購標的排除、類別很窄的否決並留紀錄；持有期間只處理收購、下市、財報不可信這類斷點；不逐檔解釋下跌，風險報表只給拆解；策略層級在事先定好的回撤點對照歷史檢討。這份設計和它一致。
